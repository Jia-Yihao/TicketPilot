# P11 澄清候选降级

## 为什么

缺订单号时 Agent 只会重复同一句「请提供订单号」。客户往往是真的想不起来单号，
而不是没听见提问：第二次被问同一个槽位时，对话已经走进死胡同，而
`repeated_clarification` 的阈值是 2，第二次追问当场就被整段转人工覆盖掉，客户
连一次自助的机会都没有。同时仓储层只有「按订单号取单」，没有任何「本人最近
几单」的读路径，Agent 手上根本没有可以列给客户点选的候选。

## 改什么

1. 新增按 `tenant_id + user_id` 过滤的最近订单查询（`CommerceRepository.list_recent_orders`），
   最多 3 条，只读、不新开公网端点。
2. 第二次缺 `order_id` 的追问改为**候选降级**：用模板列出该客户自己的最近订单
   候选卡片（L1 字段：订单号、商品名、状态、签收时间）与可直接点选的订单号，
   不调用模型；第一次追问与缺金额等其它槽位的追问保持原样。
3. `repeated_clarification` 改用独立的 `clarification_rounds` 阈值（默认 3），
   语义变成「追问一次 → 带候选追问一次 → 第三次仍未补上才转人工」；挫败度阈值
   `frustration_rounds` 不变。
4. 转人工时上下文包新增 `attempted_candidates`，把已经展示过的候选交给坐席，
   坐席不必再问一遍。
5. 候选属于个人信息：只出现在本次回复的卡片与建议里，trace 只记数量不记订单号。

## 不改什么

- 不引入模型参与澄清：候选由确定性查询与模板拼装，`AGENT_MODE=rules` 与
  `pydantic_ai` 输出逐字一致。
- 不猜订单号、不做模糊匹配：候选只能来自调用者本人的订单行。
- 不改意图路由、槽位抽取与写路径审批：`support` 的其它行为保持原样。
- 不让候选出现在坐席之外的渠道（通知、导出、日志）。

## 验收

- 第一次缺订单号：只有槽位追问，没有候选卡片。
- 第二次缺订单号：同一句话里给出 ≤3 个本人订单候选，客户点选订单号即可续跑被
  中断的意图；跨租户/跨用户的订单不出现在候选里。
- 第三次仍未补上：`HUMAN_HANDOFF`（`repeated_clarification`），上下文包含
  `attempted_candidates`；`clarification_count` 停在阈值不再增长。
- 同一段三次仍缺订单号的对话，阈值 2（旧）与阈值 3 + 候选（新）的转人工率与
  自结率有可复现的前后对比。
- trace 与日志中不出现候选订单号。
