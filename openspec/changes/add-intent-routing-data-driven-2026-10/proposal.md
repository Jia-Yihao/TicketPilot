# Proposal: 意图路由数据驱动化（阶段 B，F-9）

## 为什么

意图目录 `app/agent/intents.yaml` 头部写着「加一行即可，不改路由代码」（第 8–9 行），但这个承诺目前只对读意图成立。写意图的两行——`REFUND_REQUEST`（第 80–96 行）与 `TICKET_CREATE`（第 98–107 行）——**没有 `cues` 字段**，它们的判定写在 `app/agent/routing.py:298-314` 的顺序 `if-elif` 里，靠 `_REFUND_ACTION`（`:41`）、`_TICKET`（`:53`）两组 Python 常量匹配。

由此产生三个具体后果：

1. **加词必须改 Python**。任何新增说法（例如「那笔钱给我退回来」）都要发版，而写路径是风险最高的一段。
2. **两套词表并行且已不同步**。`routing.py` 的 `_POLICY`（`:55`）与 `intents.yaml` 的 `POLICY_QA` 各自维护一份，改一处不影响另一处；文件头部的承诺与实现不符。
3. **优先级顺序不可见**。哪一类先判由 `if-elif` 的位置决定，`intents.yaml` 的 `priority` 字段对写意图不生效；新增一行意图时无法从数据文件推断最终判定。

审计编号 F-9 记录这件事，当前状态「已裁定，待实施」。

## 目标

- **G1** `intents.yaml` 成为意图判定的唯一数据源，写意图两行具备与读意图同构的 `cues`，加一行意图不需要碰 `routing.py`。
- **G2** 判定结果**逐条不变**。346 条语料（`evals/intent/intent_set.json`）的判定输出与改造前完全一致，包括 `UNKNOWN` 的出现位置。
- **G3** 优先级与门槛写进契约。合成顺序（collaboration > 写路径 > 目录命中 > UNKNOWN）与写动作门槛（问句不算请求）不再只存在于代码的语句位置里。

## 不做什么

- 不改判定逻辑本身，**不提准确率**——本轮不追求「捞回更多」，只追求「可扩展且结果不变」。
- 不扩大模型采纳面（那是 F-1 / 阶段 A 的范围，见 `plan.md` 的边界说明）。
- 不新增意图行。用户已裁定「目录暂不扩张，先接稳已有行」。
- 不动 `confidence` 字段（F-3 独立决定）。
- 不做评测扩量。346 条语料的**等价性回归是验收门禁**，不是评测建设。

## 验收

| # | 判据 | 判定方式 |
|---|---|---|
| A1 | 346 条语料判定逐条一致 | 改造前后各跑 `evals/intent_metrics.py`，逐条 diff 为空 |
| A2 | 全量用例全绿 | `pytest -q -o addopts=`，收集数不减少，0 failed |
| A3 | 「加一行即生效」为真 | 在既有用例体内追加断言：临时注入一行假意图（含 cues），`catalog.match()` 立刻返回它，不改任何 `.py`；收集数保持 1035 |
| A4 | 写动作门槛未丢 | 问句（「什么时候可以转人工」）不产生 `REFUND_REQUEST` / `TICKET_CREATE`；既有的 `blocks_write_action` 用例全过 |
| A5 | 文档守卫不红 | 三条守卫 24 passed；说明书按需重生成 |

A1 是硬门禁。任何一处读数变化都必须解释清楚，不能以「新结果更好」为由放过——本轮不接受行为改进。

## 风险

| 风险 | 影响 | 处置 |
|---|---|---|
| 词表迁移后命中面变化 | 写路径误判，最坏是问句进入待审批队列 | 采用影子模式分步（见 `plan.md` 阶段 1），切换前必须先拿到逐条 diff |

| 改动跨 `routing.py` 与 `support_agent.py` | 两处都调用 `blocks_write_action`，漏一处即失去门槛 | `tasks.md` 把「门槛保留」列为独立任务与独立用例 |
