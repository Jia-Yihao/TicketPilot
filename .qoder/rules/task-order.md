# 任务排序与状态口径（项目级）

> 本文件只规定「按什么顺序做、什么状态才算完成、什么时候切提交」，不重复各任务的目标与验收。
> 任务清单与状态的真源是 `docs/下一步规划.md` §0.2 执行清单；本文件与它冲突时以 §0.2 为准，
> 并应先把冲突写进 §0.2 再动手。
> 本文件只声明口径，不改动任何产品代码、测试、迁移与既有文档。

---

## 1. 状态只能由证据给出

- **reviewer 未跑通、子 agent 失败或未给出结论的任务，不得标「完成 / 已收口」。**
  此时状态写「返工中（第 N 轮）」，并在条目内写明「未经独立复查」，不得用「已实地核验」
  「自测通过」替代。
- **执行者自跑 `pytest` 全绿只是准入条件，不是验收结论。** 它证明代码能跑，
  证明不了「改对了 reviewer 退回的那几条」；同一模型自查自己的改动尤其不算。
- 退回的严重项必须逐条落在条目内：哪几处、判据是什么、怎么复验。
  「三处已修复」这种无法复核的表述不算交付。
- 状态只写一次（`docs/下一步规划.md` §0.2），简报、交付说明与会话回复一律引用它，不另立状态。

## 2. 提交边界

- **每批任务验收通过后切一次提交**，不把多批改造压成一个不可回退的点。
- 提交前跑 `AGENTS.md`「提交前必须跑」的三条命令，提交信息写明本批任务编号。
- 工作树累计到几十个文件仍未提交时，先切提交再做下一批——没有提交边界时，
  任何 `passed` 读数都不属于任何单一任务，守卫红了也说不清是谁改坏的。

## 3. 文档事实数的级联

- 「收集 N 条用例 / N passed / N 个测试文件」由 `tests/test_docs_consistency.py` 的 manifest
  现算并比对，**文档写真实数字，不写约数、不省略**；改漏会红。这是有意的冗余，不要推翻。
- 但**历史读数链只保留一处**（`docs/spec/项目规格.md` §19.1），其余引用处写「当前读数见 §19.1」。
- 理由：数字有守卫兜（改漏会红），叙述没有守卫兜（改漏不会红），而一段历史读数链比数字长十倍；
  同一份文档里并列多个历史数（如 §19 的 1028 与 1074）会被读成自相矛盾。
- 新增用例时，受守卫管的当前数与不受管的历史数**不要写在同一个括号里**。
- **改了 `docs/spec/项目规格.md` 的事实数，必须同批跑 `python scripts/build_manual.py` 并提交 docx。**
  `test_manual_is_in_sync_with_the_specification` 与 `test_manual_build_record_matches_the_specification`
  直接比 docx 与 spec；spec 改了而 docx 没重生成，这两条会立刻红（2026-10-28 17:42 的实例：
  spec 已刷新到 1080，说明书还是旧读数）。

## 4. 三条排序原则（适用于任何波次）

- **同文件面只许串行**：两个任务都改同一文件（或同一测试基线）时不许并行；
  按「先复验已改过的、再测现状、最后才谈改造」排。
- **等量验收独占窗口**：验收标准是「改动前后某计数相同」的任务，窗口内不派任何新增用例或
  改基线的活。
- **全量基线只跑一次**：`README.md` 与 `docs/spec/项目规格.md` 的测试读数在每波收尾时统一
  re-cite 一次，不边做边改。
