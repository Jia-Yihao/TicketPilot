# ADR-035：退款原因与退款类型——分类由人显式给，服务端不兜底、模型不补位

- 状态：已接受
- 日期：2026-10-27
- 关联：ADR-003（服务端退款规则）、ADR-004（审批绑定订单版本）、ADR-005（台账与对账）、ADR-008（订单级退款并发防护）、ADR-009（意图目录为唯一事实源）、ADR-020（对话入口的模型边界）、ADR-024（三级模型门禁）、ADR-034（意图候选化）、ADR-036（审批金额分层——它把本 ADR 第 8 节的八键摘要修订为九键）、缺口 B-1、消费方 B-4

## 背景

本轮之前，退款写路径只知道三件事：哪个订单、退多少钱、按哪版政策。`refund_payload`
是六个键，`refunds` 表没有缘由列也没有类型列。于是：

1. **审批人批的是一笔钱，不是一件事**。同一订单、同一金额，「屏幕碎了」和「买多了」
   在摘要上逐字相同；批出去之后也无从追溯当初批的是哪种说法。
2. **B-4 想要的售后原因分布没有数据源**（`docs/下一步规划.md` 的 B-4 段），因为库里
   连这一列都不存在。
3. **全额、部分、运费、价保四种业务动作全都退化成「退一笔钱」**（B-1 段「为什么是问题」）。

两个最省事的补法都是错的：缺值时兜底成 `OTHER`，或者让模型顺手抽一个。本 ADR 记录的就是
把这两扇门关死之后剩下的八项裁定。

业务口径在 `app/agent/refund_reason_rules.yaml`（下称 **B-1 口径**）。必须说明身份：
其 §5.6 整节（采集口径）属**该口径的补充 + 用户裁决**，不是 `docs/下一步规划.md` B-1 段的
原文要求——那段关于采集只有一句「原因 / 类型由规则或客户显式选择提供，**模型不采纳**」
（`docs/下一步规划.md:2092`），没有规定规则表落在哪个文件、未命中怎么办、缺值时两个入口
各自怎么办。引用 §5.6 的任何一条时都不得写成原文要求（B-1 口径 §7 末尾自己强调了这一点）。

## 决策

### 1. 缺 `refund_reason` 即不放行——一处有意的收紧，来源是用户裁决

`docs/下一步规划.md:2102` 的原话是「不把原因做成必填的追问——客户说不清时允许 `OTHER`，
但审批详情要显示「未提供」」。本轮把「缺值就用兜底值放行」改成「缺值不放行」：对话入口
追问，任务 API 直接 422。B-1 口径 §5.6.2 与 §7 都把这一条登记为相对该原文的**有意的收紧**，
并写明裁决归属。

收紧的理由是数据污染，不是流程洁癖：自动兜底 `OTHER` 会把「系统没识别出来」和
「客户明说是其他」压成同一个值（B-1 口径 §5.6.2），而这两个值对 B-4 的分布统计意味着
完全相反的事——一个是缺数据，一个是有效数据。更糟的是 `OTHER` 一旦成为默认值，就会
随 `reason` 键进 `refund_payload` 与 `action_digest`（见第 8 节），审批人批下的是摘要已经
钉死的一枚兜底分类，他没有任何线索能发现它是兜底。

该条原文里的两条硬事实**照原样保留**（B-1 口径 §5.6.2 逐字点名「保留」）：

- `OTHER` 始终是一个合法可选出口，因此追问不会造成死锁；
- 值为 NULL 的历史记录在审批详情与回执显示中文标签「未提供」，**不映射成 `OTHER` 或 `FULL`**
  （B-1 口径 §2 表；代码上是 `app/services/refunds.py` 的 `NOT_PROVIDED_LABEL` 与
  `refund_reason_label` / `refund_type_label`——两个 label 函数都不做兜底映射）。

「追问」与「允许 `OTHER`」同时成立、不互斥，前提是追问话术**必须**把这个出口写进去：
`app/agent/intents.yaml` 的 `slots.refund_reason.prompt` 结尾是
「说不清或不方便分类的话，回答“其他”也可以继续。」（B-1 口径 §5.6.3 规定的形态）。
实现若在两端任一端失守都算违反本节：把追问做成没有出口的死锁，或者反过来「干脆默认
`OTHER`」。

判定只有一处，两个入口只是把同一个拒绝翻译成各自的表现：

- `app/services/runtime.py::resolve_refund_slots` 是共用的判定函数，缺值时返回
  `REFUND_REASON_MISSING` 并把 `error_message` 填成目录里那条 prompt；
- 对话侧：`runtime.py::_handle_refund` 在既有三道闸门（订单号 / 金额格式 / 金额缺失）
  之后按同形补的第四道闸门调 `_clarify`，本轮不建退款任务；
- 任务 API 侧：`app/api/v1/tasks.py::create_task` 调同一个判定函数，不合法即
  `ValidationAppError`（HTTP 422），不追问、不降级。

### 2. `OTHER` 不是规则表的兜底出口：`other_cues` 是另一张表，且优先于 `rules`

采集表落在新增的 `app/agent/refund_reason_rules.yaml` + loader
`app/agent/refund_reason_rules.py`，**不并入 `app/agent/intents.yaml`**（B-1 口径 §5.6.1
给了四条理由，其中可核对的一条是 `intent_catalog.py` 的 `_TOP_FIELDS` 是封闭集，并入就得
放宽那道守卫，等于把一个键名打错从「报错」降成「静默接受」）。

表里有两个互不相干的取值来源：

- `other_cues`：客户**显式**表达「其他 / 说不清 / 不想分类」的识别表，命中即
  `RefundReason.OTHER`；
- `rules`：关键词到具体分类的映射行，表序即优先级，首条命中即停。

裁定三条：

1. **`other_cues` 优先于 `rules`**。代码上是 `RefundReasonRules.match()` 先小写化入站文本、
   先扫 `other_cues`、命中就直接返回而**不再**看 `rules`。理由是方向问题：客户明说的
   「其他」是最强的分类信号，让一条顺带命中的关键词把客户的话改写成系统的猜测，正是
   §5.6.2 要防的污染，只是反着来一次。
2. **`OTHER` 作为 `rules` 的目标值是装载期错误**。`load_refund_reason_rules` 见到即报错，
   不是运行时忽略。因为 `OTHER` 的定义是一次**显式选择**，把它写成规则行就等于重新发明了
   兜底。
3. **两张表都空都算装载期错误**：`rules` 为空、某条 `cues` 为空、`other_cues` 为空或重复
   全部报错。一张永不命中的表会被静默读成「全部缺值」，而缺值在本链路是追问 / 422，
   症状看起来像「客户没说清」，实际是配置坏了（B-1 口径 §5.6.1 校验清单）。

**代价登记**：客户一句话里既说「其他」又给出具体线索时，记录为 `OTHER`，具体线索
**不保留**（坐席可另补 `reason_note`）。这是「显式优先」的直接代价，实现**不得**用
「两个都记」规避——`refund_payload` 的 `reason` 键只有一个值，两个都记要么改键形状、
要么悄悄造出第二套优先级。

已确认值不被本轮文本改写：上下文里已带合法 `refund_reason` 时沿用、**不重新匹配**
（`app/agent/routing.py::classify` 的形状是先读 `context.get("refund_reason")`，只有读不到
且规划意图是 `REFUND_REQUEST` 才调 `match_refund_reason(request)`）。沿用的适用域不是
无边界的，见第 7 节。

### 3. `refund_type`：输入可选、记录必填，派生锚在订单事实上

B-1 口径 §5.6.6 定死：`refund_type` 的**输入**可选，**记录**必填；缺值时既不拒绝、也不追问、
更**不默认成 `FULL`**。

- 显式值优先：坐席 / 调用方经 `context["refund_type"]` 提交时直接采用，不派生、不覆盖。
- 否则由服务端派生：`app/services/runtime.py::derive_refund_type`，
  `amount_cents == refundable_cents` → `FULL`，否则 → `PARTIAL`。纯函数——不读时钟、
  不用随机、不调模型、不查库，因此同一订单同一金额两次调用逐字相同。
- 派生发生在**运行时**：`_handle_refund` 里资格已通过、订单已加载、金额已确定之后。
  采集侧和调用侧都还不知道这个关系。
- 两个入口走同一条派生，不存在两套真相（测试
  `test_both_entries_derive_the_same_type`）。

**锚点是订单列 `orders.refundable_cents`，不是资格输出的 `max_refundable_cents`。**
今天这两个值相同（`app/services/refund_policy.py` 里 `max_refundable_cents` 取的就是
`order.refundable_cents`），但一个是一个事实，一个是判定结论——结论会随策略配置和订单状态
漂移。类型描述的是「这笔退款与订单可退余额的关系」，锚在结论上就会随配置漂移。

**这里有一处口径更正必须登记**：B-1 口径的较早版本把锚点写成「被 `refund_max_amount_cents`
封顶的 `max_refundable_cents`」，与代码现实不符（该列不受金额上限封顶影响），已按代码现实
更正，口径 §5.6.6 自己留了这条更正记录。本 ADR 记录的是裁定结果：**锚点是订单事实列**，
引用时以代码为准，不得回引那个早期表述。

**禁止默认 `FULL`**：一笔只退 50 分而可退余额是 10000 分的退款若被标成「全额退款」，
两类事实又压成同一个值，和第 1 节的兜底 `OTHER` 是同一种错误换个字段。

对话侧**不追问类型**：`refund_type` 不进 `REFUND_REQUEST.required_slots`，也**不得**问客户
「全额还是部分」——客户在自然语言里分不清「全额」与「可退余额正好全额」，追问会死锁，
而且 `OTHER` 那种出口对「全额 / 部分」并不成立（B-1 口径 §5.6.6 被否决备选 2）。类型对客户
不可见。

**代价登记（B-1 口径 §5.6.6 明确要求写进 ADR）**：`SHIPPING` 与 `PRICE_PROTECTION`
**只能**由坐席 / 调用方显式提交。客户自助发起、缺 `refund_type` 的退款一律落到 `FULL`
或 `PARTIAL`——也就是说**自助链路上产生不了运费退款与价保退款**。这是本裁定的已知代价，
实现**不得**用「猜一个 `SHIPPING`」之类的方式补齐；要打通它需要先有运费 / 价保的金额口径
（属 B-8，见 B-1 口径 §3）。

### 4. 模型不抽取、不采纳这两个值

落码形态：

- `app/agent/pydantic_agent.py::IntentOutput` 不新增 `refund_reason` / `refund_type`，
  提示词不新增任何抽取要求；
- 两处采纳位都不为这两个值开补位：决策复用分支与候选集采纳分支的形状都是
  `x = rule_plan.x or ...` / 「`is None` 时才取模型值」，两处**都不得**出现
  `rule_plan.refund_reason or ...` 这类补位；
- 取值通路只有两条——关键词规则命中，或客户 / 调用方显式提供。**不存在第三条（模型）通路**。

**为什么金额敢让模型补、原因不敢**（B-1 口径 §5.6.5 点名这段推理是本边界的来源，并禁止
后续反向套用）：

`amount_cents` 下游有**两道确定性闸**。第一道是资格校验，
`RefundPolicy.check` 的 `>0`、`<= refundable_cents`、`<= max_amount_cents` 三条，抽错的数字
当场被拦下来；第二道是人工审批——摘要覆盖金额，审批人盯的就是那个数。这两道闸都
不需要理解这句话是什么意思。

分类语义**没有任何确定性闸**。系统无法判定「客户这句话算质量问题还是破损」——这个判断
本身就是需要被做出的内容，不能同时充当检验它的依据。所以模型补位一旦被采纳，错值就
直接进 `refund_payload` 与 `action_digest`，审批人看到的是一枚摘要已经钉死的分类，
无从发现它是猜出来的。

一句话概括这道不对称：**金额的错会被拦住，原因的错会被批下来。**
这也是为什么它与 ADR-020 / ADR-024 / ADR-034 一脉相承：模型买的是这张待审退款单上的
订单号与金额，从来不是分类；候选化扩的是「模型能说出哪些意图行」的表达面，
不是原因值的采集面。想扩采集面需要单独的口径与验收，不能借候选化已经落地的势。

`refund_type` 同理不由关键词推断，且多一条理由：它是业务动作维度的分类，
客户自然语言几乎不区分「全额」与「部分」，误判同样没有闸能发现。

### 5. 链路命名统一用 `refund_reason`，裸名 `reason` 只出现在三处

裸名 `reason` 在本仓库已被多个不同概念占用：审批决定 / 驳回 / 失效的原因
（`approvals.reason`、`ApprovalService.decide(reason=...)`）、转人工原因
（`handoff_events.reason` / `HandoffReason`）、放弃原因（`abandon_events.reason`）、
资格诊断码（`EligibilityResult.reasons`）、执行结果原因码（`request_refund` 结果的
`reason_code`）。

裁定（B-1 口径 §1.0）：承载「退款原因」的**裸名 `reason`** 只能出现在三个合法位置——
`refunds.reason` 列、`refund_payload` 的 `"reason"` 键、`RefundReason` 类型名。链路其余各处
一律带上下文：`task.context["refund_reason"]`、`RoutePlan.refund_reason`、
`ConversationSlots.refund_reason`、YAML 顶层 `slot: refund_reason` 与规则项键
`refund_reason:`、ToolSpec 入参键 `refund_reason`、形参 `refund_reason: RefundReason`。

**映射点唯一**：只在构造载荷与落库处映射成口径裸名。代码上就是
`refund_payload` 返回字典里的 `"reason": refund_reason.value` 这一处（加上 ORM 列名）。
本节不另立第二套映射规则。

可判定的违规形态有两种，都要求在 diff 里显式可见：把 `RefundReason` 的值域赋给三处之外
的任何 `reason` 标识符（例如把退款原因传给 `decide()` 的 `reason` 参数）；或者在三处之外
新建一个裸名 `reason` 且取值来自 `RefundReason`。`task.context` 里放一个键名叫 `reason`
正属后一种，所以不允许。

`refund_type` 各处同名（形参名与载荷键名相同）属正常，不在「裸名 `reason` 重载」这个
有问题的名字上，**不得**因此改名或给它加前缀。

### 6. `reason_note` 只与 `OTHER` 同时合法，校验只写一处，绝不静默忽略

`reason_note` 是 `reason=OTHER` 时坐席可填的一段自由文本（B-1 口径 §1 术语表）。裁定：

- **非 `OTHER` 却提交了 note ⇒ 拒绝创建**：任务 API 返回 422，对话入口不建退款任务
  （按缺槽位同款形态）。
- **校验只写一处**：判定就落在共用判定函数 `resolve_refund_slots` 里那一句
  （`context.get("reason_note") is not None and refund_reason is not RefundReason.OTHER`
  → `REASON_NOTE_NOT_ALLOWED`），两个入口只是把同一个拒绝翻译成各自的表现。
  **不得**为某个入口单写一份——那会把一条规则写成两套真相。
- **不得静默忽略**：静默忽略会让坐席以为说明已留存，而审批侧实际看不到，属数据一致性风险
  （B-1 口径 §2 登记的理由）。也**不得**「先把 note 存下、等 `reason` 定了再决定」。
- **不进摘要、不进公开回执**：`refund_payload` 的键集合里没有它。理由是自由文本逐次措辞
  不稳定，纳入会造成审批快照漂移（B-1 口径 §4.2；`docs/下一步规划.md:2101` 也点了
  「不进公开回执」）。执行侧要落库时才读它：`app/services/refunds.py::_reason_note`
  只在原因确为 `OTHER` 时从任务上下文取值、去空白、空串归一为 `None`。
- 对话侧不采集它：它是坐席侧文本，不是客户槽位，因此不进 `required_slots`、不在 `slots` 声明里。

### 7. 携带原因的生命周期：三段裁定按时序，最后一段是补全不是推翻

「上一轮已经答过的原因，这一轮别再问第二遍」是本链路必须有的携带机制，但它的存活域
被改判过两次。三段都成立，第三段补第一段的洞，不推翻它。

**裁决 1（2026-10-26）**：规则匹配与写回只发生在规划意图为 `REFUND_REQUEST` 的回合；
退款任务**成功建单的回合即清除**会话槽位里的 `refund_reason`，下一笔退款重新采集、
重新追问。依据是原因的定义本身——「**发起退款时**」客户对缘由的分类选择（B-1 口径 §1 术语表），
跨流程沿用等于替客户决定了第二笔退款的原因。

**R1b（同轮）**：同一笔退款流程内不重复追问——已确认的原因在后续回合沿用、不重新匹配。
这是「携带」这件事存在的唯一理由，也是后面第 5 条被否决备选 (F) 的判据来源。

**补裁 B′（2026-10-27，独立审查轮 `rev-bprime-r4` 判定通过）**：把沿用适用域钉成一条
可机械判定的不变量。

- **保留条件**：`ConversationSlots.refund_reason` 仅在「本回合规划 / 恢复到
  `REFUND_REQUEST`」**或**「**本回合写回的** `pending_intent` 是 `REFUND_REQUEST`」时保留；
  两者皆不成立时，随**同一次 `ConversationSlots` 构造**清为 `None`。
- **第二个条件的取值来源是这条裁定的要害**：它读的是同一次构造里由
  `draft.clarification["resumable_intent"]` 算出的那个**写回值**
  （`app/agent/support_agent.py` 的 `pending_intent_value`，`:607` 算出、`:647` 写回），
  **不是**上一回合存量的 `carried.pending_intent`。

**必须登记这个订正本身**：口径早先写的是「同一笔退款流程内」——那是一句无法机械判定的话，
被 `rev-b1-r3` 的 K7 判为**声明缺位**（放弃路径根本不建单，所以现文没有任何规则禁止陈旧值
跨流程存活）。中间一版把第二个条件读成「上一回合留下的 `pending_intent`」。按那个读法，
转话题那一回合的**进入值**恰好就是上一回合留下的 `REFUND_REQUEST`，于是该回合判定「流程
仍开着」、原因原样保留，下一笔退款照旧被陈旧值喂饱——**这条不变量在它自己的修复下失效**。
该读法已作为被否决备选 **(G)** 登记在 B-1 口径 §5.6.1.1。

**缺陷事实（三回合序列，2026-10-27 在同一 `conversation_id` 上以 HTTP 实测；
现由 `tests/test_refund_taxonomy.py::test_a_topic_change_turn_clears_the_carried_reason_for_the_next_refund`
在仓库内复现同一形状）**：

1. turn1「包裹破损了，我要申请退款，订单 ORD-DEMO-1001」→ 缺金额追问
   （`clarification.reason=MISSING_AMOUNT`、`resumable_intent=REFUND_REQUEST`），
   槽位 `refund_reason=DAMAGED`、`pending_intent=REFUND_REQUEST`；
2. turn2「订单 ORD-DEMO-1001 到哪里了」→ `LOGISTICS_QUERY`，无追问、无建单：
   `pending_intent` 因为本轮没有 `draft.clarification` 被写成 `None`，而 `refund_reason`
   因为 `draft.task` 是 `None` 被**保留**——「流程标记已经消失、原因却还在」；
3. turn3「我要申请退款，订单 ORD-DEMO-1002，金额 50 元」（这句话里没有任何原因词）→
   陈旧值在 `classify()` **之前**被注入上下文，于是**没有被追问原因**，第二笔退款直接
   `WAITING_APPROVAL` 建单。这就是污染本体。

按 B′ 的读法，turn2 因它没有 `draft.clarification` 而**同时**清掉原因与流程标记，turn3
重新被追问。

**单一落点纪律**：整条不变量只落在 `app/agent/support_agent.py:620` 那一次回合**写回**构造
（`app/` 下直接构造 `ConversationSlots(` 里只有它带 `refund_reason=`，实参在 `:634`）。
明确不构成第二落点的三处：`app/services/conversations.py:115` 是新会话的默认构造、没有
沿用值可清；`ConversationSlots.from_dict`（同文件 `:59`，其 `refund_reason=` 实参在 `:67`）
是从存量 JSON **复原**的读取路径，不是本回合的写回落点；`tests/test_refund_taxonomy.py:806`
直接带 `refund_reason=` 构造槽位，属测试形状断言。本轮**不新增**事件、配置项、迁移、
转人工分支，也不新增第二处写回。

**代价登记**：客户在退款流程中途插问一句别的（被读成非退款意图）会被清掉原因、下一句
重新追问。这是**安全方向**的代价——宁可重问一次，也不替客户决定第二笔退款的原因。

**连带的一处用例订正**（不改实现）：既有用例 `test_a_carried_reason_is_not_rematched_by_the_next_message`
的 turn2 原文「包裹破损了」会被 `intents.yaml` 里 `DELIVERY_ISSUE` 的 `破损` cue 读成非退款回合，
按订正后的不变量必须清原因，与它想钉的沿用行为冲突。裁定是**改用例**：turn2 换成
「包裹破损了，我要申请退款」，并加一条 `pending_intent == "REFUND_REQUEST"` 的断言把
「本回合退款流程仍开着」钉住，原先 `refund_reason == "QUALITY"` 的断言逐字保留。

**对 B-4 的影响登记**（B-1 口径 §5.6.1.1 要求「其对 B-4 原因分布的影响写进 ADR」，此处即落点）：
同一回合内客户改口**不会**被新说法覆盖（沿用优先，见第 2 节末尾）。因此这一回合在原因分布里
恒记**第一次确认**的那个值。读看板的人必须知道这条口径：分布统计的是「客户第一次说出口的
分类」，不是「客户最后改口的分类」。本轮不改变这个取舍。

### 8. 摘要覆盖八键：增删任一键即改摘要，而加键不伤在途审批——故禁止改写存量载荷

`action_digest = canonical_digest(refund_payload)`：对载荷做规范化 JSON（键按字典序）后取
SHA-256 十六进制串（`app/services/approvals.py::canonical_digest`）。由此得到两条机械性质：
键的**书写顺序无关**（序列化前已排序），但**增删任一键都会改变摘要**——新旧审批因此互不可
替换，摘要漂移即失效。

**本 ADR 把摘要键从六项改为八项**；其后被 [ADR-036](ADR-036-审批金额分层.md)
第 6 节修订为九项。两处口径不是打架，是修订关系：引用时写「本 ADR 定八键、ADR-036 修订为
九键」。八键清单（B-1 口径 §4.1）：

| 键 | 现状 | 说明 |
|---|---|---|
| `action` | 已有，常量 `"REFUND"` | 动作类型。 |
| `order_id` | 已有 | 目标订单，租户边界内。 |
| `amount_cents` | 已有 | 实退金额（可退余额口径，B-1 口径 §3）。 |
| `currency` | 已有 | 币种。 |
| `resource_version` | 已有 | 订单乐观锁版本，绑定执行时资源状态。 |
| `policy_version` | 已有 | 政策版本，跨版本审批不可混用。 |
| `reason` | **本 ADR 新增** | 退款原因枚举值；加入摘要以让「批准的就是这件事」。 |
| `refund_type` | **本 ADR 新增** | 退款类型枚举值。 |

第九键 `approval_tier` 是**整个档位快照**（`tier_id` / `max_cents` / `roles` /
`required_approvals`），不是只放 `tier_id` 一个字符串；为什么必须整份进摘要、键名为何不叫
裸 `tier`，裁决与理由都在 ADR-036 第 6 节，本节不重复印证。落码上
`refund_payload` 返回的字典就是这九键（`app/services/approvals.py::refund_payload`，
其 docstring 已写明「键集合定死为九键」）。

**不进摘要的字段与理由**（B-1 口径 §4.2）：

- `reason_note`：坐席侧自由文本，逐次措辞不稳定，纳入会造成审批快照漂移；且不进公开回执
  （第 6 节）。
- 执行态列 `status` / `provider` / `external_refund_id` / `idempotency_key` /
  `created_at` / `updated_at`：都在审批**之后**才产生或变化，不属于「审批人批准的内容」
  快照。
- `product_id`：本轮不引入（属 B-2 / P3）。
- 资格诊断输出 `max_refundable_cents` 与 `requires_approval`：是判定输出而非审批内容；
  进摘要的是**档位快照**，不是「要不要人批」这个布尔量（B-3 口径 §5.2 明确保留这一条）。

**在途审批安全**：`verify_binding` 是对**已存储的** `action_payload` 重算摘要、再与该行
存量的 `action_digest` 比对（`app/services/approvals.py::verify_binding`）。因此加新键
**不会**使存量 PENDING / APPROVED 审批失效——旧载荷不含新键，其存量摘要也据旧载荷计算，
重算仍逐字相符。反向推论必须一起读：**禁止**对存量 `action_payload` 做回填或改写。
任何改写都会让载荷与自己当初生成的 `action_digest` 脱节，绑定校验随即失真——被摘要覆盖的
存储 JSON 必须与生成摘要时逐字一致（B-1 口径 §2「action_payload 存储」）。

一句取舍：摘要对分类敏感之后，审批人批的是**一件事**（订单 + 金额 + 原因 + 类型的组合），
不再是「一笔钱」；代价是同一订单、同一金额、不同原因的退款从此不可互相替换。

## 后果

- 摘要对分类敏感：同一订单两条不同 `reason`（或不同 `refund_type`）的退款产生不同摘要，
  在台账上可区分——这是 `docs/下一步规划.md:2096` 验收第 1 条要求的形状。
- 缺原因的退款不再静默建单：对话多一轮追问（话术自带 `OTHER` 出口），任务 API 多一个 422。
- 历史记录读出来是「未提供」，不会被贴上一个看起来合法的假分类。
- 自助链路产生不了运费退款与价保退款（第 3 节的代价）。
- 转话题会清掉已答的原因，客户下一句要重答一次（第 7 节的代价）。
- B-4 第一次有了可用的原因 / 类型分布数据源，但必须连同上面两条口径一起读。

代价与边界：

- 「缺即不放行」相对 `docs/下一步规划.md:2102` 是**有意的收紧**，裁决归属用户，
  不是原文要求；引用时必须带着这个身份。
- 显式「其他」优先于具体线索，代价是具体线索不保留。
- `refund_type` 的派生只覆盖 `FULL` / `PARTIAL` 两个值；`SHIPPING` / `PRICE_PROTECTION`
  是标签，本轮**禁止**为它们引入任何独立金额项、拆分、分摊或「应退 / 实退」多口径
  （B-1 口径 §3，属 B-8）。
- 同一回合内改口不覆盖，分布恒记第一次确认值（第 7 节）。
- 采集口径整体属 B-1 口径 §5.6 的**补充 + 用户裁决**，`docs/下一步规划.md` B-1 段未规定。
- 本轮不覆盖退货流程（`WAITING_RETURN` / `returns` 表属 B-2）、不引入 `product_id`、
  不做退款原因选择器 UI、不改 `RefundPolicy.check` 的金额取值。
- `docs/guide/接口说明.md` 的字段说明与 `intents.yaml` 版本号 bump 属后续同步（B-1 口径 §5.6.7 只登记）。

## 被否决的方案

生命周期不变量的五条（编号沿用 B-1 口径 §5.6.1.1 的清单，字母不连续，无 B/E；该编号沿革
在无提交锚点的脏工作树下**无法独立复核**，此句属**自述**，可核的是这五条正文逐字可见）：

- **(A) 只在转人工时清除**：漏掉不转人工的转话题，而那正是本缺陷的主形态。
- **(C) 读 abandon events**：既撞既有边界——`app/agent/support_agent.py:232-233` 的
  `handle()` docstring 明写 handoff bundle 与 abandon events 是「never a decision branch」，
  该句不在 `_detect_abandon` 自身的 docstring（`:1235`）里，但 `_detect_abandon` 正是在
  `handle()` 内被调用（调用点 `:480`），所以撞的正是这条边界；又只覆盖闲置超时，
  覆盖不了转话题。
- **(D) 新增一个 abandon action**：引入新机制，超出 B-1 本轮边界（与单一落点纪律直接冲突）。
- **(F) 只在 `_resume_pending` 返回 `resumed` 为真的回合沿用**：会把 R1b 的初衷当场废掉——
  客户重述退款、`plan.intent` 已经是 `REFUND_REQUEST` 时 `_resume_pending` 返回假，
  于是同一流程内照样要重新追问。
- **(G) 存活条件读上一回合留下的 `pending_intent`（即 `carried.pending_intent`）**：
  它恰好在泄漏形态里为真（转话题回合的进入值就是上一回合留下的 `REFUND_REQUEST`），
  按它写等于不变量不生效；可核对的证据就是同一串三回合里 turn2 保留、turn3 不被追问。

本链路其他被否决的形态：

- **缺 `refund_reason` 时兜底成 `OTHER`**：把「系统没识别出来」与「客户明说是其他」压成
  同一个值，且兜底值会随摘要被审批钉死（第 1 节）。
- **缺 `refund_type` 时默认 `FULL`**：同一个错误换个字段——一笔部分退款被标成「全额退款」。
- **给 `refund_type` 也建一张关键词规则表**：客户几乎不区分「全额」与「部分」，命中极不可靠，
  而 `SHIPPING` / `PRICE_PROTECTION` 根本不是客户的语言。
- **追问客户「全额还是部分」**：`OTHER` 那种出口对「全额 / 部分」不成立，说不清 → 澄清 →
  再问会死锁，自助退款永远走不通。
- **把对话侧发起的退款全部转人工**：自助退款是主线能力，而派生规则已能在不牺牲可退余额
  口径的前提下给出确定类型。
- **让模型抽取原因 / 类型并在补位位采纳**：分类语义没有确定性闸，错值会直接被批下来（第 4 节）。
- **把规则表并入 `intents.yaml`**：必须同时放宽 `intent_catalog.py` 的 `_TOP_FIELDS` 守卫，
  把键名打错从报错降成静默接受，且让「意图目录」同时承载两类事实。
- **在 `rules` 里加一行 `OTHER` 作兜底**：`OTHER` 是显式选择，写成规则行就是重新发明兜底
  （loader 装载期报错）。
- **客户同时说「其他」和具体线索时两个都记**：`reason` 键只有一个值，两个都记要么改键形状、
  要么悄悄造出第二套优先级。
- **非 `OTHER` 带 `reason_note` 时静默忽略**：坐席以为说明已留存、审批侧实际看不到（第 6 节）。
- **为某个入口单写一份校验或派生**：一条规则写成两套真相。
- **回填或改写存量 `approvals.action_payload`**：任何改写都会破坏 `verify_binding`（第 8 节）。
