# ADR-033：澄清候选降级——把「再说一遍单号」换成「这是你的订单」

- 状态：已接受
- 日期：2026-10-26
- 关联：ADR-004（转人工信号表）、ADR-016（渐进式披露）、ADR-024（三级模型门禁）、P11

## 背景

客户说「帮我查一下订单」而没给单号时，Agent 的回答是把同一句话再说一遍：
「请提供订单号」。客户想不起来第二次，得到的还是同一句话——第三次直接转人工。
这在信号表里叫 `repeated_clarification`，它的阈值当时**借用**了
`frustration_rounds`（=2）。

两个问题叠在一起：

1. **追问是无效的**：缺的不是「再问一次」，是「客户看不见自己的订单号」。项目已经
   有按身份预取的能力（ADR-016 的 L1/L2/L3、P3-b 的预取），却没有用在澄清这一步。
2. **阈值是共用的**：`repeated_clarification` 和「客户明显烦躁」用同一个数字。
   即便加上候选卡片，第二次澄清也会先被判成转人工，卡片永远渲染不出来——
   新流程被旧阈值挡在门外。

## 决策

### 1. 澄清预算成为独立阈值

`ESCALATION_CLARIFICATION_ROUNDS=3`（`clarification_rounds`），与
`frustration_rounds`（仍为 2）彻底分开：

| 信号 | counter | threshold |
|---|---|---|
| `frustration` | `frustration_rounds` | 2 |
| `repeated_clarification` | `clarification_rounds` | 3 |

`EscalationState.clarification_count` 在 `count_outcome()` 里被**夹在预算上**：
转人工后 Agent 静默期间计数不再增长，不会因为客户继续说话而无限上升。
调回 `ESCALATION_CLARIFICATION_ROUNDS=2` 即逐字回到旧行为，不需要改代码。

### 2. 第二次追问改为候选降级，只用模板

`order_id` 槽位第二次仍缺失时，不再重复原话，而是列出**这个人自己**最近的订单
（最多 3 条），每条只给四个 L1 事实：订单号、商品名、状态、签收时间。没有金额、
没有可退余额、没有物流明细——候选只需要「被认出来」，展开是另一次受作用域约束的读。

- 读路径 `CommerceRepository.list_recent_orders(tenant_id, user_id, limit)`：
  租户与用户**同时**进谓词，谁都不放宽；`paid_at DESC, id DESC` 排序，
  同一秒付款的两条订单也有唯一顺序。
- `sections` 恒为空、`total_chars` 恒为 0：澄清路径不触发任何 L2/L3 预取。
- 卡片 `kind=order_candidate`，订单号同时进入 `suggestions`，点一下即发送。
- 不调用模型、不读时钟、不猜单号；`AGENT_MODE=rules` 仍是一次都不问模型。

### 3. 隐私边界写在轨迹上

移交包（坐席可见）是唯一多带一份候选的载体。`support.reply` span 只记录
`clarify_candidates` 这个**数量**，不记录任何订单号；订单号不进 trace、日志与其他通道。

### 4. 第三次仍失败才转人工，且带上已尝试候选

`attempted_candidates` 从 `draft.cards` 回读——坐席被告知的是客户**真正看到过**的
那几条，不是重新查一遍可能已经变动的列表。没有候选时该字段是空列表而不是缺失。

## 后果

- 缺单号的对话多了一轮自助机会；配合的客户不再因为「想不起一串编号」被转走。
- 阈值可独立调整，烦躁与困惑不再是同一个计数。
- 每个数字都在服务端算好、按身份预取，模型只做表达——延续 ADR-024 的门禁取向。

代价与边界：

- 候选只在 `order_id` 槽位触发。金额、商品这类槽位仍是一句普通追问：把它们也做成
  候选需要先定义「候选来自哪里」，本轮不猜。
- 上限 3 条是产品判断，不是分页控件。订单很多的人看到的仍只是最近三条，
  真要翻列表属于会话外的能力。
- 个性化（ADR-018 的简洁偏好）可能把 `suggestions` 里的候选削减到 2 条，
  卡片本身不削；这符合「不超过 3 条」的契约，但意味着chip 数量不恒等于卡片数量。
- 本 ADR 的前后对比来自**脚本化剧本**（`evals/clarification_scenarios.json`），
  不是生产遥测；它证明阈值改动的后果，不证明真实流量分布。

## 被否决的方案

- **继续借用 `frustration_rounds`**：候选卡片会被第二次澄清的转人工覆盖，等于没做。
- **让模型生成候选文案**：违反「确定性代码做判断、模型只做表达」，且 `rules` 模式退化。
- **在澄清轮预取完整订单卡（L2/L3）**：客户还没表明是哪一单，就把金额与物流摊开了。
- **轨迹里记候选订单号便于排障**：trace 是可回放、可导出的一等产物，不该成为泄漏面。
- **移交时重新查询候选**：坐席看到的列表可能与客户当时看到的不一致。
- **把上限提到 5 或做成翻页**：澄清是帮客户「认出来」，不是替代订单列表页。

- `tests/test_support_candidates.py` 12 条：租户/用户双重作用域与并列排序、
  L1 字段恰好四个、商品名取自目录、跨用户与跨租户不泄漏、无订单时不编造、
  缺字段不崩、点选候选续跑原意图、轨迹只记数量不记单号。
- `tests/test_policy_engine.py` +1 条、`tests/test_handoff.py` +3 条并改写信号 7：
  阈值独立解析、命名阈值全部可解析、`repeated_clarification` 走 3 而非 2、
  第三次转人工且计数停在预算、移交包含已展示候选、无候选时字段为空列表。
- `tests/test_clarification_evidence.py` 11 条 + `evals/clarification_candidates.py`：
  同一批剧本在旧阈值(2) / 新阈值(3) 下重放，见 `docs/guide/证据索引.md`。
