# ADR-038：分数种类与分尺度阈值——一个数配一把尺，空检索分三种

- 状态：已接受
- 日期：2026-10-28
- 关联：ADR-011（转人工是一等公民——`no_evidence` 是它的 P1 信号之一）、ADR-021（稠密通道按 BM25 的盲区触发，而不是按分数开关——本次把「另一个尺度的分」变成可判定的种类）、ADR-025（架构依赖守卫——`core` 是第 0 层，`retrieval` 是第 2 层，这是 `EVIDENCE_KINDS` 只能写字面量的原因）、ADR-027（分层检索评测集）、ADR-029（统计问答两条路径——`verdict` 这一种的来源）、`docs/guide/评测说明.md`（本次的口径文件）

## 背景

三件互相关的事，本质是同一个错误的三张脸：**把不同尺度的数当成同一个数。**

**其一：`score` 里躺着哪个通道的分，只有写它的人知道。** 混合检索把稀疏通道的原始分、
稠密通道的余弦分、融合分、重排分都写进同一个 `RetrievedChunk.score` 字段，字段本身不带
任何种类信息。下游只能猜，而猜错不会有报错——它只会让排序看起来正常、判定悄悄错掉。

**其二：0.35 这根线在四个尺度上各错一处。** 转人工的 `no_evidence` 信号原本只有一个阈值
`escalation_no_evidence_score default 0.35`（`app/services/escalation.py` 的 `_below_evidence`，
阈值键在 `app/agent/escalation.yaml` 的 `no_evidence` 行上）。这个数放在不同尺度上意味着
完全不同的东西：

| 尺度 | 典型量级 | 0.35 意味着 |
|---|---|---|
| 稀疏（BM25） | 十几分 | 「只要有结果就永不触发无依据」——线低到失效 |
| 稠密（余弦） | 0…1 | 勉强合理，但与 BM25 无关 |
| 融合（RRF，`rrf_k=60`） | 单通道榜首约 1/61 ≈ 0.0164 | 线高到**每轮都触发**，等于把转人工变成默认行为 |
| 重排（`relevance_score`） | 0…1 | 与稠密同一个量级，但与 BM25 无关 |

一个数字要同时服务四种量级，只可能在其中三种上错。更糟的是它的错法是**静默**的：
阈值错了不抛异常，只是该转人工的没转、不该转的转了。

**其三：「库里没有」和「这次没检索到」被合并成一句话。** 检索为空时对外一律说
「未检索到相关内容」。对客服来说这两件事的含义相反：前者说明这个租户根本没有这条政策，
说什么都没用，应该结束对话；后者说明条款在库里、只是这个问法没匹配上，应该请客户换个
说法或转人工。合并它们等于把两种完全不同的处置递给下游。

## 决策

### 1. 分数带种类：`score_kind` 是必填字段，词表封闭且只有一处定义

`app/retrieval/search.py` 定义 `SCORE_KINDS = ("sparse", "dense", "fusion", "rerank")`，
`RetrievedChunk` 与 `ScoredChunk` 都带 `score_kind`，默认 `"sparse"`（既有调用点尚未标明
尺度时，它的分确实来自 BM25）。

`app/core/policy.py` 另有一张 `EVIDENCE_KINDS = ("sparse", "dense", "fusion", "rerank", "verdict")`。
它看起来像是 `SCORE_KINDS` 的副本，**但它不是重复声明，而是被分层守卫逼出来的两件事**：
`core` 是第 0 层、`retrieval` 是第 2 层，第 0 层不许 import 第 2 层（ADR-025）。所以 `core`
里的那张表只能是字面量，而两张表不能各说各话——有一条测试同时钉住两张表的内容与包含关系，
表一旦漂移就红。

第五种 `verdict` 不在 `SCORE_KINDS` 里，因为它不是检索分数，而是动作层自己的判断
（0 或 1）。它必须存在：`app/agent/actions.py` 有六处 `SELF_ANALYTICS` 分支写
`EvidenceScore(1.0 / 0.0, "verdict")`。若 `verdict` 不是合法种类，每一次统计问答都会因为
「找不到这个种类」被当成无依据而转人工——把一条本来正确的路径整批打掉。

### 2. 分尺度阈值：四种可配、「verdict」硬编码且故意没有配置项

`EscalationThresholds.no_evidence_threshold(kind)`（`app/core/policy.py`）是唯一的查表入口：

| `score_kind` | 配置项（env） | 默认 | 这一把尺长什么样 |
|---|---|---|---|
| `sparse` | `escalation_no_evidence_score`（`ESCALATION_NO_EVIDENCE_SCORE`） | **5.0** | BM25，十几分是强命中 |
| `dense` | `escalation_no_evidence_score_dense`（`..._DENSE`） | 0.35 | 余弦，0…1 |
| `fusion` | `escalation_no_evidence_score_fusion`（`..._FUSION`） | 0.0164 | RRF，单通道榜首约 1/61 |
| `rerank` | `escalation_no_evidence_score_rerank`（`..._RERANK`） | 0.35 | 重排 `relevance_score`，0…1 |
| `verdict` | **无**——硬编码 `_VERDICT_NO_EVIDENCE_THRESHOLD = 0.5` | 0.5 | 动作层自己的 0/1 判断 |

`verdict` 不给旋钮是有意的：它的取值域是 `{0.0, 1.0}`，0.5 是唯一能区分两者的中点。
把它做成环境变量只会让人把它调成 0.6 或 0.4 然后以为行为变了——其实两种取值下判定完全相同，
或者直接把判定改坏。`0.0 < 0.5 <= 1.0` 与旧口径 `0.0 < 0.35 <= 1.0` 判出的结果是同一个。

**未知种类一律 `KeyError`，不回落稀疏线。** `no_evidence_threshold()` 遇到不在表里的
`kind` 直接 `raise KeyError(f"Unknown evidence score kind: {kind}.")`；`_below_evidence`
先用 `threshold(family)` 校验信号表里写的阈值族名（`no_evidence_score`），名字不对同样
`KeyError`。这两处都不设默认值：回落等于把一个新尺度的分拿去比旧尺度的线，而这正是本次
要消灭的错法，静默回落会让它换个入口复活。

### 3. 混合检索回写自己产出的分，让分数与名次同源

`app/retrieval/hybrid.py::_scored_order` 一条规则：**顺序从哪儿来，分就从哪儿来。**

- **没有重排结果**：整张表都带各自的 RRF 融合分，种类 `fusion`，**排序与改动前逐位相同**。
- **有重排结果**：头部按重排分**降序**排（同分保持端点给的顺序），种类 `rerank`；尾部
  （端点没有回答的候选）保留融合分并夹紧到 `min(该块融合分, 本次最小重排分)`，也标
  `rerank`，于是整张表仍在同一把尺上且保持有序。
- **重排失败或没有意见**：fail open 回融合分（`retrieval_rerank_enabled` 出厂默认 `False`，
  `app/core/config.py:76`）；端点是可选项，它的故障不该让检索整条失效。
- **只有一路有结果时也标 `fusion`**：RRF 在单通道上同样会算出一个融合分，标 `sparse`
  会让下游拿 BM25 的线去比 RRF 的数。

`citation()` 的键集不变——`score_kind` 不进引用。客户看到的引用里不需要知道数是怎么算的，
需要知道尺度的只有判定侧与轨迹。

### 4. 空检索三分：`EMPTY_REASONS` 把「库里没有」和「这次没检索到」分开

`app/retrieval/search.py` 定义 `EMPTY_REASONS = ("empty_query", "no_visible_chunks", "no_match")`
与纯函数 `classify_empty(query, visible)`，判定顺序固定：

| 顺序 | 条件 | `empty_reason` | 含义 |
|---|---|---|---|
| 1 | `query.strip()` 为空 | `empty_query` | 没有可检索的东西 |
| 2 | 该身份可见的切块数为 0 | `no_visible_chunks` | 库里根本没有这个租户能读的条款 |
| 3 | 其余 | `no_match` | 条款在库里，这个问法没匹配上 |

`SupportContextService.policy_evidence()` 把结果包成 `PolicyEvidence(cards, best, empty_reason)`：
`best` 是**全局最高分**的那一条（带它的 `kind`），`empty_reason` 只在零命中时非 `None`。

两个实现细节是刻意的：

- **空白问句不查库、也不数可见切块**：`query.strip()` 为假时 `visible` 直接留 0，因为
  「有没有东西可读」在这种问句上没有意义，数一次只会在轨迹里留下一个与本次检索无关的数。
- **可见切块数只从 `PolicySearchService(self.session).visible_chunks(identity)` 取**，不走上
  被注入的 searcher：注入的那个可能是改写器或混合通道，它们回答不了「这个租户到底能读到什么」
  这个问题。代价是零命中时多一次计数查询——这是可接受的，因为零命中本来就是少数路径。

## 后果

正面：

1. 分数与名次同尺度，下游读 `score` 时不必也不该再猜通道；判定侧的线跟着种类走，四把尺
   各配一个默认值。
2. 未知种类变成 `KeyError` 而不是静默默认值——新增一个尺度却忘了配线，测试会红，或者运行
   时直接报错，不会悄悄用别人的线。
3. 「库里没有」与「这次没检索到」在轨迹与动作层草稿里可区分，处置方向不再混。
4. `verdict` 让统计问答不再被「无依据」信号误伤——这是第五种必须存在的原因。

代价与风险（逐条登记，三条中前两条是可观察的行为变化）：

1. **`escalation_no_evidence_score` 的默认值从 0.35 改成 5.0，这是可观察的读数变化。**
   稀疏通道的分一旦落在 `[0.35, 5.0)` 区间，改动前答得出、改动后转人工。本机 seed 数据上
   的量级（**这是本机 seed 数据量级，不是评测读数**）：「保修政策是什么」榜首稀疏分 4.2593
   ——改动前作答、改动后转人工；「退款条件是什么？」14.45、「售后政策明细有哪些」5.162、
   「退货运费谁承担」9.6082 仍在线上作答。也就是说这条改动**确实会让一部分问句从「作答」
   变成「转人工」**，这是它有意的方向（那一档的分本来就弱到不该拿来答复客户），但它必须被
   当成读数变化登记，而不是当成「只是改了个配置」。
2. **头部按重排分降序排，是名次变化。** 端点返回的顺序不保证跟它自己的分一致，所以按分数
   重排（同分保持端点顺序）。这条只在 `RETRIEVAL_RERANK_ENABLED=true` 时可见；出厂默认
   `False`，因此默认配置下的输出与改动前逐位相同。
3. **`verdict` 这一种同时覆盖两类东西**：检索分数（0…1 的相关性）与动作层的判断（0 或 1
   的结论）。两者共用一把尺能成立，纯粹因为他们都落在 `[0, 1]` 且 0.5 能分开——不是因为他们
   语义相同。谁将来往 `verdict` 里塞第三种含义，这条就失效。

## 被否决的方案

**把 `no_evidence` 的 `reply_mode` 从 `replace` 改成 `append`，让客户真的看到两句不同的话。**
否决。理由不是文案不好，而是**代价落在别处**：同一个 `no_evidence` 信号同时挂着
`POLICY_QA` 与 `SELF_ANALYTICS` 两个 `intents`（`app/agent/escalation.yaml`），改
`reply_mode` 会连统计问答那条路径的可见文本一起改掉——那是另一个面，不在本次范围，而且会
让支持集（`evals/support_set.json`）的读数整体位移，变成一次口径变更而不是一次阈值修正。

于是本次接受一个明确的成本：**零命中的 POLICY_QA 一律触发 `no_evidence` 信号，而它的
`reply_mode: replace` 让 `SupportAgent._shape` 整句替换掉动作层的措辞。所以
`empty_query` / `no_visible_chunks` / `no_match` 三者在客户眼前看到的是**同一句转人工文案**，
真正不同的只有动作层 `Draft.reply`（`no_match` 是那句「这次没检索到和这个问题相关的条款：
问法可能和条款措辞对不上。可以换个说法再问一次，或者直接转人工核实。」，
`empty_query` 与 `no_visible_chunks` 沿用原来那句）与轨迹上的 `empty_reason`。**
这条成本是知情的、被接受的，不是遗漏：把它写成「客户会看到两句不同的话」是错的。

其余被否决的两条：

1. **继续用一个 0.35 覆盖所有尺度，只把 BM25 那一侧调大。** 否决：这正是「一个有结果就永不
   转人工、融合分那侧每轮都转」的原状。一个数字无法同时服务四个量级，调它只是决定错在哪一侧。
2. **给未知种类回落稀疏线并记一条告警。** 否决：告警在测试里看不见，在离线批跑里也看不见，
   等于把「新尺度没配线」变成一条没人读的日志。`KeyError` 让它在第一次跑用例时就暴露。

## 已知缺口

1. **尾部块标 `rerank`，但它的值是夹紧后的融合分。** 语义上它不属于重排尺，标 `rerank`
   是为了让整张表只有一个种类（否则尾部会拿融合线去比一个被夹过的数）。这条不进入阈值判定：
   `best` 是全表最高分，必在头部，尾部种类不会被读到。属语义与措辞的偏差，登记在此。
2. **动作层 `_EMPTY_POLICY_REPLIES[evidence.empty_reason or "no_visible_chunks"]` 的 `or`
   兜底**只在一种退化状态可达：命中了切块、但所有卡片都被跨天有效期边界拒掉，于是
   `cards` 为空而 `empty_reason` 仍是 `None`。此时按 `no_visible_chunks` 说话，与实际情况
   偏差一个词，不会被客户区分的（见上一节：客户本来也只看到转人工那一句）。
3. **`EMPTY_REASONS` 没有运行时校验**：三个取值是常量，`classify_empty()` 是纯函数，但
   没有任何断言钉住「返回的字符串一定在词表内」。建议后续补一条最小钉住用例。
4. **`dense` 与 `rerank` 没有端到端断言，但两者原因不同**：`rerank` 是**默认关闭**的可选通道
   （`app/core/config.py` 的 `retrieval_rerank_enabled=False`），打开时 `HybridPolicySearch.search()`
   会把 `score_kind` 写成 `rerank`、端到端可达，缺的只是一条真的打开它跑一遍的用例。
   `dense` 则**到不了这个面**：`_dense_ranked()` 产出的稠密分只在混合器内部充当一路通道，
   `search()` 的输出只会是 `fusion` 或 `rerank`（`_scored_order()` 只写这两种），因此
   `evidence_kind` 永远读不到 `dense`、`escalation_no_evidence_score_dense` 在当前接线方式下
   **不可达**。这一半不是「缺一条用例」，是「缺一条接线」：要用它得先让稠密分真的成为某条
   路径的输出，再补端到端用例；在那之前不得写成「已被覆盖」。
5. **`evals/**` 本次未跑**（离线评测由使用者侧自行复跑）。因此「阈值改动对评测读数的位移」
   没有读数，只有上文那批 seed 量级作为量级说明——它不是评测读数。
