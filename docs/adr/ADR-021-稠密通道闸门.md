# ADR-021：稠密通道按 BM25 的盲区触发，而不是按分数开关

- 状态：Accepted
- 日期：2026-10-25
- 关联：[ADR-001](ADR-001-工作流优先.md)（工作流优先）、`docs/spec/项目规格.md` §11.4/§11.5、`evals/dense_gate_analysis.py`

## 背景

上一次把稠密通道的四个通道都在本机真实端点上跑出了数字（§11.5 的表），但那张表只回答了「打开之后能拿到什么」，没有回答「什么时候值得打开」。

原来的形态是**一个布尔开关**：`RETRIEVAL_DENSE_ENABLED` 一开，所有查询都去调 embedding 端点。这有两个问题：

1. **代价与收益无关。** 稠密通道在候选块上是全表余弦扫描 + 一次远程 embedding 调用；17 个块扫得起，5 万块扫不起（§11.5 已列为边界）。如果 90% 的查询 BM25 已经稳稳命中第一名，每一条都付一次远程调用就是纯浪费。
2. **阈值无处可调。** 有人会想把开关换成「BM25 分数低才开」，但**低分和答错不是一回事**。

第 2 点不是推测，是实测撞出来的：**BM25 在这份语料上错得很自信。** 17 条标注里有 3 条 rank-1 没命中，它们的 BM25 top-1 分数是 **12.96 / 20.64 / 25.31**。这三条的分数比 12 条命中用例里的多数还高。所以「分数低才开稠密」这条规则，**恰好在最该开的三条上不会触发**。

## 决策

### 1. 门控在 embedding 之前决定，用两个信号

`app/retrieval/hybrid.py::DenseGate` 在**调用 embedding 之前**判断这一条查询要不要稠密通道：

```text
min_top1_score = 5.0     BM25 top-1 分数下限（低于它 → weak_sparse）
min_coverage   = 0.35    查询词在 top-1 块里的覆盖率下限（低于它 → low_coverage）
```

判定顺序：无稀疏命中 → `no_sparse_hits`；top-1 分数 < 5.0 → `weak_sparse`；**top-1 词覆盖率 ≤ 0.35 → `low_coverage`**；否则 `sparse_confident`，跳过 embedding。

命中即开，**不命中即省**：门控通过时把 BM25 的命中**原样保留**再与稠密结果做 RRF 融合，所以稠密通道只是在稀疏结果之上补位，不是替换。

### 2. 为什么是覆盖率而不是分数

覆盖率 = 「查询词里有多少比例出现在 top-1 块的标题 + 正文里」。它度量的是**词面证据的厚度**，而 BM25 的三个 rank-1 失败恰好就是「词面对上了、语义对不上」的那一类：

| 用例 | BM25 top-1 分数 | top-1/top-2 分差 | 覆盖率 | 稠密看到的名次 |
|---|---|---|---|---|
| `refund-scope` | 12.96 | 1.76 | 0.33 | 1 |
| `delay-handling` | 20.64 | 0.90 | 0.35 | 2 |
| `ticket-priority` | 25.31 | 5.42 | 0.26 | 4 |

三条的覆盖率是 0.26 / 0.33 / 0.35，是 17 条里最低的三条；而它们的分数是中上段。**分数和错不对几乎不相关，覆盖率和错不对相关。**

### 3. 阈值是扫出来的，不是拍的

`evals/dense_gate_analysis.py` 在同一份 17 条标注上做两轮扫描（`--coverage-sweep` / `--score-sweep`），每档都报告 recall / MRR / nDCG、**embedding 实际调用次数**和**三个 rank-1 失败被捞回几个**：

覆盖率扫描（保留出厂分数下限 5.0）：

| 覆盖率阈值 | recall@1 | recall@3 | recall@5 | MRR | nDCG@5 | embedding 调用 | 捞回失败 |
|---|---|---|---|---|---|---|---|
| 0.25 | 0.794 | 0.912 | 0.971 | 0.875 | 0.882 | 0/17 | 0/3 |
| 0.30 | 0.794 | 0.912 | 0.971 | 0.875 | 0.882 | 1/17 | 1/3 |
| **0.35** | 0.794 | **0.971** | 0.971 | 0.882 | 0.889 | **5/17** | **3/3** |
| 0.40 | 0.794 | 0.971 | 0.971 | 0.882 | 0.889 | 7/17 | 3/3 |
| 0.50 | 0.794 | 0.971 | 0.971 | 0.882 | 0.889 | 9/17 | 3/3 |

分数扫描（关掉覆盖率）：

| 分数阈值 | recall@1 | recall@3 | recall@5 | MRR | nDCG@5 | embedding 调用 | 捞回失败 |
|---|---|---|---|---|---|---|---|
| 5.00 | 0.794 | 0.912 | 0.971 | 0.875 | 0.882 | 0/17 | 0/3 |
| 13.00 | 0.794 | 0.971 | 0.971 | 0.882 | 0.889 | 1/17 | 1/3 |
| 20.00 | 0.794 | 0.971 | 0.971 | 0.882 | 0.889 | 3/17 | 1/3 |
| 26.00 | 0.794 | 0.971 | 0.971 | 0.882 | 0.889 | 11/17 | 3/3 |

读法：**分数阈值要开到 26 才捞得回全部三条，代价是 11/17 的查询都要付一次 embedding（65%）；覆盖率阈值 0.35 同样捞回全部三条，代价是 5/17（29%）。** 两者买到的是同一个结果，coverage 的代价是 score 的一半不到，所以出厂值取 coverage 0.35。

### 4. 门控是**加法**，不是替代

出厂配置下，门控后的读数与无条件稠密**一样好**：

```text
bm25  : recall@1 0.7941 / @3 0.9118 / @5 0.9706 / mrr 0.8745 / ndcg@5 0.8824
gated : recall@1 0.7941 / @3 0.9706 / @5 0.9706 / mrr 0.8824 / ndcg@5 0.8890
        embedding 调用 5/17
```

`recall@3` 从 0.9118 抬到 0.9706（与无条件 hybrid 同级），`recall@1` 不降——门控没有牺牲任何指标，只把 embedding 调用从 17 次降到 5 次。

### 5. 决策留痕

`HybridPolicySearch.last_dense_decision` 记下这一条查询的判定（`sparse_confident` / `low_coverage` / `weak_sparse` / `no_sparse_hits` / `always_on` / `no_embedder`）。检索实例是**每次调用新建**的，所以这个字段不会跨请求串味；它被检索 span 带上，回放时能看到「这一条为什么没走稠密」。

### 6. 没有门控时保持旧行为

`RETRIEVAL_DENSE_GATE_ENABLED=false` 时 `dense_gate=None`，稠密通道每次都跑（判定记为 `always_on`）。这保留了「先在 CI / 离线把稠密通道打开看全貌」的用法，也保留了上一次那张无条件 hybrid 表的可比性。出厂默认 `RETRIEVAL_DENSE_GATE_ENABLED=true`。

## 后果

- **embedding 调用从 17 次降到 5 次**（-71%），指标一项没降。这条数字是本次在 LM Studio `bge-m3` 上跑出来的（`evals/dense_gate_analysis.py`，provider = endpoint）。
- **一个必须说清的修正**：上一次文档里写的「4 条用例的正确答案进不了前两名」在**逐条证据**上是 **3 条 rank-1 完全没命中 + 1 条部分命中**（`refund-window` 首个命中正确、另一个相关章节被挤出 top-3）。门控只对**前 3 条**有意义（`refund-window` 的问题不是名次而是第二个相关章节没进 top-3，稠密也救不了）。本 ADR 与 §11.5 用的是同一份数据，数字以这里的逐条表为准。
- **门控阈值是这份语料上的标定值**，不是通用结论。语料换了要重跑 `evals/dense_gate_analysis.py` 重新扫。
- **门控只能省调用，不能提准确率。** 它的价值在于「同样的效果、更低的代价」；真正抬 `recall@1` 的是重排（0.912）和稠密本身（0.853），门控两样都不做。
- **覆盖率是词面信号**，对同义改写、跨语言提问这类「词对不上但意思对」的情况不敏感；这类查询在 BM25 里本来就拿不到分，覆盖率会偏低 → 门控会放行稠密，这恰好是对的行为。
- 稠密通道仍是**全表余弦扫描**，没有 pgvector、没有 ANN。门控省的是 embedding 调用，不是扫描成本；块数长大后扫描才是瓶颈。
- 没有「门控准不准」的在线评估——只有离线扫描。线上无法区分「门控放行了但稠密也没捞回来」和「门控本该放行」。

## 备选方案

- **保留布尔开关，只在文档里写「按需打开」**：没有可执行的判定，所谓「按需」只是口号；实测里 65% 的查询要付 embedding 才是「按需」。
- **只按分数门控**：被上表否掉——要捞回全部三条 rank-1 失败需要 11/17 次调用。
- **只按覆盖率门控、去掉分数下限**：分数下限留着是为了兜住「BM25 几乎没有词面证据」的情形（`weak_sparse`），成本是 0 次额外调用，没有理由去掉。
- **门控时直接用稠密替换稀疏 top-1**：会让 `recall@1` 从 0.794 掉到 0.794 之下——§11.5 的表已证明无条件 hybrid 的 `recall@1` 就是 bm25 的水平，替换不会更好。
- **按 query 长度 / 意图类别门控**：意图类别在检索层拿不到（检索在路由之后、但意图与「BM25 盲区」没有对应关系）；长度与错不对无关。
