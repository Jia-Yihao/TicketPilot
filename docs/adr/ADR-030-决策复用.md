# ADR-030：台账复用入口的模型读数，但先独立复核

- 状态：Accepted（2026-10-26 补充裁决：新增决策 6「服务端派生键的重封与留痕」，未推翻任何既有条款）
- 日期：2026-10-26（2026-10-26 修订：补入决策 6，定死「同一份上下文」的读法）
- 关联：[ADR-020](ADR-020-对话入口的模型缺口.md)（对话入口只在缺口上问模型）、[ADR-003](ADR-003-服务端退款规则.md)（退款资格由服务端规则判定）、[ADR-004](ADR-004-审批绑定.md)（钱的动作要人点头）、`docs/下一步规划.md` §9.3（P2）

## 背景

[ADR-020](ADR-020-对话入口的模型缺口.md) 让对话入口在规则读不懂时问一次模型，并只采纳退款意图；
同一轮的写动作随后进任务台账，`_run` 用同一份请求**重新** `brain.plan` 一次。这个设计保住了
「台账不信任入口」：入口那道门写错时，最坏是多追问一轮，而不是一张被入口指定了意图的退款单。

代价也是真的：一次端到端退款对话要问两次模型，`llm_usage` 落两行，实测 **2 次调用 /
918+645 token / 20.3 秒**（ADR-020 的原始读数）。两次调用还可能给出不同答案——入口采纳了
退款意图，台账重算后不采纳，用户看到的是「入口问过一轮，台账又按另一套结论落任务」。

要改的不是安全属性，而是**验证方式**：把「重算」换成「复核」。入口留下的不能是一句结论，
而是一份足以让台账独立复算的决策记录。

## 决策

### 1. 决策记录只在内存里，不落任务字段

`ModelDecision`（`app/agent/decision.py`）是 frozen dataclass，随 `create_task(...,
decision=...)` 传给台账，**不写进 `tasks.request` 或 `tasks.context`**。落库的结论会让入口
控制台账；内存里的记录只是一份待复核的输入，台账不采纳时可以直接丢弃。

记录携带六样东西：

| 字段 | 用途 |
|---|---|
| `digest` | 请求 + 上下文的规范化摘要，与幂等键使用同一套 `canonical_digest`（「上下文」的读法定死见决策 6） |
| `ruleset` | 规则集指纹 `RULESET_FINGERPRINT` |
| `model_name` | 当次调用的模型标识（`None` 表示没有模型） |
| `rule_intent` / `rule_order_id` / `rule_amount_cents` | 入口当时看到的规则读数 |
| `model_intent` / `model_order_id` / `model_amount_cents` | 模型读到的结果 |
| `trace` | 这次调用的用量（请求数、重试、token、延迟、状态、是否走 OTel） |

### 2. 复用前逐项复核，任何一项不同就重算

`IntentBrain.plan(..., decision=...)` 先跑 `classify()` 得到**当前**规则读数，再要求
`ModelDecision.verifies()` 同时满足：

1. 请求摘要相同（同一句话、同一份上下文）。「同一份上下文」按决策 6 读作**本回合终态上下文**，不是模型调用瞬间的输入快照；
2. 规则集指纹相同（规则文件一个字节都没变）；
3. 模型名称相同（没有换模型或从模型切回规则）；
4. 规则意图、订单号、金额三项读数与当前规则完全一致。

全部满足才复用：返回同一份读数，来源仍记 `pydantic_ai`，`ModelTrace.reused=True`。
任何一项不满足就落到普通路径，需要时重新调用模型——最坏情况是多一次调用，
**不会**出现未经复核的结论。

### 3. `rules` 模式忽略记录，一次都不问

`AGENT_MODE=rules` 在碰模型之前返回。即使传进来一份格式正确的记录，台账也按规则路径
执行，`ModelTrace` 为 `None`。同时记录里的 `model_name` 必须与当前 brain 的模型一致，
所以规则模式的 `None` 不会与模型模式的记录互相匹配。

### 4. 复用不写第二行用量账

`task.routed` 的 `model` 载荷保留完整读数，并带 `model_reused=true`；`llm_usage` 只在
`model_trace` 存在且未复用时写一行。复用意味着这次读数已经在对话入口那一轮付过钱，
再记一行会把同一笔调用算两次。模型失败时入口不产生记录，台账会重新调用；失败的那次
仍按原逻辑记 `FAILED`，因为它确实花了钱、什么也没买到。

### 5. 两轮澄清仍然各付一次

复用绑定的是**同一份请求摘要**。第一轮「ORD-DEMO-1001 那笔钱给我退回来」与第二轮
「129 元」是两个不同的请求，摘要不同，第二轮台账不能复用第一轮入口的读数。这是刻意
保留的边界：跨轮缓存需要另一套「同一会话 + 槽位合并后请求」的键，不能靠放宽摘要匹配
来省这一次。已知代价登记（2026-10-27 独立审查随附一般项）：`resumed`（被中断意图
恢复）回合若叠加决策 6 的迟发键命中，复用同样失败、多付一次模型调用——这与「初始
digest 与终态 digest 不同源」的既有不对称同源，本轮接受该代价，未修。

### 6. 服务端派生键允许以终态上下文重封摘要，但必须留痕（2026-10-26 补充裁决）

**定死的读法**：决策 2 第 1 项的「同一份上下文」= **本回合终态上下文**，即台账复核时
实际拿去算 `request_digest(request, context)` 的那份 `context`；它**不是**模型调用
那一瞬间的输入快照。因此入口在模型回答之后往 `context` 里补键时，必须用终态上下文
**重算**（重封）`ModelDecision.digest`，而不是留着一份与终态上下文不一致的旧摘要去
「证明」模型见过那个键。

**为什么允许（这是审查要看的论证，不只是结论）**：可后置进这份 `context` 的只有
**服务端派生键**，当前唯一一个是 `refund_reason`——它在 `app/agent/support_agent.py`
的迟发匹配块里由关键词规则表从**本回合自己的原话**读出来。按
`.qoder/rules/refund-reason-taxonomy.md` §5.6.5，退款原因**不属于模型的抽取面**：
模型不抽取、不采纳，`IntentOutput` 里根本没有这个字段，提示词也没有任何「抽取退款
原因」的要求。于是它的出现不可能改变被复核的那几项读数——`verifies()` 的六项里除了
`digest`（本次重算的对象）之外，规则意图、规则订单号、规则金额、规则集指纹与模型名
**逐字未动**。复用因此仍然只复用「模型确实回答过的东西」，决策 1 与决策 2 要防的
「入口把自己的复核证据改掉」不成立：变的那一段是**服务端自己算出的事实**，没有任何
一项模型读数被替换或补位。

不这么定的两条路都更贵：不重封，则台账复核必失败（摘要与终态 `context` 不一致），
落回普通路径**再问一次模型**——本 ADR 省下来的第二次调用被买回去，`llm_usage` 从
1 行变 2 行；为省那次调用而放宽 `verifies()` 的摘要比对，则等于取消决策 2。

**代价与防线**：痕迹必须留在 trace，使记录不谎称模型见过该键。形状是一条
`kind=understand`、`name=decision.reseal` 的 span，属性 `derived_keys` 只写**键名**
列表（当前恒为 `["refund_reason"]`），不写值、不写订单号、不写摘要本身——与
「trace 只记候选数量、不记候选订单号」是同一条边界。读 trace 的人由此能看出这一轮的
摘要是后置键进上下文之后重算的，而不是模型输入的一部分。三条硬边界：痕迹**不进**
回复 / 公开回执、**不进**模型 prompt、**不进** `ModelDecision.verifies()` 比对的六项
字段；`tasks` 的幂等键与 `digest` 的计算口径不变
（`.qoder/rules/intent-candidates.md` §2.3 第 6 条），重封只重算，不改算法。
澄清（2026-10-27 独立审查随附一般项的订正，不是新增边界，是把既有形状写准）：trace 面
（`GET /api/v1/traces/{trace_id}`）是客户可自查**自己**会话与任务的观测面，痕迹在这个面上
确实可见，因此逐字成立的口径是「不进回复 / 公开回执」而不是「不进任何客户可见文本」；
客户能读到的那条 `decision.reseal` span 的属性**只写键名**列表 `derived_keys`
（当前恒为 `["refund_reason"]`），不写值、订单号与摘要本身。

**重开条件（不得顺手套用本节）**：若将来出现第二个后置键、而该键**会**进模型输入，
本节裁决**不适用**，必须重开一条 ADR。判据是「这个键当时给模型看过吗」，不是「它
是不是服务端算出来的」。写代码时注意 `_consult_model` 里的 `model_context` 与台账
`context` 是两份：前者多带 `pending_intent` / `last_intent` 供候选内核取证据，
`digest` 覆盖的是后者。任何把 `model_context` 独有的键搬进 `context`、或让模型补位
`refund_reason` 的改动，都会踩到这条重开条件。

## 证据

### 用例（离线，不依赖模型服务）

`tests/test_decision_reuse.py` 11 条（第 8 条于 2026-10-26 P8 轮补入，第 9–11 条于
2026-10-26 重封留痕轮补入）：

| 用例 | 钉住的事实 |
|---|---|
| 验证通过的记录被复用 | 入口 1 次调用；台账复用后仍 1 次；`trace.reused=True` |
| 每一种不匹配都重算 | 摘要、规则集、模型名、规则意图、规则金额、换请求六种篡改，逐项触发新调用 |
| `rules` 模式忽略记录 | 0 次调用，来源 `rules` |
| 端到端一轮退款 | 1 次调用、1 行 `llm_usage`、`model_reused=true` |
| 模型失败 | 不建任务、不产生错误写动作，仍记一行 `FAILED` |
| `rules` 模式端到端 | 0 次调用、0 行用量 |
| 两轮澄清各付一次 | 两轮共 2 次调用、2 行用量；第二轮请求摘要不同，不能复用 |
| 复用搬运当初的 reason | 记录里 `model_reason` 非空时，复用原样带回该原因；不重新判定、不额外发请求（P8 轮补入） |
| 重封留痕存在且不多花一次调用 | 重封回合（模型被采纳、原因由迟发匹配补进上下文）有一条 `decision.reseal` span，`derived_keys == ["refund_reason"]`；仍 1 次调用、1 行用量、`model_reused=true`；痕迹不进回复、不进模型输入、不进 `tasks.context`（重封留痕轮补入） |
| 迟发匹配未命中时没有痕迹 | 模型被问并被采纳、但这句原话没有原因关键词：该键不出现、不重封，trace 里**没有** `decision.reseal`（上一条的反向半边，防恒真） |
| 规则直读原因的回合没有痕迹 | 规则把意图与原因一起在模型之前读好（`route.refund_reason` 非空，迟发匹配整块跳过）：trace 里**没有** `decision.reseal` |

### 真实模型读数（本机 LM Studio `qwen3-8b`）

**单轮完整退款**（`ORD-DEMO-1001 那笔钱 129 元给我退回来`）：

```text
agent_calls=1  usage_rows=1  source=chat  requests=1
input_tokens=476  output_tokens=164  latency=6321 ms
task_status=WAITING_APPROVAL  model_reused=true
task.routed.model: requests=1 input=476 output=164 latency=6321.4 ms
```

用量行与 `task.routed.model` 是同一次运行里的同一个 `ModelTrace`，因此逐项相同；
这里不是把两次运行的读数拼在一起。

**同请求、同模型的 A/B**（入口先各问一次，再比较台账；token 绝对值随生成长度浮动，不与上面的单轮块逐字相等）：

| 路径 | 调用次数 | token | 台账耗时 |
|---|---|---|---|
| 旧路径（台账重算） | 2 | 1234 | 13.63 s |
| 新路径（复核后复用） | 1 | 620 | 6.97 s |

**两轮澄清**（先问缺金额，再补「129 元」）：仍为 2 次调用——见决策第 5 条，这不是回归。

## 后果

- 单轮写动作的模型代价减半：一次调用、一行用量、一份读数。`planning_source` 仍由台账
  自己写，不能靠入口伪造。
- 「台账不信任入口」没有变弱：台账验证的是**可复算的输入**（摘要、规则集、模型配置、
  规则读数），不是入口的结论。篡改任何一种输入都会退回重算。
- 决策记录不能跨进程传递：`RULESET_FINGERPRINT` 是进程内规则集指纹，换一个部署或改一行
  规则都会让旧记录失效。这是安全方向，不是缺陷。
- 两轮澄清仍各付一次。要做跨轮复用，需要单独的会话级键与槽位合并口径，不能顺手放宽
  摘要匹配。
- 记录只覆盖「入口确实调用了模型」的轮次。规则读懂的句子入口不问模型，台账也不问，
  零调用路径逐字未变。
- 本轮没有新增表、没有迁移；`ModelDecision` 是内存对象。
- 决策 6 之后，「模型答完之后补进上下文的服务端派生键」这一类回合多一条
  `decision.reseal` span（`kind=understand`）。它只多一个 span，不改任何读数：调用次数、
  用量行数、`model_reused` 与回执文案逐字不变；默认的规则直读路径零新增 span。
- 本轮新增 7 条用例只有 SQLite 证据；PostgreSQL 复跑计入全量门禁读数，不单独声称。

## 备选方案

- **把入口的 `SupportPlan` 直接传给台账**：台账变成「调用方说什么就记什么」，入口写错时
  没有任何一层能纠正，`planning_source` 也失去意义。否决。
- **把模型结论写进 `tasks.context` 再读回来**：落库的结论会让入口控制台账，且回放/重试
  都会带上旧结论。否决。
- **只比请求摘要就复用**：规则或模型换了以后仍会复用旧读数，等于让配置变更失效。否决。
- **按「同一会话」跨轮复用**：需要槽位合并与更复杂的失效规则，且会把第一轮的模型读数
  用在第二轮的请求上。本轮不做，留作独立设计。
- **复用后仍写一行用量账**：同一笔调用会被计两次，模型预算与统计都会失真。否决。
