# ADR-013：事务性 Outbox——消息与业务事实同生共死

- 状态：Accepted
- 日期：2026-10-24

## 背景

退款执行有一条明确的失败路径：**请求发出去了，结果没回来**。

外部退款服务在「已提交但响应超时」时会发生这件事。此时本地状态是
`UNKNOWN`——既不能算成功，也不能算失败。这条路径如果只靠请求线程处理，会有三个问题：

1. **消息会丢。** 如果「请稍后再确认」这句话是请求线程顺手写的，进程在写台账之后、
   写消息之前崩溃，客户就既没有退款结果，也没有人通知。
2. **对账会漏。** 需要对账的退款散落在「台账状态 = UNKNOWN」里，谁来扫、扫到哪、
   扫不出来怎么办，全凭记忆。
3. **客户侧无感。** 客户拿到的回复是请求线程当场拼的；事后想统一重发或改口径，没有第二份可信来源。

更一般的问题在所有「本地已改、外部未改」的场景里都成立：这类问题最难排查，
因为两边对不上，而且没人说得清是什么时候对不上的。

## 决策

### 1. 消息行与业务事实写在同一个事务里

新增 `outbox_messages` 表，字段与终局方案 §4.3 一致：

| 字段 | 含义 |
| --- | --- |
| `aggregate_type` / `aggregate_id` | 消息属于哪个业务对象（如 `refund_task` / 任务 ID） |
| `event_type` | 消息类型（如 `refund.pending_confirmation`） |
| `payload` | 消息内容（JSON） |
| `dedupe_key` | 幂等键，唯一约束 |
| `status` | `PENDING` / `PROCESSING` / `SENT` / `FAILED` / `CANCELLED` |
| `retry_count` / `available_at` / `last_error` | 重试状态 |
| `sent_at` | 落地时间 |

退款进入 `UNKNOWN` 时，`RefundExecutionService._queue_pending_confirmation` 在**同一个事务**里
写入一行 `refund.pending_confirmation`。台账变成 `UNKNOWN` 与消息进入队列，要么一起发生，
要么都不发生——不存在「台账说不知道，消息说已经通知了」的中间态。

`dedupe_key` 上有唯一约束（`refund:{task_id}:pending_confirmation`）：同一个业务事实
被写两次也只产生一条消息。这让「重试请求路径」不会变成「重发通知」。

### 2. 投递是独立于请求线程的 worker

`OutboxService.deliver(sink)` 是一轮投递：

```text
取到期行 → 条件更新认领（status = PROCESSING）→ 提交 → 推送 → 标记 sent / 失败退避
```

- **认领先提交，再推送。** worker 在推送途中崩溃时，行停在 `PROCESSING`，
  而不是被误标成已送达。语义是「至少一次」，不是「恰好一次」。
- **认领是条件更新**（`WHERE id = ? AND status = 'PENDING'`）。两个 worker 抢同一行时，
  只有一个能赢——在 SQLite 和 PostgreSQL 上都成立（`tests/test_postgres_outbox.py`
  用两个线程验证过：恰好一个 `True`）。
- **sink 抛异常 = 没送达。** 行退回 `PENDING`，`retry_count++`，按指数退避推迟
  `available_at`；超过 `max_attempts`（默认 5）转为 `FAILED`（死信）。
- **sink 是注入的。** 本项目没有外部系统可推，若代码里假装有，就等于造了一个
  会说谎的队列。当前实现推的是「退款对账」：把台账 `UNKNOWN` 的退款与权威退款记录对上。
  （2026-10-24 补充：同一注入点现在有两个消费者，第二个是主动通知的出站投递，
  见 [ADR-017](ADR-017-proactive-outbound-seam.md)。「没有外部系统可推」仍然成立——
  出站只有拒绝发送与写本地文件两种传输。）

### 3. 没确认不是送达

本项目最初只投递 `refund.pending_confirmation`，它的消费者是**对账**
（T7-4 起增加 `proactive.confirmed`，消费者是 `ProactiveSender`，见 ADR-017）：

- 权威记录显示已退款或已失败 → 消息 `SENT`；
- 权威记录仍然查不到 → 消息**不算送达**，退回等待下一轮；
- 一直查不到 → 退避重试到阈值，进入死信。

这是「结果未知（已发出，未确认）→ 不重试，进入对账」这条规则的落地：
执行器不重复发出，Outbox 负责把「未确认」这件事收敛掉，并且收敛失败时留下痕迹。

### 4. 队列对坐席可见

`GET /api/v1/outbox`（要求 `support` 或 `approver` 角色，按租户隔离）列出队列与死信；
`POST /api/v1/outbox/deliver` 触发一轮投递。死信不是日志里的一行字，而是坐席能查到的队列项。

worker 以独立进程运行：`python scripts/outbox_worker.py`（`--once` 单轮，
默认每 30 秒一轮）。它不跑在应用进程里，所以投递不会和请求抢同一个数据库连接。

## 后果

- 退款结果未知时，客户与坐席都能看到「仍在核实」，而不是一片空白。
- 对账有了确定的重试节奏与终点：收敛了就是 `SENT`，收敛不了就是死信。
- 消息与业务事实同生共死，进程崩溃不再制造「本地改了、外面不知道」的静默分叉。
- 代价是一张表、一个 worker 进程和一套投递状态机；换来的是「最终一致」可证明。
- sink 是注入的，所以将来接真正的外部系统（物流、支付通知）时，
  生产者一行不用改。

## 备选方案

- **请求线程里直接写通知**：消息会丢，且与请求强耦合——请求失败就没有通知。
- **定时扫 `tool_executions` 里状态为 UNKNOWN 的行**：等价，但没有消息语义，
  没有幂等键，没有死信，没有退避，也无法把「这次要通知什么」与「这次要重试什么」分开。
- **事务内直接调外部系统**：外部超时时事务要么长时间挂起要么回滚，
  而外部可能已经生效——这正是要避免的分叉。
- **消息队列（Kafka/RabbitMQ）**：能力强但引入中间件依赖；本项目的规模用不到，
  而「同事务写行」这一条用数据库就能做到。
