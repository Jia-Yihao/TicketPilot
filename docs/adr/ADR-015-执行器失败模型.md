# ADR-015：执行器失败模型——重试、熔断、降级与回执

- 状态：Accepted
- 日期：2026-10-24

> 编号说明：写作本篇时 ADR-012（策略外置与阈值灰度）与 ADR-014（记忆模型）都还空着，
> 本篇按落地顺序排在当时已用的最大编号之后。两个预留号后来分别由 ADR-014（T5）与
> ADR-016（T4，渠道抽象，未占预留位）补齐，ADR-012 仍空。

## 背景

工具调用失败时，最容易出的两类事故是**静默**与**重复**。

- **静默**：调用抛了异常，Agent 没有回执，客户只看到一句「稍等」，不知道发生了什么；
- **重复**：一次超时让系统以为没发生，于是再发一次——对写操作来说这是第二次扣款。

之前这版代码把「调用工具」写成一个 `try/except`，失败就返回一句错误文案。
它没有回答三个问题：这次失败**是什么性质**？能不能**再来一次**？不能重来时**说什么**？

## 决策

### 1. 失败分六类，分类决定后果

`app/tools/executor.py::FailureKind`：

| kind | 含义 | 是否重试 | 降级 |
| --- | --- | --- | --- |
| `validation` | 参数不合法，请求根本没发出去 | 否 | `ask_user`（问客户补槽位） |
| `timeout` | 超时，结果未知 | 视幂等性，见下 | `retry_later` |
| `upstream` | 上游 5xx / 熔断打开 | 是 | `retry_later` |
| `unknown` | 发出去了，不知道结果 | **永远不重试** | `stop`（进入对账） |
| `business` | 业务明确拒绝（超期、余额不足） | 否 | `stop` |
| `internal` | 内部异常 | 否 | `handoff` |

分类在**异常层**完成（`TimeoutError` → timeout、HTTP 5xx → upstream、
`ToolResult(ok=False)` → business、其余 → internal），业务代码不需要自己声明失败类型。

### 2. 两条不可让步的安全规则

```python
if kind is FailureKind.UNKNOWN:
    return False                      # 结果未知：永不重来
if manifest.side_effect and manifest.idempotency != "required":
    return False                      # 写操作且不幂等：永不重来
```

- **有副作用的工具，只有声明了幂等（`idempotency="required"`）才允许重试。**
  否则重试就是第二次副作用。
- **结果未知一律不重试**，哪怕工具是幂等的。原因不是幂等性不够，而是语义：
  「已发出、未确认」的正确下一步是**对账**（ADR-013 的 Outbox），
  不是再发一次。这条规则曾经写漏过，被 `tests/test_tool_executor.py`
  里的 `test_an_unknown_outcome_is_never_repeated` 逮住。

> **2026-10-28 增补（第三条）**：上面两条由执行器强制，新工具绕不过。还有一条不在这里，
> 它约束的是工具**怎么把结果交出来**——**结果未知必须以失败码浮上来，不能伪装成回执**。
> 执行器只按 `error_code` 分故障类，认不出「`ok=True` + 可疑码」这种伪装，所以这条是工具
> handler 的义务，由 `tests/test_refunds.py::test_an_unconfirmed_refund_is_a_failure_not_a_receipt`
> 钉住（`request_refund` 遇 `PENDING_CONFIRMATION` 返回 `ok=False` + `OUTCOME_UNKNOWN`）。
> 规格侧见 `docs/spec/项目规格.md` §23.2。本条增补不改上面两条决策。

### 3. 重试、熔断、降级写在 Manifest 里，不写在代码里

`ToolManifest.retry` 声明可重试的 kind、最大次数与退避基数；
`ToolManifest.degradation` 声明降级链（有序，每一步都带用户能看懂的话）。
执行器按声明执行，代码里没有「如果超时就重试三次」这种硬编码。

退避是指数的：`backoff_ms * 2^(attempt-1)`，实测序列 `[0.2, 0.4]`。

熔断器（`CircuitBreaker`）**按进程共享**，不是按会话：一个上游坏了是对所有人坏，
按会话各断各的等于没断。连续失败达阈值 → `open`（直接快速失败，不再打上游）
→ 冷却 → `half_open`（放一个探测请求过去）→ 成功则回到 `closed`。

降级链走完的兜底是 `handoff`：**不允许「我不知道」式的回复**。
每一步降级都写进 trace（`tool.degraded.{name}`）与任务事件（`tool.degraded`）。

### 4. 回执只从工具自己的返回值渲染，且必须能填满

`ToolManifest.receipt` 是给用户看的那句话，占位符从 `result.data` 里取，
**不从请求里取**——所以金额和单号不可能由模型书写。

三条硬规则：

1. 占位符只能引用 `result_schema` 声明过的字段；引用未声明字段，回执注册失败，
   工具在注册阶段就被拒（不是运行时报错）。
2. **填不满就不渲染**：缺字段、或字段类型对不上，整条回执作废，
   退回 handler 自己写的 message。半句话比 handler 自己的话更糟。
3. 回执**替换** handler 的 message，只在它能完整渲染时替换。

第 2 条是踩出来的：改写 `get_order` 的回执时丢了「可退余额」，
Golden Set 的 `order-query-own` 用例当场失败。修法不是把断言放宽，
而是把回执补成完整的一句，并把这个规则写进 `ToolManifest` 的文档字符串。

### 5. 网关管五道闸，执行器管调用之后

`ToolGateway`（调用前）：参数校验 → 权限 → 审批 → 幂等键 → 审计。
`ToolExecutor`（调用后）：预算、重试、熔断、降级、回执。

失败的副作用**无论工具有没有自己的审计**都会写一条 `audit_events`（`outcome=ERROR`），
detail 里带 `failure_kind`、`attempts`、`degradation`——排查时能直接看到
「这是超时还是上游挂了」「试了几次」「最后走了哪条降级」。

## 后果

- 每种失败都有确定的后果：要么重试、要么问客户、要么转人工、要么进对账，
  没有「兜底 catch 一下」。
- 写操作不会被执行两次；未确认的结果不会被重复触发，而是被对账收敛。
- 重试与降级策略在 Manifest 里可见、可评审、可按工具调整。
- 回执保证「金额与单号来自工具返回，不由模型书写」，同时不会因为字段缺失
  而说出半句话。
- 代价是执行器、网关、回执渲染三块新代码，以及每个工具多写一段 Manifest。

## 备选方案

- **统一的 `except Exception` 返回错误文案**：静默与重复两种事故都从这里来。
- **在业务代码里判断「能不能重试」**：每个工具一套判断，迟早不一致；
  而且判断依据（幂等性、失败形态）是工具的属性，本来就该写在工具旁边。
- **回执由模型组织**：金额与单号会被模型改写或漏写，且无法回归测试。
- **回执缺字段时填空串**：客户看到「订单 ORD-DEMO-1001 当前状态为  ，金额」这种句子，
  比不说更糟。
- **按会话各断各的熔断**：上游故障时所有会话仍会各自重试到超时。
