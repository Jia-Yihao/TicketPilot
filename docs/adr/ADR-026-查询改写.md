# ADR-026：查询侧改写——只改检索文本，不改原话

- 状态：Accepted
- 日期：2026-10-25
- 关联：[ADR-021](ADR-021-稠密通道闸门.md)（稠密门控）、[ADR-024](ADR-024-三级模型闸门.md)（三级模型门控）、[ADR-025](ADR-025-架构与文档守卫.md)（文档一致性守卫）

## 背景

检索的输入是用户原话，但政策语料用的是政策自己的措辞：

- 用户说「三十天以内」，政策写「签收后 30 天内」；
- 用户说「退钱」「快递」「找人工」，政策写「退款」「物流」「转人工」；
- 用户问「严重延迟应该怎么处理」，政策章节叫「处理方式」。

BM25 只认字面。旧金标的 17 条里，`refund-scope`（哪些订单可以退款）明明有
「适用范围」这一章，第一名却是「退款金额」；`delay-handling` 与 `ticket-priority`
的期望章节分别排在第 3、第 3 位。这不是模型不够强，是**查询和语料说的不是同一套词**。

同时，项目有一条不能破的边界：用户原话、意图路由、槽位抽取、金额与订单号、回复文本，
都必须继续基于原始消息。任何「把用户的话改一改再往下走」的做法都会污染这些确定性环节。

## 决策

在检索入口加一层**确定性、离线、只追加**的查询改写，作为 `PolicySearch` 的装饰器：

```text
用户原话 ──► RewritingPolicySearch ──► search_text ──► 稀疏 / 稠密 / 重排
                    │
                    └── 原话仍用于消息、路由、槽位、回复
```

三类变换，按优先级追加到 `search_text` 末尾：

| 变换 | 例子 | 规则 |
|---|---|---|
| 中文数字归一化 | `三十天` → 追加 `30天`；`两周` → `14天`；`一百二十九元` → `129元` | 数值必须跟中文量词；全角数字也认；**保留中文原形** |
| 同义词扩展 | `退钱` → 追加 `退款`；`快递` → `物流`；`找人工` → `转人工` | 只在用户词出现且政策词缺失时追加；只追加政策侧措辞 |
| 章节标题注入 | `严重延迟怎么处理` → 追加 `处理方式` | 先按领域词与 5W1H 选章节，默认 1 个（口径上限 2）；只取 ACTIVE 政策里真实存在的 15 个标题 |

### 1. 追加，不替换

`search_text` 永远是 `原话 + 追加词`。`七天无理由退货` 不能因为把 `七天` 归一成 `7天`
就丢掉与章节标题的字面匹配；`ORD-DEMO-1001`、`DE20010003` 这类标识一个字符都不碰。

### 2. 5W1H 是选择器，不是标签

六个面向固定为 `WHO` / `WHAT` / `WHEN` / `WHERE` / `WHY` / `HOW`。它决定两件事：

- 关键词规则没命中时，用「领域 + 面向」兜底选章节：`退款 + WHEN` → `退款条件`，
  `延迟 + HOW` → `处理方式`，`工单 + WHO` → `转人工`；
- 评测集扩量时每条用例都带 `facets`，扩量必须覆盖六个面向，不能全堆在 `WHAT`。

### 3. 包在最终链路上，而不是某一层里

改写器包在 `build_policy_search()` 组装完成的检索器外面。无论是纯 BM25、
`HybridPolicySearch` 还是带重排的链路，稀疏评分、稠密门控的覆盖率、重排器看到的
都是同一句 `search_text`。这样也避免在每个通道里各写一遍改写，导致门控与评分错位。

### 4. 可关、可分层关

六个配置项都有默认值，写进 `.env.example`：

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `RETRIEVAL_QUERY_REWRITE_ENABLED` | `true` | 总开关；关掉后返回未包装的旧对象 |
| `RETRIEVAL_QUERY_REWRITE_NUMBERS` | `true` | 中文数字归一化 |
| `RETRIEVAL_QUERY_REWRITE_SYNONYMS` | `true` | 同义词扩展 |
| `RETRIEVAL_QUERY_REWRITE_SECTIONS` | `true` | 章节标题注入 |
| `RETRIEVAL_QUERY_REWRITE_MAX_SECTION_HINTS` | `1` | 章节提示上限（口径上限 2） |
| `RETRIEVAL_QUERY_REWRITE_MAX_EXPANSIONS` | `8` | 追加词上限（不含原话） |

总开关关掉时 `build_policy_search()` 返回的仍是原来的 `PolicySearchService` 或
`HybridPolicySearch`，不是「行为等价的包装器」——这样「关掉」这件事本身可以被类型断言钉住。

## 证据

旧金标 17 条，同一语料、同一 `today`、同一门槛，只切换 `--rewrite`：

| 指标 | 改写关 | 改写开 | 变化 |
|---|---|---|---|
| recall@1 | 0.7941 | 0.9706 | +0.1765 |
| recall@3 | 0.9118 | 0.9706 | +0.0588 |
| recall@5 | 0.9706 | 0.9706 | 0 |
| MRR | 0.8745 | 1.0000 | +0.1255 |
| nDCG@5 | 0.8824 | 0.9772 | +0.0948 |
| intent_accuracy | 1.0000 | 1.0000 | 0 |
| stale_hits | 0 | 0 | 0 |
| cross_tenant_hits | 0 | 0 | 0 |
| dense_trigger_rate（gated） | 0.29 | 0.12 | −0.17 |

逐条看四个已知缺陷：

- `refund-scope`（哪些订单可以退款）：第 5 名 → 第 1 名，MRR 0.20 → 1.00；
- `delay-handling`（严重延迟怎么处理）：期望章节第 3 名 → 第 1 名，MRR 0.33 → 1.00；
- `ticket-priority`（什么情况下创建最高优先级工单）：第 3 名 → 第 1 名，MRR 0.33 → 1.00；
- `refund-window`（签收后多少天内退款）：名次不变。该用例有两个相关块（同一章节被切成两段），
  首个命中本来就正确，第二块仍在 top-5 之外，所以 `recall@1` 与 `recall@5` 都是 0.5；这是切块与
  语料问题，改写不解决，**不把它算作改写收益**。

`delay-handling` 与 `ticket-priority` 到第 1 名，靠的是把章节标题作为追加词送进 BM25，
而不是给章节加权：排序逻辑一行没改，门槛也没有为了这两条调过。`refund-window` 留在原地，
说明「有相关块没进候选」这类覆盖问题不在改写能解决的范围内。

通道对比（hashing 稠密替身，同一批 17 条）：

| 通道 | 改写关 recall@1 / MRR | 改写开 recall@1 / MRR |
|---|---|---|
| bm25 | 0.79 / 0.87 | 0.97 / 1.00 |
| dense | 0.74 / 0.81 | 0.76 / 0.88 |
| hybrid | 0.85 / 0.90 | 0.97 / 1.00 |
| gated | 0.85 / 0.90 | 0.97 / 1.00 |

改写后 gated 的稠密触发率从 0.29 降到 0.12：稀疏通道更能自己找到词，门控就不必再叫稠密通道。
hybrid 与 bm25 打平，说明在这份小语料上稠密通道没有额外贡献，而不是改写把稠密压坏了。
`dense` 也涨了（0.74 → 0.76），说明改写对两路召回都有正向作用，不是只对 BM25 有效。

## 后果

- 旧金标 17 条的门槛（`recall@1 ≥ 0.7`、`recall@3 ≥ 0.85`、`recall@5 ≥ 0.9`、
  `mrr ≥ 0.8`、`nDCG@5 ≥ 0.8`、`stale/cross = 0`）全部通过，且五项质量指标没有一项下降。
- 新增的 200 条金标上，改写整体是正收益，但不是每一项都不降：`gold_dev` 的 `recall@1`
  0.87 → 0.905、MRR 0.9433 → 0.9658、nDCG@5 0.9303 → 0.9450，而 `recall@3` 从 0.96 降到 0.95
  （100 条分母上正好少 1 条命中，`g-refund-confirmation-05` 从 1.0 掉到 0.0）；`gold_test`
  的 `recall@1` 0.755 → 0.81、MRR 0.8733 → 0.9067、nDCG@5 0.8743 → 0.8976，`recall@3/@5`
  持平在 0.94。800 条银标只报覆盖（`silver_test` 的 `recall@1` 0.7312 → 0.7300，400 条分母上
  净少 0.5 条命中，46 条用例有升有降后相抵），不设通过/失败判定。分层口径见
  [ADR-027](ADR-027-分层检索评测.md)。
- 真实运行路径（`app/agent/support_agent.py` 与 `app/services/runtime.py` 的
  `build_policy_search()`）默认走改写；关掉总开关即可逐位回到旧路径。
- `evals/retrieval_metrics.py` 新增 `--rewrite {on,off}`（默认 `on`），
  `--json` 增加逐条 `retrieved` / `recall` / `mrr` / `ndcg` / `dense_decision`，
  改写前后的对比可以落到单个用例，不必只比总分。
- 章节标题表是**手写的 15 条**，有测试对种子语料的 ACTIVE 章节做漂移检查：
  改了政策标题却没改这张表，测试会红。同义词表同理，只收录能在政策正文里找到落点的组。
  选章节前还有一道**标题存在守卫**：查询里已经出现任一 ACTIVE 标题时不追加提示，
  避免把用户已经点名的章节又推一遍、挤掉真正的相邻章节。
- 新增测试 `tests/test_query_rewrite.py` 与 `tests/test_retrieval_set.py`：数字（含全角、
  月份、周）、词的边界（`一般`/`一致` 不误转）、订单标识不动、追加不替换、预算上限、
  5W1H、章节兜底、空白查询、包装器透传 `last_dense_decision`、总开关回退，以及
  1k 数据集的形状、分层拆分、模板网格、外部问法哈希与「只借措辞」边界。
- **诚实边界**：这 17 条样本很小，`dense_trigger_rate` 只代表这份语料；稠密通道用的是
  hashing 替身而非真实 embedding；改写规则是人工词表，覆盖率受词表限制，未收录的说法不会自动扩展。
  数字归一化只处理中文数字与全角数字，半角阿拉伯数字加中文量词（如 `40块`）原样保留，不在本次范围内。
  分层评测集（[ADR-027](ADR-027-分层检索评测.md)）给出了 200 条金标与 800 条银标的
  同口径对比，但它仍然只覆盖随包的 4 份政策，不能外推成「改写普遍有效」。

## 备选方案

- **用模型改写查询**：能覆盖词表外的说法，但引入网络依赖、非确定性、延迟与成本，
  而且会让「离线评测数字可复现」这条基线失效。本项目当前的目标是把确定性部分做扎实，
  模型改写留给有真实评测集之后再讨论。
- **替换而不是追加**（`三十天` → `30天`）：会在 `七天无理由退货` 这类章节标题上丢字面匹配，
  且用户原话被永久改掉，无法审计。
- **把改写放进 `PolicySearchService` / `HybridPolicySearch` 内部**：两条通道会各改一次，
  门控看到的覆盖率、稀疏看到的词、重排看到的句子可能不是同一句；包在最外层只有一处入口。
- **无限追加同义词与章节**：查询会被自己的扩展词淹没，BM25 的长度归一化反过来惩罚长查询。
  因此章节最多 2 个、追加词最多 8 个，数字优先、章节次之、同义词最后。
- **按评测集调章节权重**：能让 `delay-handling` / `ticket-priority` 立刻到第 1 名，
  但那是拟合 17 条样本。本次只做「把正确的词加进去」，排序仍交给 BM25。
