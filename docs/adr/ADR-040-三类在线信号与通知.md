# ADR-040：三类在线信号与通知——阈值是数据、出口只搬运、判定不调模型

- 状态：已接受（随 R11 实现 T2–T5 落盘；本 ADR 由 R11 文档轮补写，2026-11-01 提交审查，**经独立 reviewer 第 2 轮复验通过**）
- 日期：2026-11-01
- 关联：ADR-011（转人工是一等公民——信号 A 的分子就落在它的 `NO_EVIDENCE` 上）、ADR-024（三级模型门控——本 ADR 的「零模型调用」沿用它那条「问了也买不到东西就不问」的线）、ADR-036（审批金额分层——「阈值只回答要不要」，YAML + loader 的形状先例）、ADR-038（分数种类与分尺度阈值——「分数阈值 ≠ 比率阈值」的消歧在此沿用）、ADR-039（单轮反问——`counter_question.yaml` 同形 loader）、`app/core/online_signals.yaml`（唯一判定口径）、`docs/下一步规划.md` §0.2 的 R11 行

## 背景

R11 之前，本仓对「线上表现变坏」这件事既有读数、又没有判定。

**有埋点、有比率，就是没有「一条线」。** `app/api/v1/traces.py::trace_metrics` 现算 span 健康度
（`error_rate` / `p95_latency_ms`），返回的是数字；`app/api/v1/handoffs.py::handoff_metrics` 逐字调
`HandoffMetrics.collect()`（`app/services/handoff.py::HandoffMetrics`）产出 `handoff_rate` 等读数。
两条链路里都不存在「异常」二字——数字要靠人自己盯着看。

**没有告警留痕，也没有「复核」这个动作。** `audit_events` 里只有业务动作行（如 `handoff.escalate`，
`app/services/handoff.py` 内的 `AuditRepository.record` 调用点），没有任何信号类动作；误报率因此无处可读
——不是没算，是没有「被复核过」这件事可算。

**基线文件是离线读数，在线链路一处都没读它。** `evals/baseline/business.json` 有 46 条读数，
`_meta.recorded_at = "2026-10-28T12:53:08"`，其中 `handoff_metrics.handoff_rate = 0.3654`
（52 个会话 / 19 次转人工）；`app/**` 对 `evals` 零真实 import。

这三件事凑起来，让「加一个告警」不是加一个 if，而是加一条有形状的数据链。三条既有约束先把形状钉死了：

1. **阈值不得写死代码**（台账原文「各由阈值（从基线文件读，不写死代码）」），但 **app 不得读 evals**
   ——`docs/architecture-guard.yaml` 的 tiers 是 `core`/`observability`/`db`=0、`models`/`schemas`=1、
   `repositories`/`retrieval`/`sql`=2、`tools`/`agent`/`channels`=3、`services`=4、`api`=5，`evals` 不在
   分层清单里，`app/**` 读 `evals/**` 是跨树依赖。两条同时成立，只剩一种落法：**YAML 存抄本 + 测试兜一致性**。
2. **在线信号只出动作建议，不许自动改提示词或阈值**（台账红线逐字）。出口必须只读，文本必须是静态字段，
   不是模型生成、也不是运行时拼接业务数据。
3. **采集与判定零模型调用**（口径 §6-2 硬条款，依据 §14.1 裁定表「用确定性信号替代，不另起一个 agent……
   多调一次模型判答案既不必要也不可复现」）。

另有两处同名概念必须先消歧，否则整条链会接错：**`Notification`（`app/models/memory.py::Notification`）
是客户可见实体**（docstring：「A proactive proposal waiting for the customer's yes or no」），运维告警禁止
复用它；**`escalation_no_evidence_score`（`app/core/config.py::Settings` 的字段，默认 5.0）是单条证据的分数
阈值**，与信号 A 的 0..1 比率线是两个数、不得互相顶替（ADR-038 那条线）。

## 决策

### 1. 三个信号各有唯一真值来源，判定只在出口层做

采集层 `app/services/signal_readings.py::collect_readings` 只读库计数、产出 `SignalReading`
（`signal_id` / `window_minutes` / `numerator` / `denominator` / `metric_value`），**不做任何判定**；
判定（`metric_value > threshold`）、HTTP、审计、误报率全在出口层与服务层。

- 信号 A `no_evidence_rate`：分子 = `handoff_events.reason == NO_EVIDENCE` 的行数；分母 =
  `ConversationMessage.role == "user"` 且 `intent ∈ {"POLICY_QA", "SELF_ANALYTICS"}` 的消息数
  （经 `conversation_id` JOIN `conversations` 收租户）。意图集合在
  `app/services/signal_readings.py::NO_EVIDENCE_INTENTS` 抄一份，它与 `app/agent/escalation.yaml` 的
  `no_evidence.intents` 是否一致，由 `tests/test_signal_readings.py` 现读该 YAML 比对钉死。
- 信号 B `handoff_rate`：**逐字复用** `HandoffMetrics.collect()` 的 `handoff_conversations` /
  `conversations` / `handoff_rate`，不另立第二套分子分母。
- 信号 C `tool_failure_rate`：分子 = `status == FAILED`；分母 = 已落定状态
  `{SENT, RECONCILED, FAILED, CANCELLED, UNKNOWN}`（排除 `PENDING`——尚未执行，不计入任何一侧）。
  该表无 `tenant_id` 列，租户边界**必须**经 `ToolExecution.task_id → Task.tenant_id` JOIN 收。

先否决的两条备选：从 `retrieve` span 的 `attributes` 重算 A（JSON 列跨方言不可靠，且本仓纪律是从不解析
`attributes`）；用会话数做 A 的分母（A 的分子是事件级，分子分母不同级、不可比）。

### 2. 阈值是 YAML 数据 + 封闭键 loader，不是环境变量

`app/core/online_signals.yaml` + `app/core/online_signals.py`。五处同形先例共享 `@lru_cache(maxsize=1)`
缓存形态（`approval_tiers` / `intent_catalog` / `escalation` / `counter_question` / `refund_reason_rules`）；
封闭键校验的形态则照 `intent_catalog::_reject_unknown`（`escalation` 只有缓存形态，读键用 `.get` 带默认值、
未知键静默忽略，**不**是封闭键先例）。

**它没有环境变量、没有 `Settings` 字段、也不进 `.env.example`。** 理由与「阈值不写死在代码里」同源：
阈值是**有结构的多行数据**（每行六键 + 一个 `baseline` 子块），不是一个标量开关；摊成 `Settings` 字段会得到
一堆「各管一半」的碎片面。**改 YAML 后重启进程生效，不承诺热加载**——`get_online_signals` 每进程缓存一份，
与 `approval-tiering.md` §7 同措辞。

封闭键的四处：顶层 `{version, signals}`、信号行六键、`baseline` 五键，外加 `signal_id` 的三值封闭词表
且互不重复、恰三行。数值约束同样在加载期：`threshold: float ∈ (0, 1]`、`realert_minutes: int > 0`。
`threshold` 与 `realert_minutes` 的读取函数都先挡 `bool`——`bool` 是 `int` 的子类，不挡的话
`threshold: true` 会被当成 `1.0` 放行。

### 3. YAML 里存的是抄本，不是引用

`calibrated: true` 的行（今天只有信号 B）必须四件齐：源文件路径、读数键、抄的值、抄录日期；
`calibrated: false` 的行（A、C）定死字面 `"none"` / `"none"` / `null`，且 `note` 必含「未经基线校准」。
两个方向由 loader 双向互锁校验，**任何违反契约的行都是错误，不是跳过的行**——悄悄跳一行会让运行期读到
一份没人评审过的表。

与基线的一致性由 `tests/test_online_signals.py` 现读 `evals/baseline/business.json` 断言
`copied_value == readings[reading_key]`，**fail-closed**：文件缺失 / 键缺失 / 值不符一律失败、不得跳过。
`tests/` 跨树读取不受 tiers 管制，这条链因此成立。

现读数（三行逐字）：`no_evidence_rate` 阈值 `0.20`、`calibrated: false`；`handoff_rate` 阈值 `0.55`、
`calibrated: true`、抄本 `0.3654`；`tool_failure_rate` 阈值 `0.10`、`calibrated: false`；三行
`realert_minutes` 都是 `15`。B 的 0.55 **高于**基线 0.3654，属向上取的**判断值**，不是基线值——YAML 的
`note` 与文档都这样写，不把它说成「基线校准出来的」。

### 4. 出口是一个只读端点 + 一个复核写入端点，鉴权照 `_require_staff` 形

`app/api/v1/monitor.py`，`APIRouter(prefix="/api/v1/monitor", tags=["monitor"])`，两个 operation：

- `GET /api/v1/monitor/signals`：`window_minutes: int | None = Query(default=None, ge=1, le=60*24*90)`
  （常量 `MAX_WINDOW_MINUTES`）。三行固定顺序，每行九字段 `signal_id` / `window_minutes` / `numerator` /
  `denominator` / `metric_value` / `threshold` / `breached` / `calibrated` / `action_suggestion`，
  外加顶层 `false_positive_rate`。`breached` 用**严格大于**判定，等于阈值不算触警。
- `POST /api/v1/monitor/reviews`：请求体仅三字段 `signal_id` / `conclusion` / `window_minutes`；
  响应是**受理回执**，逐字回显这三要素，不返回信号表、**不重算误报率**（避免第二份读数路径）。

鉴权用 **`_require_staff` 形**——放行 `admin` 或 `("approver", "support")`，失败抛
`ForbiddenError("Staff role required.")`；**不用** `_require_seat`（只放 `support`）。理由：这两个端点是
**运维健康读数**，与 `traces` 的 `/metrics` 同类；`handoffs` 的 seat 门守的是接案工作队列与案卷，与本条无关。
`_require_staff` 在 `app/api/v1/monitor.py` 里是模块私有副本，不跨模块 import 私有符号，两份副本的角色集合
由一条测试钉死相等。

响应模型在 `app/schemas/monitor.py`（tier 1），路由注册只在 `app/main.py` 加一行 `include_router`（现 13 行），
**不新建 `app/api/v1/` 下的路由汇总文件 `router.py`**。

### 5. 触警留痕是幂等去重，不是「每窗口恰一条」

`monitor.signal.breached`（`resource_type = monitor_signal`、`resource_id = signal_id`、
`outcome = "SUCCESS"`——「触警」语义由动作名承担，不发明新 outcome 字面）。去重判定
`app/services/signal_audit.py::_already_breached` 只用具体列，两个条件化成一次计数查询：存在
`created_at >=` 本次读取窗口起点的行，**或**距最近一条不足 `realert_minutes`（YAML 行参数，初值 15）
——取两个截止时刻中更早的那个做下界。

**为什么不是「每窗口恰一条」**：端点是现算只读的，看板一次刷新就是 N 次读取，「每窗口恰一条」会在每个窗口
重复刷告警；幂等去重既防刷屏也不丢新发事件。`record_breach` 返回「本次是否真的写了」，API 层只在真写了时
`session.commit()`——「只 flush 不 commit」是 `AuditRepository.record` 的既有契约，事务边界归 API 层。

### 6. 复核结论是封闭词表，误报率三态且可分

`monitor.signal.reviewed`：`outcome` 即复核结论，`app/services/signal_audit.py::REVIEW_OUTCOMES` 这一个
`frozenset` 是**唯一产出点**（`FALSE_POSITIVE` / `CONFIRMED`）。`record_review` 先校验 `conclusion` 落在词表内、
再校验 `signal_id` 是阈值表里的信号（用 `get_online_signals()` 这一唯一词表来源，不另立字面清单；请求体里的
未知 `signal_id` 解析出的 `KeyError` 收敛成 `ValidationAppError`（HTTP 422），不冒泡成 500）。校验先于写入：
非法输入**一行都不写**。

**复核不绑定具体某条 breached 行，因此没有幂等去重**：每次复核各留一行。被复核的对象是「某信号在某窗口
breach 过」这一判定。

误报率 `app/services/signal_audit.py::false_positive_rate` = `count(reviewed 且 outcome=FALSE_POSITIVE) ÷
count(reviewed)`，同租户、同窗口，分子分母都是具体列等值比较。三态：

| 已复核数 | 读数 | 语义 |
|---|---|---|
| 0 | `null` | 没复核过 |
| >0 且全 `CONFIRMED` | `0.0` | 复核过、全对 |
| >0 且有 `FALSE_POSITIVE` | `round(fp / reviewed, 4)` | 复核过、有误报 |

`null` 不落 `0.0`：「没复核过」与「复核过且全对」是两件事，合并会把「没人看」显示成「一切正常」。

### 7. `detail` 键集封闭，分类只走具体列

breached 行 `detail` 恰四键 `{signal_id, window_minutes, metric_value, threshold}`；reviewed 行恰两键
`{signal_id, window_minutes}`。禁入客户文案、单号、原始 span / 属性值——`detail` 是 JSON 列且台账他人可读，
纪律同「只记计数，不记单号」。

**读侧同样不解析 JSON**：去重与误报率的分子分母都按 `action` / `outcome` / `resource_type` / `resource_id` /
`tenant_id` / `created_at` 具体列等值比较。这与 `traces.py`「从不解析 attributes」同向，也避开跨 SQL 方言的
JSON 解析差异。

### 8. 零分母在出口层映射成 `null`，既有端点的 `0.0` 不动（裁定 11）

信号 B 的采集层**逐字**透传 `HandoffMetrics.collect()` 的读数；零分母时那个读数是 `0.0`
（`app/services/handoff.py::HandoffMetrics` 的 `_rate()` 零分母返回 0.0），采集层**不改它**。`null` 的映射
只在出口层发生：`app/api/v1/monitor.py::_exit_metric` 在 `reading.denominator <= 0` 时返回 `None`，
`breached` 随之为 `false`。

**这是出口层映射，不是第二份事实源。** 信号 B 的读数仍逐字取自 `collect()`，`_rate()` 一行不改；既有
`GET /api/v1/handoffs/metrics` 的 `handoff_rate` 仍是 `0.0`。两层各有断言：monitor 信号行为 `null`、既有端点
为 `0.0`，**且不得互相断言等价**——`null` 的语义是「本出口不输出伪读数」，`0.0` 是既有端点的历史字面。
信号 A / C 的零分母在采集层 `_ratio` 已经输出 `None`，出口层因此不需要再动。

### 9. 红线与边界的机器可判形式

- `action_suggestion` **逐字**等于 YAML 值（字节相等断言），不生成、不拼接、不调模型。
- 零模型调用：monitor 端点调用链测试里放模型桩，断言不被触发。
- 六份 YAML 字节不变（`intents` / `escalation` / `approval_tiers` / `counter_question` /
  `refund_reason_rules` / `online_signals`）；`app/**` 内不存在任何写配置 / 写 YAML 的路径。
- 不新增迁移、表、列、依赖（`alembic/versions/` 维持单 head）；不改 `web/**`；不复用 `Notification`；
  不做推送；不写两条动作名与 `monitor_signal` 之外的新审计动作 / 资源类型。

## 后果

**正面。**
「线上变坏」第一次有了可判定的形态：三条比率各有阈值、各有静态动作建议，触警留痕可查、可复核，误报率
可单独读。阈值与动作文本第一次落成数据而不是代码，补校准只改 YAML、不改代码。整条链**零模型调用**
——采集是 SQL 计数、判定是数字比较，读数可复现、不花钱、不受模型版本漂移影响。出口的 `null` 让
「分母为零」与「比率真的是零」第一次分了开来。

**代价（如实登记，不得软化）。**

1. **A / C 的阈值未经基线校准。** `0.20` / `0.10` 是占位初值，基线文件里**没有**这两项读数（实核
   `evals/baseline/business.json`：只有 `handoff_metrics.*` 等业务读数，无无依据率、无工具失败率）。后果是
   这两条线可能长期不触发，也可能天天误触发，而两种情形都不会有任何东西告诉你「阈值该调」。补校准只改
   YAML（`calibrated: false → true` + 抄本四项填充），但「调成多少」要等基线轮给出读数。
2. **C 把 `UNKNOWN` 计入分母、不计入分子 ⇒ 失败率保守偏低。** 「外部结果未知」既不能声称失败、也不能当它
   不存在，两害相权取偏低——代价是真出问题时告警来得更晚。
3. **C 读失败台账、不读熔断实时态 ⇒ 告警滞后至少一个读取节奏。** 熔断器状态在内存且每进程一份
   （`app/tools/executor.py::CircuitBreaker` 的 docstring：「not treated as a correctness mechanism」），
   实时态根本不可读、重启即清零；台账才是可复现读数。
4. **误报率不绑定具体告警行。** 复核的是「窗口 × 信号」这一判定，不是某条 breached 行；要绑定须新增表 / 列
   ——那是本轮明令不做的级联。因此回答不了「这一条告警被误报过几次」。
5. **两个端点而不是一个。** 裁定 3 字面只给「一个只读端点」，但 reviewed 行必须有生产者——没有写入口，
   误报率永远是 `null`，「误报率单独可读」这条验收标准就不成立。代价是 OpenAPI 多 1 path + 1 operation、
   多一个写端点带来的鉴权面（按 `_require_staff` 形处理，不放宽）。
6. **`_require_staff` 两份私有副本**（`app/api/v1/traces.py` 一份、`app/api/v1/monitor.py` 一份）。不跨模块
   import 私有符号是本仓既有形态，代价是角色集合可能各改各的——只靠测试钉住相等。
7. **抄本可能与基线漂。** 阈值表里的 `0.3654` 是 2026-10-28 的时点快照；基线文件重跑后数字会变，而 YAML
   不会自动跟着变。漂了只会在测试跑起来时变红，**运行期不会发现**，也没有任何日志提示。
8. **无推送 ⇒ 告警不主动到人。** 不刷新看板就没人知道触警，发现延迟取决于读取频率。这是选择不是缺陷
   （推送需要外部端点与凭据＝新增配置项，而「生产环境不因新增配置拒绝启动」是既有纪律），但代价要写在纸上。
9. **出口 `null` 与既有端点 `0.0` 并存。** 同一「零分母」事实在两个面上是两个值，消费方不得混用、不得互相
   断言等价；两层各有一条断言（决策 8）。这不是可消除的重复，是两处历史与两种语义的接缝。

**其他可观察后果。**
OpenAPI 从 48 条路径 / 51 个操作增至 **50 条路径 / 53 个操作**（实测 `create_app().openapi()`，两笔增量就是
两个 monitor operation），`openapi_paths` / `openapi_operations` 两个事实组随之漂移，`app_py_files` /
`mypy_files` / `test_py_files` / `test_collected` 同批漂移；其中「OpenAPI 里共」与「本轮收尾读数」两段是
`in_manual: true` 的 claim，改动必须与说明书 docx 同批重生成。`adr_count` 从 38 变 39（本 ADR）。
每次读取触警信号都可能写一行审计（幂等去重压低写入，但不是零），`audit_events` 行数会随看板刷新节奏增长。
误报率读数取决于人是否发起复核——端点只提供入口，不提供纪律。

## 被否决的方案

1. **把三条阈值写进 `app/core/config.py` / `Settings` / 环境变量**：阈值是六键 × 三行的结构化数据，摊成环境
   变量会得到一堆「改一半」的字段；环境面每加一项就多一条「生产环境不得因新配置拒绝启动」的风险，而
   `Settings` 面已有 89 个字段，不该再加三个语义完全不同的比率线。
2. **让 `app/**` 直读 `evals/baseline/business.json` 当阈值来源**：`evals` 不在
   `docs/architecture-guard.yaml` 的 tiers 里，`app` 读 `evals` 是跨树依赖。「从基线文件读」这条台账措辞被
   落实为**抄本 + fail-closed 一致性测试**，而不是让生产代码依赖评测目录。
3. **把 A / C 也填成抄本值、标 `calibrated: true`**：基线文件里没有这两项读数，填一个数就是伪造校准。
   `calibrated: false` + 「未经基线校准的占位初值」是诚实前提，YAML 的 `note` 与文档都必须这样写。
4. **信号 B 自己 `SELECT COUNT(handoff_events)` 另立一套分子分母**：会造出第二份「转人工率」事实源，两处
   演化必漂；且 `collect()` 的 docstring 已经定死「分母始终是窗口内的会话数，不是历史累计」。
5. **「每窗口恰一条」breached 行**：端点是现算只读的，看板刷新即多次读取，会在每个窗口重复刷告警。
6. **复用客户可见的 `Notification` 模型做运维告警**：`Notification` 是「等客户点头的主动提议」，`user_id`
   指向客户、确认即写出箱行；把运维告警塞进客户可见实体是语义污染，也是越界。
7. **做主动推送（webhook / 邮件 / IM）**：需要外部端点与凭据＝新增配置项，且推送的重试与幂等是另一条
   未审级联。告警的可观测形态定死为「端点可读 + 审计留痕可查」。
8. **用模型判断答案好坏 / 让模型生成 `action_suggestion`**：违反台账红线「只出动作建议，不许自动改提示词或
   阈值」，也违反「零模型调用」硬条款——多调一次模型判答案既不必要也不可复现。
9. **把复核绑定到具体某条 breached 行**：要绑定就得新增表 / 列 / 迁移，属本轮明令不做的级联；而「某窗口 ×
   某信号 breach 过」这个判定已经是复核的最小可判定单位。
10. **零分母直接输出 `0.0`**：把「没数据」显示成「一切正常」，是最糟的假读数。反过来「让采集层把 B 的 `0.0`
    改成 `None`」也不行——那是改 `_rate()` 与既有端点读数，会动到既有的第三条事实源；所以 `null` 只在出口层
    做映射（决策 8）。
11. **两个端点都用 `_require_seat`**：seat 门只放 `support`，守的是接案工作队列与案卷；运维健康读数与它不同类，
    会无谓地把 `admin` / `approver` 挡在门外。
12. **解析 `detail` / `attributes` JSON 来分类或统计**：JSON 列跨 SQL 方言解析不可靠，且本仓既有纪律是从不解析
    `attributes`；分类只走具体列。
13. **把 `conclusion` 做成自由字符串**：值域必须有唯一产出点，否则误报率的分子无法等值比较、也无法在文档里
    写清。
14. **复核端点顺手返回重算后的误报率**：同一读数会出现两条路径，看板与入口各读各的就会漂；误报率只由只读
    端点一处可读。

## 已知缺口

1. **A / C 的阈值未经基线校准，且基线文件里没有对应读数。** `0.20` / `0.10` 是占位初值，补校准需要先有一轮
   能产出无依据率与工具失败率读数的基线；在那之前这两条线既可能不触发也可能误触发。
2. **抄本与基线的一致性只在测试跑起来时可见。** `tests/test_online_signals.py` 是 fail-closed 的，但漂移不产生
   运行期信号、不写日志、不出告警——「阈值表里的 0.3654 还是不是今天的读数」只能靠跑测试回答。
3. **误报率不绑定具体告警行**，回答不了「这一条告警被误报过几次」；复核粒度固定在「窗口 × 信号」。
4. **无推送，告警不主动到人。** 发现延迟完全取决于看板读取频率；这是选择，但意味着「没人看＝没人知道」。
5. **信号 C 的读数滞后于熔断实时态**：C 读台账、不读内存态，熔断状态不落库、每进程一份、重启即清零，因此
   实时态不可读；告警滞后至少一个读取节奏，且 `UNKNOWN` 计入分母使失败率保守偏低。
6. **并发读取下的 breach 去重上界未定义。** `_already_breached` 是「查一次、没有就写」，期间没有行锁，
   `audit_events` 也没有针对 `(action, resource_type, resource_id, created_at)` 的唯一约束；两个并发读取可能
   各写一条。当前无并发用例、无断言，**不得写成「并发下至多一条」**。
7. **`_require_staff` 的两份私有副本没有结构性收敛点。** 只靠一条测试断言两份 `_STAFF_ROLES` 相等；如果有人
   只改一处并同时改测试，漂移不会被任何机制拦住。
8. **守卫级联只登记、不修改。** 本轮文档轮只把 `adr_count` 从 38 改到 39（六处），并把 §3.9 与 README 的接口行
   写进去；`openapi_paths` / `openapi_operations` / `app_py_files` / `mypy_files` / `test_py_files` /
   `test_collected` 的完整 re-cite 归 R12 收尾轮。三份守卫清单（`docs/fact-baseline.yaml` /
   `docs/code-anchors.yaml` / `docs/architecture-guard.yaml`）本轮一个字都没改。
9. **`docs/下一步规划.md` §0.2 的 R11 行已登记 T2–T5 落地与剩余范围（末句为「台账状态仍由证据给出，本批不将
   R11 整条标为收口」）。** 本轮按证据仍不标收口；收口标注另起一轮，只引用 T6 门禁读数与 `replay --self-check` 读数。
10. **完整门禁本轮未跑。** 本轮是文档轮：跑了三份文档守卫（`29 passed`）、`ruff check app tests scripts evals
    alembic`、以及本组四个用例文件（`108 passed`）；**未跑**的是全量 `pytest`、`evals/**` 的模型读数（按项目
    惯例由使用者侧本机模型复跑——R11 本身零模型调用，但这些读数是 R11 之外的既有门禁）、需
    `TICKETPILOT_TEST_POSTGRES_URL` / Redis 的 PG 侧用例、以及 `npm run build`。
11. **出口层的零分母映射与既有端点的 `0.0` 之间没有「同一分母」的机器校验。** 裁定 11 要求两层
    「不得互相断言等价」，反过来说也没有任何断言钉住「两层的分母是同一个分母」——B 的跨面一致性靠两边各自读
    `collect()` 这一点，而不是靠一条比较断言。
