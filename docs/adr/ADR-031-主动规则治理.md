# ADR-031：主动规则的版本、四眼审批与回滚

- 状态：Accepted
- 日期：2026-10-26
- 关联：[ADR-019](ADR-019-主动规则可编辑面.md)（规则写接口：它明写「没有双人复核、没有版本表」是当期边界）、[ADR-004](ADR-004-审批绑定.md)（四眼原则）、[ADR-014](ADR-014-客户记忆与主动授权.md)（客户先确认）

## 背景

ADR-019 把规则写面放出来了，也把两个缺口写在「后果」里：**没有双人复核**——一个人就能改
所有客户收到的话；**没有版本表与一键回滚**——审计里只有模板的 SHA-256，改错了只能对着
摘要人工打回去。这与退款写路径的四眼审批直接矛盾：一笔退款要两个人，所有客户收到的
每一句话却只要一个人。

写路径本身已经是确定性的：模板白名单、位置参数拒绝、400 字上限、失败不落半行，这些
由 `tests/test_proactive_rules.py` 的坏模板用例守住。缺的不是「挡坏格式」，而是
「挡住一个好人改错」和「改错以后能回去」。

## 决策

### 1. `PUT /rules/{event_type}` 只提交，不生效

请求体仍是 `template` / `enabled` / `cooldown_minutes`，另加可选的 `reason`；
`requires_confirmation` 仍然不可写。响应从 `200 ProactiveRuleView` 改为
`202 ProactiveRuleChangeView`，状态固定为 `PENDING`。

提交事务只写 `proactive_rule_changes`，**不碰 `proactive_rules`**。因此：

- 客户侧读不到待批内容，`emit` 继续用现行模板；
- 同一租户 + 事件类型同时只允许一条待批改动；
- 提交前仍跑原来的模板校验，坏模板在提交时就被拒绝，不会留半行。

### 2. 批准由另一名 approver 完成，提交者不能自批

`POST /rules/changes/{id}/approve` / `reject` 要求 `approver` 角色，并要求
`identity.user_id != submitted_by`。`admin` 也受同一条身份约束：管理员可以批准，
但不能批准自己提交的那一条。拒绝后改动为 `REJECTED`，规则与版本都不变。

批准时校验 `base_version == 规则当前 version`；不一致返回 `409
RULE_VERSION_CONFLICT`，不覆盖并发写入。唯一约束 `(tenant_id, pending_key)`
兜住「两个提交同时通过读检查」的竞态。

### 3. 生效写不可变版本，版本号只增

`proactive_rules.version` 从 1 开始。每次批准：

1. 规则值更新，`version += 1`；
2. 插入一条 `proactive_rule_versions` 快照（模板、启停、冷却、确认闸、提交人、
   批准人、理由、改动 id、时间）；
3. 改动状态改为 `APPROVED`，记录 `applied_version`。

版本行只插入，不更新、不删除。种子规则在第一次改动前就有版本 1（`change_id=seed`，
`submitted_by/approved_by=system`），所以改动前的通知也能找到它用的文案。

### 4. 回滚是同一条写路径

`POST /rules/{event_type}/rollback {version, reason}` 读取目标版本快照，复制成一条
`kind=ROLLBACK` 的待批改动；它不会直接写规则，也不会删掉任何历史版本。批准后规则
回到旧值，但版本号继续递增，`target_version` 留在改动记录里。

「一键」指的是一次调用就重建出旧状态，不需要运营重打模板；不是绕过审批。

### 5. 通知记录版本，但不回溯

`notifications.rule_version` 在生成时写入当时生效的版本号。通知正文已经渲染完成，
后续批准或回滚都不会改写它。给定一条通知，可以用 `rule_id + rule_version`
找到当时的快照；给定一次改动，可以看 `base_version`、`applied_version` 与
`decided_by`。

### 6. 审计记摘要与版本，不复制文案

- `proactive.rule.submit`：事件类型、改动 id、kind、base_version、字段名、
  目标启停/冷却、模板 SHA-256、理由 SHA-256、回滚目标版本；
- `proactive.rule.approve`：前后版本、提交人、批准人、模板与上一版模板的
  SHA-256、目标状态；
- `proactive.rule.reject`：改动 id、base_version、拒绝人、理由 SHA-256。

审计不保存模板或理由原文。原文只在版本快照与待批改动里，和规则读接口同级的
租户边界内可见。

### 7. 接口面

```text
PUT    /api/v1/memory/rules/{event_type}               提交改动（202）
GET    /api/v1/memory/rules/changes                    列出改动（可按 status）
GET    /api/v1/memory/rules/changes/{change_id}        读取单条改动
POST   /api/v1/memory/rules/changes/{change_id}/approve 批准（approver）
POST   /api/v1/memory/rules/changes/{change_id}/reject  拒绝（approver）
GET    /api/v1/memory/rules/{event_type}/versions       版本历史（staff）
POST   /api/v1/memory/rules/{event_type}/rollback       提交回滚（support）
```

控制台规则页在同一页面完成提交、待批列表、批准/拒绝、版本展示与回滚；
提交者的批准按钮不出现，服务端仍会再拒绝一次。

## 后果

- **旧客户端会看到 202 而不是 200。** 这是有意的契约变化：`PUT` 不再意味着
  「已生效」。控制台的 `updateProactiveRule` 已改为返回改动，并在提交后重新读取
  规则；外部调用方必须显式批准。
- **多一张规则表和一张改动表。** 迁移 `a1c7e9d4b820` 建表并为既有规则回填版本 1；
  SQLite 与 PostgreSQL 走同一份迁移。
- **版本表会增长。** 每次批准一条，属于审计资产而非缓存；本次不做归档或压缩。
- **不做规则删除。** `enabled=false` 仍是唯一停用方式；历史版本与通知的
  `rule_id` 不能悬空。
- **不做灰度。** 批准即全租户生效，与 ADR-019 的边界一致。
- **审批权限仍来自开发 Header 适配器。** `prod` 环境 fail-closed 的 OIDC 缺口
  没有因本 ADR 改变（P7）。
- **测试口径**：`tests/test_proactive_rules.py` 34 条覆盖提交/批准/拒绝/回滚/
  自批/缺角色/重复待批/版本冲突/跨租户/审计摘要/真实 HTTP 走查；坏模板用例保持
  原有九种拒绝形状。全量门禁与读数见 `docs/guide/证据索引.md`。
