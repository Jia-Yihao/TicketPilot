# ADR-028：意图评测回到真实语料——规则覆盖、代价矩阵与模型缺口

- 状态：Accepted
- 日期：2026-10-25
- 关联：[ADR-020](ADR-020-对话入口的模型缺口.md)（对话入口的模型缺口）、[ADR-026](ADR-026-查询改写.md)、[ADR-027](ADR-027-分层检索评测.md)

## 背景

旧的意图结论只有两处来源，两处都不是真实用户问法：

1. `evals/support_set.json` 的 61 条用例带 `intent` 期望值，`evals/retrieval_metrics.py`
   拿规则输出与它比较，五个通道都是 `intent_accuracy = 1.0000`。这些问法是按
   `app/agent/routing.py` 的 cue 表写的——按词表写的句子当然命中词表，所以 1.000
   只证明「用例与实现同源」；
2. `scripts/llm_gap_probe.py` 的 11 句同样是按词表外手写的探测句，不是工单采样。

缺的不是声明，而是替换这两个数字的 held-out 语料。用户要求：真实语料、可追溯来源、
人工标注、不拿外部或模型标签当 gold，并把「规则读不懂」「规则读错」「规则把可答问句
判成 UNKNOWN」分开计量。

## 决策

### 1. 两层语料，永不合并成一个准确率

| 层 | 规模 | 来源 | 用途 |
|---|---|---|---|
| `external` | 201 | ModelScope `E_commerce_Customer_Service`（Apache-2.0）的用户原话，按行号抽样 | 措辞真实性的主证据；分意图报覆盖与准确率 |
| `authored_gap` | 144（12 意图 × 12） | 项目按意图定义手写 | 补外部层缺失或过少的意图；只证明覆盖，不证明频率 |

外部源文件 `dev_clean_v2.jsonl` 不进仓库，SHA256 为
`202e45eed3e53e0f8bfcca8283e5183e3b7119bdd433a9b2158f25eaac3d427c`；进仓库的是
`evals/intent/external_phrasings.jsonl`（文本 + gold + 行号）与
`external_manifest.json`（来源 URL、许可证、源文件与样本摘要）。抽样规则拒绝 6 位以上
连续数字、邮箱、URL 与空文本，行号必须指回源文件。外部数据自带的问答/意图标签一条未用。

两层分开报告的理由：外部层没有 `SELF_ANALYTICS`，`HUMAN_HANDOFF` 只有 10 条且用词是
「店长/负责人/客服电话」而不是「转人工」，`TICKET_CREATE` 的措辞也偏少。把补位层合并
进去会制造「12 个意图都有 30 条真实样本」的假象；分开写，读者能看到哪个数字是真实
分布、哪个只是覆盖。

### 2. 人工标注与可争议的标签

`evals/intent/intent_set.json` 的 345 条 gold 全部是 `label_source = human`，标注口径写进
数据集的 `label_rule`：

- 该由哪个能力来服务，按 `app/agent/intents.yaml` 读，不按分类器的 cue 表读；
- 要动钱的是 `REFUND_REQUEST`，即使句子里带订单号；
- 要登记一个案子的是 `TICKET_CREATE`，即使起因是配送问题；
- 问规则怎么规定的是 `POLICY_QA`，即使没有政策文档覆盖——「无依据就拒绝」是预期行为；
- 能落到订单字段（付款、地址、金额）的算 `ORDER_QUERY`，问包裹在哪的算 `LOGISTICS_QUERY`；
- 问「我这一单/这次退货符不符合」的是 `REFUND_ELIGIBILITY`，问「规则一般怎么说」的是 `POLICY_QA`；
- `UNKNOWN` 是「没有任何目录能力该服务它」，不是「分类器没把握」。

`UNKNOWN` 是合法标签，且 12 个意图（含 `UNKNOWN`）在每一层都有分母；`SELF_ANALYTICS`
与 `HUMAN_HANDOFF` 的缺席/偏少原因写在 `intent_notes` 里，不用 0 填充。

### 3. 指标把「拒答」与「读错」分开

`evals/intent_metrics.py` 只调用公开入口 `classify` → `classify_support`，不复制 cue 表，
也不读目录内部状态。每层报告：

| 指标 | 定义 |
|---|---|
| `coverage` | 规则给出非 `UNKNOWN` 的比例 |
| `accuracy` | 预测等于 gold 的比例（含 gold `UNKNOWN`） |
| `answerable_accuracy` | 排除 gold `UNKNOWN` 后的正确率 |
| `unknown_matched` / `unknown_misread` | gold 为 `UNKNOWN` 时答对 / 被读成某个已知意图 |
| `false_unknown` | 可答问句被判成 `UNKNOWN`，单独计数，不算「读错」 |
| `per_intent` | 每个 gold 意图的 n / correct / unknown / wrong / coverage / accuracy |

gold 为 `UNKNOWN` 的行不把「答成 UNKNOWN」记成 wrong；它的 `coverage` 显示 `n/a`，
因为「覆盖率」对这个标签没有意义。

### 4. 误判代价：四类互斥，写意图再分方向

每个用例只落进一个桶，判定顺序是 `correct` → `false_unknown` → `write_intent_error` →
`read_intent_error`。`write_intent_error` 再拆三个方向：

| 方向 | 含义 |
|---|---|
| `extra_write` | 用户只想读，却会被建任务 |
| `missed_write` | 用户要退款/建单，却只得到一条只读回答 |
| `write_to_write` | 退款与建单互相错判 |

代价由预测意图和目录槽位推导：缺槽位算一次澄清，槽位齐全的退款/建单算一个任务，退款
任务最多算一个审批（上限，不是已批），`HUMAN_HANDOFF` 算一次移交，退款金额记
`amount_exposed_cents`——用户在这一轮提到的金额，**不是已退金额**。`false_unknown`
另报其中属于写请求的条数，因为「少一轮追问」和「少一次退款入口」不是同一种代价。

规则路径不调模型，所以每个桶的 token 都是 0；延迟单独按规则调用计时，并先用一句
预热把目录与商品索引的一次性初始化排除在读数外。两轮计时在 **5–9 ms** 之间浮动
（`external` 8.4 / 5.3 ms，`authored_gap` 5.4 / 9.2 ms），单次读数不应当成 SLA。

### 5. 模型只在缺口上被问，且只报它能表达的标签

`--model` 只对规则 `UNKNOWN` 的行调用 `IntentAgent.parse`。模型的契约只有六个标签
（`INTENT` 的 `IntentLiteral`）：`POLICY_QA` / `ORDER_QUERY` / `LOGISTICS_QUERY` /
`TICKET_CREATE` / `REFUND_REQUEST` / `UNKNOWN`。gold 落在这六个之外的缺口（如
`REFUND_STATUS`、`DELIVERY_ISSUE`、`PRODUCT_QUERY`）被跳过，记
`out_of_label_space`，**不算模型答错**；模型失败与非法标签也单独计数，不混进准确率分母。

槽位补位只报 `order_id` 与 `amount_cents`。缺口子集里 `order_id` 的分母结构性为 0：
任何带 `ORD-` 标识的句子都会被规则读成 `ORDER_QUERY`，本来就不会成为缺口。`amount_cents`
是唯一可测的槽位补位维度；任何模型编造的订单号或金额都会让 `--enforce` 退出 1。

### 6. 旧 61 条门槛原样保留

`evals/support_set.json` 的 61 条、`golden_set.json` 的 40 条、检索评测与回放口径都没有改。
旧的 `intent_accuracy` 继续作为回归门槛存在，但**主结论只引用新语料**；两套数字不合并。

## 证据

同一份 345 条语料、`AGENT_MODE=rules`、本机 SQLite，2026-10-25 实测（
`python evals/intent_metrics.py --enforce`）：

|---|---|---|---|---|---|---|---|
| `external` | 201 | 0.5473 | 0.4527 | 0.3989 | 91 | 37 | 73 |
| `authored_gap` | 144 | 0.5000 | 0.4028 | 0.3485 | 58 | 26 | 60 |

分层代价矩阵：

| 层 | 桶 | n | share | 澄清 | 任务 | 审批 | 移交 | 金额暴露 |
|---|---|---|---|---|---|---|---|---|
| `external` | correct | 91 | 0.4527 | 49 | 8 | 0 | 0 | 0.00 |
| `external` | write_intent_error | 13 | 0.0647 | 3 | 1 | 0 | 0 | 0.00 |
| `external` | read_intent_error | 24 | 0.1194 | 9 | 0 | 0 | 0 | 0.00 |
| `external` | false_unknown | 73 | 0.3632 | 0 | 0 | 0 | 0 | 0.00 |
| `authored_gap` | correct | 58 | 0.4028 | 19 | 1 | 1 | 1 | 129.00 |
| `authored_gap` | write_intent_error | 8 | 0.0556 | 5 | 0 | 0 | 0 | 129.00 |

| `authored_gap` | false_unknown | 60 | 0.4167 | 0 | 0 | 0 | 0 | 0.00 |

### 规则读错集中在哪些说法

- **退款请求被读成政策问答或订单查询**：`external` 的 20 条退款请求里有 9 条读错，
  其中 6 条变成 `POLICY_QA`、1 条变成 `ORDER_QUERY`；`authored_gap` 里
  「帮我退款 ORD-DEMO-1001 129 元」也被订单号带成了 `ORDER_QUERY`。
- **`HUMAN_HANDOFF` 几乎读不出来**：外部层 10 条里 9 条 `UNKNOWN`，剩下 1 条被读成
  `TICKET_CREATE`。用户说「店长」「负责人」「客服电话」时，cue 表只认「转人工」。
- **`DELIVERY_ISSUE` 与「物流查询」分不开**：外部层 27 条里 14 条 `UNKNOWN`、3 条被读成
  `LOGISTICS_QUERY`；用户描述破损、少件、未收到时往往不带「物流」「快递」这些词。
- **`ORDER_QUERY` 的「改地址」说法大面积落空**：外部层 16 条里 9 条 `UNKNOWN`，
  因为它们只说「改地址」「地址写错了」，没有「订单」二字。
- **产品短问句落空**：「哪个好」「什么牌子」「有活动吗」这类依赖上下文的问法，
  没有商品名时规则不给 `PRODUCT_QUERY`。
- **退款状态被读成政策问答**：外部层 15 条里 7 条读错，多为「什么时候退款」「退款进度」
  这类不带「状态」词的问法。

这些不是「规则写得差所以调词表」的清单，而是下一轮要决定「补规则、补模型、还是补澄清」
的输入；本轮只负责把它们变成可复算的数字。

### 模型缺口

规则 `UNKNOWN` 的 163 行里，只有 **91 行**的 gold 落在模型六标签契约内（外部 50、补位 41），
模型只对这 91 行被问；其余 72 行（外部 41、补位 31）是 `REFUND_STATUS` / `DELIVERY_ISSUE` /
`PRODUCT_QUERY` / `SELF_ANALYTICS` / `HUMAN_HANDOFF` 等模型表达不了的精标，记
`out_of_label_space` 并跳过，不算答错。`openai:qwen/qwen3-8b` + 本机 LM Studio，
2026-10-25 实测：

| 读数 | 值 |
|---|---|
| 调用 / 成功 / 失败 / 非法标签 | 91 / 91 / 0 / 0 |
| 粗意图正确 | 72/91 = **0.7912** |
| 其中 gold 可答（非 `UNKNOWN`）的正确率 | 47/61 = **0.7705** |
| 仍回 `UNKNOWN` | 31（其中 6 条是可答问句） |
| gold `UNKNOWN` 被读成已知意图 | 5/30（25 条判对） |
| 槽位 `order_id` 补位 | 0/0（结构性无分母） |
| 槽位 `amount_cents` 补位 | 7/8 = 0.875（漏 `ext-unknown-08`） |
| 编造 `order_id` / 金额 | 0 / 0 |
| token / 延迟 | 输入 39,142 + 输出 19,898 = **59,040**；总 880.5 s，平均 **9.68 s/次** |

分意图（correct / asked）：`REFUND_REQUEST` 19/19、`LOGISTICS_QUERY` 12/13、`POLICY_QA` 7/13、
`ORDER_QUERY` 5/10、`TICKET_CREATE` 4/6、`UNKNOWN` 25/30。模型最大的价值在退款请求
（规则在同一批缺口上一句都没读出来），最大的噪声是把 5 条真正的 `UNKNOWN` 读成已知意图；
本轮只测量，不据此扩大采纳口径——没有二次确认之前，这类错误会变成一次无依据的写动作。
`--enforce` 在本次运行中退出 0：零编造、零非法标签、零调用失败。

## 后果

- 意图质量的主结论改成引用两层新语料；旧的 `intent_accuracy = 1.000` 只保留为回归门槛，
  并在文档里注明它是「按 cue 表写的 61 条」。
- `python scripts/build_intent_set.py --check`、`python evals/intent_metrics.py --enforce`
  进入提交前检查与 CI；前者守数据集可复算，后者守四桶求和、UNKNOWN 拆分、写方向拆分、
  语料无逐字 cue、模型只在缺口被调用、模型零编造。
- `tests/test_intent_eval.py` 钉住语料形状、人工标注、脱敏、非循环、指标口径与模型桩件；
  `evals/intent_metrics.py` 的每个数字都能由命令行复现。
- 规则的短板从「没有数字」变成「有明确分母的短板」：退款请求、转人工、配送异常、
  改地址、产品短问句。后续是否改规则、改模型或改澄清策略，必须有这一层的改前/改后读数。

## 诚实边界

- 外部层只有一个公开客服语料来源，措辞偏电商售后，**不代表 TicketPilot 自己的流量分布**；
  补位层是手写覆盖证据，不是频率证据。
- 345 条 gold 由单人对照意图定义写定，**没有第二标注者与一致性系数**；标注口径已写进
  数据集，但边界句仍有争议空间。
- 外部语料只保留用户原话与行号；脱敏规则拒绝长数字串、邮箱与 URL，但不能证明源语料
  在采集时已经获得用户授权，许可证只覆盖数据本身。
- 模型只有六个标签，`REFUND_STATUS` / `REFUND_ELIGIBILITY` / `DELIVERY_ISSUE` /
  `PRODUCT_QUERY` / `HUMAN_HANDOFF` / `SELF_ANALYTICS` 的缺口无法用当前模型补位；
  这些 `out_of_label_space` 行不是模型失败，也不能算进模型准确率。
- `amount_exposed_cents` 是「用户在这一轮提到的退款金额」，不是支付、不是已退、不是损失；
  审批数是「槽位齐全的退款任务最多一个」的上限，真实链路还要过资格与人工。
- `authored_gap` 的 12×12 是为了让每个意图有非零分母，**不是为了凑一个好看的总数**；
  它的 coverage/accuracy 不能外推到真实流量。
- 规则延迟是单机、单进程、SQLite 的读数，不含网络与模型；`--model` 的延迟只对
  `openai:qwen/qwen3-8b` + 本机 LM Studio 成立，托管模型未验证。

## 备选方案

- **继续只报 61 条的 1.000**：成本最低，但面试追问「真实用户换个说法呢」时仍然答不上来；
  而且会把「按词表写用例」误当成质量证据。
- **直接把外部语料的意图标签当 gold**：外部标签体系与本项目 12 个意图不对应，且无法逐条
  核对 `intents.yaml`；照搬会把别人的标注错误变成我们的质量结论。
- **用模型标注 345 条 gold**：会得到更漂亮的覆盖率，但标签不可审计，也违反「不拿模型输出
  当 gold」的约束。
- **把两层合并报一个准确率**：补位层占 42%，会把外部层的真实短板稀释掉；分层报告才能
  同时看到「真实分布」和「覆盖缺口」。
- **在全量语料上问模型**：那样得到的是「模型换一种分类器的总分」，不是「规则读不懂时模型
  能不能捞回」；本轮只测后者。
