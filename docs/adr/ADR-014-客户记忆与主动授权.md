# ADR-014：长期记忆只存客户自己写的，主动服务必须客户点头

- 状态：Accepted
- 日期：2026-10-24

> 编号说明：本 ADR 占用 [ADR-015](ADR-015-执行器失败模型.md) 预留的 ADR-014 号位。
> 预留时拟的标题是「Memory Three-Tier Model（记忆三层）」，落地时发现三层里只有两层值得建：
> 会话内状态已在 `conversations` / `turns` 里，跨会话个性化用一张客户自持的档案表就够，
> 第三层（长期事实抽取）恰恰是本项目不做的——所以标题改成现在这个更诚实的说法，编号不变。

## 背景

客服系统很容易滑向两个方向：

1. **「记住客户」变成「画像客户」。** Agent 从对话里推断出手机号、住址、支付信息，
   写进一张 profile 表，然后下一次回复时拿来用。这在演示里很聪明，在真实项目里是
   一份没有法律依据、也没有删除路径的敏感数据副本。
2. **「主动服务」变成「主动推送」。** 订单退款到账、物流异常，系统直接给客户发消息。
   一旦规则或频控写错，它就是骚扰；而骚扰的代价由业务方承担，不由写规则的人承担。

T5 要同时给出这两件事的边界，并且边界要能被测试卡住。

## 决策

### 1. 记忆只有客户自己写的 PUT 这一条写路径

`app/services/memory.py` 的 `MemoryService` 暴露 `get / update / delete / export` 四个动作，
`update` 是唯一写路径，~~而 `app/agent/` 里没有任何一处会调用它。~~
**后半句已由 [ADR-018](ADR-018-记忆进答案.md) 改写（2026-10-24，T9）**：
Agent 现在会读档案，但不走 `MemoryService`——`app/agent/personalization.py` 用
`select(具体列)` 只取 `preferred_name / preferences`，不实例化 ORM 实体、不给空客户建行、
也不写 `memory.read` 审计（本 ADR「后果」段那条「每轮多一行审计」正是绕开它的原因）。
「写路径只有客户自己的 `PUT`」这半句没变，`tests/test_personalization.py` 有用例守住。

`CustomerProfile`（`app/models/memory.py`）的列就是白名单：

| 列 | 允许内容 | 约束 |
| --- | --- | --- |
| `preferred_name` | 称呼 | ≤40 字，命中 PII 直接拒绝 |
| `locale` | 语言 | 正则 `^[A-Za-z]{2,3}(-[A-Za-z0-9]{2,8})?$` |
| `preferences` | `contact_window` / `tone` / `product_interests` | 其余键 `422`；tone 只能是 `concise`/`detailed` |
| `history_summary` | 客户自己写的历史摘要 | ≤500 字，入库前 `redact()` |
| `proactive_opt_in` | 是否接受主动服务 | 默认 `False` |
| `muted_event_types` | 退订的事件类型 | 只能是已知事件 |
| `max_notifications_per_day` | 频控上限 | 1–20，默认 3 |

表里没有手机、地址、支付、证件任何一列——不是「我们不会存」，是「存不下」。

`PUT /api/v1/memory` 用 `model_dump(exclude_unset=True)`：没发的字段不动，
所以这是一个可部分提交的更新，不是覆盖式表单。

### 2. 拒绝与脱敏是两种策略，取决于字段能不能合法含数字

- `preferred_name`、`contact_window`、`product_interests`：`redact()` 后发现内容被改过
  就 `422` 拒绝，并把原因说清楚（「looks like personal contact or payment data and is not stored」）。
  这些字段没有合法理由携带手机号或卡号，被改过就意味着客户在填错的字段。
- `history_summary`：客户很可能合理地说「上次留的手机 13800138000 已联系」，
  所以这里**掩码而不是拒绝**——入库的副本永远不含原值。
  `profile_view()` 读出时再 `redact()` 一次，所以即便历史数据里有明文也不会回显。

审计（`memory.read/update/delete/export`）只记录**动过哪些字段名**，不记录字段值。

### 3. 主动服务是一条只有客户能打开的门

链路固定为：事件 → 租户规则 → 通知 → **客户确认** → Outbox。

`ProactiveService.emit()` 按顺序做闸门检查，任何一步不过就写一条
`proactive.suppressed` 审计并返回 `SUPPRESSED` + 原因码：

| 顺序 | 原因码 | 判据 |
| --- | --- | --- |
| 1 | `NO_RULE` | 该租户没有这个事件类型的启用规则 |
| 2 | `NO_CONSENT` | 客户没有 `proactive_opt_in` |
| 3 | `UNSUBSCRIBED` | 该事件类型在 `muted_event_types` 里 |
| 4 | `DUPLICATE` | `(tenant, user, event_type, event_key)` 已存在（另有唯一约束兜底） |
| 5 | `COOLDOWN` | 同事件类型在 `cooldown_minutes` 内已发过（含已取消的） |
| 6 | `FREQUENCY_CAP` | 24 小时内活跃通知数 ≥ `max_notifications_per_day` |
| 7 | `TEMPLATE_CONTEXT_MISSING` | 模板占位符在 context 白名单里取不到 |

模板渲染只吃白名单字段（`order_id`/`ticket_no`/`amount`/`summary`/`status`/`product`），
值经 `redact()`，缺字段用空串而不是抛异常（`_SafeContext`），正文截断到 500 字。
`event_key` 本身也过 PII 检查：它是幂等键，不是数据存放处。

### 4. 确认就是那一笔事务

`requires_confirmation=True` 的规则产出 `PENDING_CONFIRMATION`，此时**没有**任何出站消息。
客户 `POST /api/v1/memory/notifications/{id}/confirm` 才在同一次提交里：

```text
status -> CONFIRMED, confirmed_at = now, OutboxService.enqueue(dedupe_key = proactive:{id})
```

于是 `CONFIRMED` 不可能没有对应的排队消息，重复确认因为 `dedupe_key` 唯一而只会有一条队列行。
取消（`CANCELLED`）是不可逆的：取消后再确认返回 `409 NOTIFICATION_CANCELLED`。

### 5. 删除是彻底的

`MemoryService.delete()` 删 profile、删该客户全部 `notifications`，并把
`event_type='proactive.confirmed'` 且仍在 `PENDING/PROCESSING` 的 Outbox 行置为 `CANCELLED`
（已在途的消息由 worker 看到 `CANCELLED` 而不投递）。导出（`GET /memory/export`）
只返回视图与状态计数，并带 `redacted: true`。

### 6. 角色边界

`GET/PUT/DELETE /memory`、`/export`、`/notifications*` 只能操作 `identity` 自己的行
（跨租户、跨用户一律 `404`，不泄露存在性）。`POST /memory/events` 与 `GET /memory/rules`
要求 `support` 角色——业务方报告事实，客户决定是否被打扰。
T10 之后 `PUT /memory/rules/{event_type}` 同样要求 `support`（`admin` 因 `has_role` 自动通过），
但它的边界是**租户级**而不是客户级：坐席改的是本租户的规则，碰不到别的租户的行
（跨租户既看不见也改不到，由用例断言）。

## 后果

- 记忆里有法律依据的记录只有一种：客户自己写的。`tests/test_memory.py` 里
  PII 拒绝、掩码、部分更新、跨用户 404、删除后队列表状态都有断言。
- 主动通知不会因为「规则写得宽」而变成群发：同意、退订、频控、冷却、幂等五道闸门
  都有独立原因码，压掉了什么一眼可见。
- 代价与边界，如实记下：
  - ~~**记忆目前只被存与查，没有注入 Agent 回复。** 这是有意的：注入会让回复依赖
    一张客户可随时改写的表，而回复口径需要重新评测。作为下一步（见 `docs/下一步规划.md`）。~~
    **已由 [ADR-018](ADR-018-记忆进答案.md) 收口（2026-10-24，T9）**：
    当年的顾虑没有被推翻，而是被收窄——回复只接受**四种可枚举、可断言、可关掉**的效果
    （称呼、卡片重排、按简洁偏好裁追问、把目录里认识的兴趣转成一条追问），全部是模板或
    形状变化，不吃客户原文；`MEMORY_PERSONALIZATION_ENABLED` 默认开、关掉后回复逐字回到
    注入之前。「回复口径需要重新评测」这条代价的如实版本是：**种子不建档案，所以 101 条评测与
    回放 diff 逐字不变可以断言；但一个客户一旦有了档案，他此前的历史 trace 就不再逐字可回放。**
  - ~~`NotificationStatus.SENT` 尚未回写。Outbox worker 投递成功后不会回调通知表，
    所以确认之后的「是否真的送达」在通知行里看不出来，要看 Outbox。~~
    **已由 [ADR-017](ADR-017-主动出站接缝.md) 解决（2026-10-24，T7-4）**：
    `proactive.confirmed` 有了消费者，只有传输写成功才回写 `SENT`；默认 `none` 传输仍拒绝发送，
    此时通知停在 `CONFIRMED`、原因码写在队列行的 `last_error` 里。
  - ~~规则是种子数据（`seed_proactive_rules`，demo 租户三条），
    没有规则编辑 API——改模板要走数据库或后续的管理面。~~
    **已由 [ADR-019](ADR-019-主动规则可编辑面.md) 收口（2026-10-24，T10）**：
    `PUT /api/v1/memory/rules/{event_type}` 按 `(tenant, event_type)` upsert，坐席可改
    `template` / `enabled` / `cooldown_minutes` 三项，控制台多了第 10 页。当年"改模板要走数据库"
    的顾虑没有被推翻，而是被换成一条更强的约束：**坏模板现在不许存**——引用白名单外的键会让这条
    规则永远被 `TEMPLATE_CONTEXT_MISSING` 静默抑制，`{}` 会让 `emit()` 抛 `ValueError` 变成一次 500，
    两种都在写入时 422 拒绝并点名出错的字段。三条纪律没变：`requires_confirmation` 不可写（新规则
    恒为 `True`，它是本 ADR「决策 3」那条同意闸的实现位），事件类型仍是代码里的 enum 不能从界面新增，
    审计只存 `template_sha256` 不存文案。**没有的是双人复核**——审批那一层有（ADR-004），
    规则文案这一层没有，一个人就能改所有客户收到的话；这条差异写在 ADR-019 的后果段里，
    文档里不许把它写成"配置有复核"。
  - 频控按「24 小时滚动窗口内的活跃通知」计算，不是自然日；`max_notifications_per_day`
    这个名字描述的是客户理解的语义，实现是滑动窗口。
  - ~~通知只落到 Outbox 队列，没有真实出站渠道：与 ADR-013 的「sink 是注入的」同一条约定。
    渠道侧（ADR-016）已有渲染矩阵，但把通知投递接到邮件/IM 尚未接线。~~
    **接线状态见 [ADR-017](ADR-017-主动出站接缝.md)**：出站复用 ADR-016 的渲染矩阵，
    去向由服务端三段拼出。「sink 是注入的」这条约定没变——注入的是 `OutboundTransport`，
    而本仓库只提供拒绝发送与写本地文件两种。

## 备选方案

- **让 Agent 自动抽取记忆**：演示效果最好，但它会写、会改写，而写错一次的代价由客户承担；
  本项目选择只允许客户自己写。
- **事件直接推送、给客户「取消订阅」的入口**：把同意做成默认开（opt-out）。
  这需要法务与合规口径支撑，本项目没有，所以做成 opt-in。
- **用 profile 表做个性化回复**：省一步，但个性化与「不存 PII」会互相拉扯——
  一旦回复依赖画像，画像就会有人想加字段。
  **[ADR-018](ADR-018-记忆进答案.md) 采用的正是这一条，但把拉扯的一侧钉死了**：
  影响面收在一个纯函数里、只吃枚举与目录规范名、字段白名单不因「想多个性化一点」而扩张。
- **Redis 计数器做频控**：更快，但频控与通知行会分叉；数据库里一条查询就能算清楚，
  本项目没有理由为它再加一个存储。
