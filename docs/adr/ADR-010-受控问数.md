# ADR-010：受控 Text-to-SQL 执行

- 状态：Accepted
- 日期：2026-10-24

## 背景

客服场景里有一类问题是固定工作流答不了的：「我上个月退了几笔款」「按状态看我一共花了多少钱」「最近的工单有多少」。这些问题不指向某一个订单，也不是退款规则，而是**对调用者自己记录的聚合**。

两条路可以走：

1. 让模型写 SQL 再执行；
2. 让模型（或规则）说出「要什么」，由服务端生成并执行 SQL。

第一条路的失败模式是不可接受的：模型可以写出越权的谓词、写出 `UPDATE`、写出把别的租户的数据算进来的查询。只要一次提示注入或一次幻觉，就会造成数据泄漏。而客服 Agent 的价值恰恰是「不把钱退错」，同一套严谨性必须用在查询上。

## 决策

实现一条**受控** Text-to-SQL 链路：模型与规则只负责把问题翻译成一份「查询计划」，SQL 由服务端生成、由服务端检查、由服务端在只读连接上执行。

四段式，每段都能单独拒绝：

```text
问题 ──planner──► SqlPlan ──builder──► SelectStatement(AST) ──guard──► scoped statement ──executor──► 行
      说不清就 NO_PLAN                 只能构造白名单形状          白名单+租户注入              只读连接
```

### 1. 规划器：只说「要什么」，不说「怎么查」

`SqlPlan` 只有五个业务字段：`dataset`、`metric`（`count` / `sum` / `count_and_sum`）、`group_by`（`status` / `month` / `day`）、`time_range`、`status`。

- 记录集由线索词决定（退款 / 工单 / 订单），第一个命中者胜出；
- 聚合方式由量词决定（「多少笔」→ count，「一共花了多少钱」→ sum）；
- 分组由「按状态」「按月」决定；
- 时间范围由「最近 N 天」「上个月」等决定；
- **状态线索必须属于该记录集**：问「失败的退款」只有在退款表有状态列时才成立，「失败的订单」同理。跨集线索是「不匹配」，不是「忽略」。

规划器认不出的问题**不产生计划**，直接 `NO_PLAN`。这句话的原则是：说不清的问题应该交给人，而不是猜一个答案。

### 2. 构造器：SQL 以树的形式生成

构造器产出 AST（`SelectStatement`）而不是字符串，理由是守卫要用同一个解析器读回来检查。按月/按日分桶需要方言差异：SQLite 用 `STRFTIME('%Y-%m', ts)`，PostgreSQL 用 `TO_CHAR(ts, 'YYYY-MM')`。方言由连接的 `dialect.name` 决定。

### 3. 守卫：三道规则，顺序固定

```text
形状：单条 SELECT、白名单表、白名单列、白名单函数、LIMIT 在上限内
作用域：租户与归属由执行器注入，语句里写了就拒绝
绑定：所有取值都是参数；能进 SQL 字符串的只有固定清单里的日期格式
```

- **白名单表**：`refunds`、`orders`、`tickets`，各自声明可读列与两个作用域列（`tenant_id`、`user_id`）。作用域列**不在可读列里**，所以语句根本无法提到它们。
- **白名单函数**：`COUNT`、`SUM`、`COALESCE`、`MIN`、`MAX`、`AVG`、`STRFTIME`、`TO_CHAR`、`LOWER`、`UPPER`。没有一个能写、读文件或访问网络。
- **内联字面量**：只有 `%Y-%m`、`%Y-%m-%d`、`YYYY-MM`、`YYYY-MM-DD`。其余一律参数化。
- **作用域注入**：守卫把 `tenant_id = :tenant_id AND user_id = :user_id` 作为**顶层合取项**加到 `WHERE` 上，然后用 `require_scope` 复查这个谓词确实是顶层合取项——防止有人写一个 `OR` 把作用域挤进括号。

守卫拒绝时抛 `SqlRejected`，带一个**稳定的理由码**（`REASON_CODES` 共 19 个）。理由码是执行台账记录的内容，也是测试断言的内容，所以一次拒绝对「你为什么没答上来」是可解释的。

### 4. 执行器：数据库侧的第二道防线

守卫是应用层的第一道防线。执行器是数据库侧的第二道，**不依赖守卫写对了**：

| 方言 | 措施 |
|---|---|
| PostgreSQL | `SET TRANSACTION READ ONLY` |
| SQLite | `PRAGMA query_only=ON`，用完回滚并关闭 |

即使守卫漏了一条规则，连接本身也写不进去。

执行完的结果经 PII 脱敏后再返回；执行记录（成功、失败、被拒）写入 `sql_queries` 台账，并产生一个链路 span。

## 后果

- 「我的数据有多少」这类问题有了确定答案，且答案一定只包含调用者自己的记录。
- 拒绝是可解释的：19 个理由码覆盖形状、作用域、绑定三类原因。
- 查询台账让「Agent 拒绝了什么、为什么」可审计。
- 代价是能力受限：只能问「计划器认识的问题」。这是刻意的——**不支持的自由度换来不会越权**。
- 计划器目前是规则实现（`HeuristicSqlPlanner`）。将来可以换成模型驱动的计划器，链路的其余三段不用改，因为契约是 `SqlPlan`，不是自然语言。

## 备选方案

- **让模型直接写 SQL**：拒收。理由见「背景」：失败模式的代价与本项目的核心主张冲突。
- **模型写 SQL + 白名单校验**：比本方案弱，因为模型可以生成守卫不认识的形状，而模型又会重试到能通过为止；守卫的拒绝理由码也就失去了意义。
- **预置报表 / 固定查询模板**：安全但无法覆盖开放式问题，且每加一个问题都要发版。计划器是同一个问题的另一种解法：新增问题改线索词，不改 SQL 生成与执行。
- **只做查询改写，不做查询**：回答质量会明显下降；「上个月退了几笔」在改写后仍需要一次真实聚合。
