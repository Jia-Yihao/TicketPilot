# ADR-023：三条接缝跨进程——限流、模型用量、任务幂等

- 状态：Accepted
- 日期：2026-10-25
- 关联：[ADR-004](ADR-004-审批绑定.md)（审批绑定）、[ADR-005](ADR-005-台账与对账.md)（台账与对账）、[ADR-013](ADR-013-事务性发件箱.md)（事务性 Outbox）、[ADR-016](ADR-016-渠道抽象.md)（渠道抽象）、`docs/guide/安全说明.md`

## 背景

项目跑到「一个进程能跑通」之后，有三处**只在单进程下成立**的事实。它们被写进了 `docs/guide/安全说明.md` 的「已知缺口」，也散在代码注释里：

1. **限流是进程内令牌桶。** `TokenBucket` 的字典在本进程里，N 个 worker 就给同一租户 N 倍预算。文档里那句「多 worker 会放大」是实话，但**没有第二种实现**，所以它是缺口而不是选项。
2. **模型用量是进程内计数器。** `IntentAgent.usage`（`LlmUsage`）是 dataclass 里的整数，进程一重启就归零。README 里那些 token / 延迟数字是**本进程**的记账，不是账本。
3. **任务创建没有幂等键。** 同一段文本提交两次会生成两个任务、各跑一遍。写路径的其余部分都有幂等（`tool_executions`、`tickets`、`refunds`、渠道消息），只有入口这一层没有。

三件事的性质相同：**它们在单进程演示里看不出问题，在多 worker 部署里会变成事实错误**——配额被放大、账单对不上、重复退款。这正是面试里「你说多进程部署会怎样」会问到的地方。

## 决策

### 1. 限流：接口不变，加一个 Redis 实现

`app/core/rate_limit.py` 把「这一条请求还能不能花」抽象成 `RateLimitStore` 协议（`consume(key) -> (allowed, retry_after)`），有两个实现：

| 实现 | 计数方式 | 边界 |
|---|---|---|
| `TokenBucket`（默认） | 令牌连续补充，`per_minute/60` 每秒补一个 | 精确，但**进程内**，N worker = N 倍预算 |
| `RedisFixedWindow` | `INCR` + `EXPIRE`，一分钟一个窗口 | **共享**，但窗口粗：租户可以在分钟边界前后花掉两个窗口 |

`RATE_LIMIT_STORE=redis` + `REDIS_URL` 打开共享配额。缺 `REDIS_URL` 或缺 `redis` 包时**启动即报错**，不静默退回进程内。

选 `INCR`+`EXPIRE` 而不是 Lua 脚本，是一次远程往返 vs 一次远程往返之差——固定窗口不精确（边界可花双倍），但省掉每个请求一次 Lua 求值。这是明写的取舍。

**Redis 挂掉时退回本地桶**，而不是放行全部流量：一个死掉的配额存储不该变成无限预算，退回进程内保证虽然不权威，但至少是老行为。这一条在 `RedisFixedWindow.consume` 的 `except` 分支里。

键格式 `ticketpilot:rate:{tenant|ip}:{key}:{window}`，TTL 是窗口 + 5 秒，避免边界请求把一个即将消失的计数器重建出来。

### 2. 模型用量：从进程内计数器变成表

新增 `llm_usage` 表（迁移 `d7a1f3c9b2e4`）与 `app/services/llm_usage.py::LlmUsageService`。每一行记一次模型运行：

| 列 | 含义 |
|---|---|
| `requests` / `retries` | 模型请求数 / 校验重试数 |
| `input_tokens` / `output_tokens` | token 计数 |
| `latency_ms` | 墙钟耗时 |
| `status` | `OK` / `FAILED` |
| `source` | `task`（任务路径）/ `chat`（对话路径） |
| `planning_source` | 这次规划是谁做的（`rules` / `pydantic_ai` / `rules_fallback`） |
| `task_id` / `conversation_id` | 归属的业务对象 |

**写入时机**：

- 任务路径在**同一个事务**里与 `task.routed` 事件一起写（`app/services/runtime.py`）。要么都有，要么都没有——不会出现「任务记了模型、账本没记」。
- 对话路径写在**这一轮自己的 session** 上，在提交之前（`app/agent/support_agent.py`）。另开连接会在 SQLite 上等这一轮的写锁。

**失败必须放行。** 对话路径上的一次用量写入失败不能变成 500——记账不该成为可用性依赖。所以对话路径的写入用短事务 + 失败即放过；任务路径的写入在已有事务里，失败会随事务一起回滚，这是刻意的：任务本身也就没跑成。

读取接口 `GET /api/v1/analytics/llm-usage?hours=24` 给租户级汇总（总量、按 source 拆分、最近若干行）。聚合在 Python 里算——一个租户的模型调用量按设计就很小，这样 SQLite 与 PostgreSQL 走同一条代码路径；扫描上限 20000 行，防止病态租户把内存吃满。

### 3. 任务幂等键：`Idempotency-Key` 头 + 唯一索引 + 请求摘要

`POST /api/v1/tasks` 现在接受 `Idempotency-Key` 头（最长 200 字符）。语义三条：

| 情况 | 结果 |
|---|---|
| 新键 + 新请求 | 建任务并执行（201） |
| 同键 + **同**请求摘要 | **回放**已有任务，不重复执行；返回体带 `idempotent_replay: true` |
| 同键 + **不同**请求摘要 | `409` `Idempotency-Key was reused with a different request.` |

请求摘要 = `canonical_digest({"request": ..., "context": ...})`（与审批摘要同一个 `canonical_json`，`sort_keys=True`、紧凑分隔符，所以跨进程稳定）。

唯一索引 `uq_tasks_idempotency` 在 `(tenant_id, user_id, idempotency_key)` 上（迁移 `b4e8d2f6a1c9`）。**仲裁者是数据库约束，不是应用层的时序**：两个 worker 同时用同一个键提交时，一个撞 `IntegrityError`，回滚后读回赢家写的行——摘要相同就回放，不同就 409。应用层的先查后建只是**省掉常见的顺序重试**这一笔写，不是正确性的来源。

回放时如果原任务还没跑（停在 `CREATED`），`_replay` 会把它接着跑完——键的含义是「这件事我提交过」，不是「我只要一份回执」。

## 后果

- **三条接缝现在都有第二种实现或第二种事实来源**，不再是「单进程才成立」。
- **限流的共享配额仍不精确**：固定窗口在分钟边界可花双倍预算。要精确得用滑动窗口或 Lua 脚本，代价是每个请求多一次计算。本轮选简单的那一侧并写明。
- **Redis 是可选依赖**：`redis` 不在默认安装里，只有 `RATE_LIMIT_STORE=redis` 时才 import；`pyproject.toml` 里是可选 extra。选 `redis` 但没装 → 启动即报错，不会静默退回。
- **`llm_usage` 是新增表**，需要迁移（`alembic upgrade head`）。`AUTO_CREATE_TABLES=true` 的开发模式会自动建。
- **对话路径的用量写入是 best-effort**：失败时这一轮的 token 不会进账本。任务路径不是。两种语义不同，是因为两处的失败后果不同。
- **没有按会话 / 按用户的模型预算。** 账本能告诉你花了多少，不能阻止下一次调用。限流按租户和 IP，不按模型成本。
- **幂等键的键空间是 `(租户, 用户, 键)`**：不同用户用同一个键不会互相命中，符合「键属于调用方」的直觉，但也意味着客户端要自己保证键在**同一用户**下稳定。
- **`Idempotency-Key` 不带键 = 不受保护**：客户端不给键，重放防护不存在。这与渠道层 `X-Channel-Message-Id` 的残留边界是同一类（`docs/guide/安全说明.md` 已列）。
- **账本没有保留期策略**：行只增不减。真要长期跑需要分区 / 归档，本轮没做。

## 备选方案

- **限流用 Redis 令牌桶（Lua）**：精确，但每个请求一次 Lua 求值 + 一次远程往返。本轮选固定窗口，换取实现简单与「一次往返」。
- **Redis 挂掉时放行全部流量**：一个挂掉的配额存储变成无限配额，等于没有限流。退回本地桶是更诚实的降级。
- **用量只写 span 不建表**：span 已经在记 `model_*` 属性，但 span 没有租户级汇总能力，也没有跨 worker 的口径（本项目的 span 表是共用的 Postgres，其实有）。建表的收益是**可查询**与**可聚合**，代价是一张新表。
- **用量聚合下推到 SQL**：能支撑大租户，但要写两套方言（SQLite 与 PostgreSQL 的时间函数不同）。当前量级下 Python 聚合更省事也更稳。
- **幂等只查不建索引**：查一次能挡住顺序重试，挡不住并发双提交——两个 worker 都查不到，都会建。约束才是仲裁者。
- **同键不同请求直接回放旧结果**：那会用旧答案回答一个新问题。409 是对的。
- **把 `Idempotency-Key` 也加到渠道入口**：渠道层已经有 `X-Channel-Message-Id` 的唯一约束与内容摘要（`channels/store.py::claim`），两套键并存会让客户端不知道该用哪个。本轮不加。
