# ADR-037：写意图判定迁到意图目录——判定器唯一化，但判定结果一条都不改

- 状态：已接受
- 日期：2026-10-27
- 关联：ADR-009（意图目录为唯一事实源——本 ADR 把这条承诺兑现到写意图上）、ADR-020（对话入口只在规则读不懂时问模型，且只采纳退款）、ADR-024（三级模型闸门）、ADR-028（意图语料评测——本轮用它做等价性回归）、ADR-030（决策复用，`RULESET_FINGERPRINT` 的来源）、ADR-034（意图候选化——本轮的候选集副作用见第 9 节）、缺口 F-9 / 阶段 B

## 背景

ADR-009 说意图目录是唯一事实源，`app/agent/intents.yaml` 的头部注释更进一步写着「加一个能力
就是加一行，不改路由代码」。但**写意图**一直是这句话的例外，而且是个没被登记的例外：

- `REFUND_REQUEST` / `TICKET_CREATE` 两行在目录里**没有 `cues`**，判定在 `app/agent/routing.py`
  的 `_REFUND_ACTION`（6 条）与 `_TICKET`（5 条）两个硬编码元组里，靠顺序 `if-elif` 先到先得。
- 于是改 YAML 对写意图**零影响**，而这件事此前没有任何登记：写意图用的是最弱的判定方法
  （后记为病灶 D1），且两套词表并存、口径与实现不符（后记为 D2）。
- 更要紧的是**风险与方法的错配**：写路径（建退款、建工单）是整条链路里唯一会产生
  人工审批负担的一侧，判定却锁在只有改代码才能调整的位置。

本轮的性质必须先说清楚：**这是等价重构，不是效果改进**。判据不是「新结果对不对」，
而是「同一句话改前改后必须是同一个意图，包括 `UNKNOWN` 落在哪些句子上」。因此
本轮**不许加词**（哪怕加了明显更准）、不许改优先级、不许动采纳面。等价性是门禁，
准确率是另一轮的事——把两件事混在一次改动里，等价性基线就失效了，谁都说不清
哪个变化来自哪里。

## 决策

### 1. 判定器唯一化：`classify()` 的写分支改为问目录，cues 逐字复制

`classify()` 不再自己拿词表比字符串，而是调用新的私有函数
`app/agent/routing.py::_match_write_intent()`：遍历 `get_catalog().ordered_specs()`，
只看 `write_path: true` 的行，第一个「任一 cue 出现在文本里」的行即判定结果。
目录侧那两张写行的 `cues` 是**逐字复制**原词表内容得到的——匹配语义本来就是
`cue in text` 的子串命中，`intents.yaml` 的 cue 在进入匹配前也已经随整句话小写化，
所以「逐字复制 cue」在算术上就等价于旧词表，不需要额外证明。

`REFUND_REQUEST` 6 条、`TICKET_CREATE` 5 条，一条不加、一条不减、不合并同义词。
加词是独立事项（第 8 节的代价登记说明了为什么本轮忍住不加）。

### 2. 问句门槛两处都保留，且门槛的生效被断言「cue 确实命中」证明

`blocks_write_action()` 这个闸门在写路径上有两个调用点，本轮**一个都没丢**：

| 位置 | 作用 |
|---|---|
| `app/agent/routing.py`（`classify()` 内 `blocked = blocks_write_action(text)`） | 被挡住的句子不进写意图，落到读分支或 `UNKNOWN` |
| `app/agent/support_agent.py::classify_support` 第 ② 步（`and not (blocks_write_action(text))`） | 端到端的写意图同样被这道闸拦住 |

另外目录内部还有第三道：`IntentCatalog.match()` 对带 `match_request_only: true` 的行
自己就调 `blocks_write_action`。三道闸的语义是同一个谓词，不是三份不同的规则。

门槛光「还在」不够——如果 cue 表恰好没覆盖那句话，测试也会绿，而门槛其实早就被删了。
所以 `tests/test_intent_rules.py::test_policy_questions_never_trigger_write_actions` 的
断言写成三条一组：`classify()` 判 `POLICY_QA`、生产路径 `classify_support()` 判 `POLICY_QA`、
而 `_match_write_intent()` 对同一句话**必须非 None**。第三条证明「cue 命中了、是门槛挡的」，
于是将来任何人删掉门槛都会立刻打红，而不是悄悄换个词表糊过去。

### 3. 等价性的判据是端到端，不是过程层

判定最终由 `classify_support()` 三步合成（① collaboration 行 → ② 写意图 → ③ 目录命中，
兜底 `UNKNOWN`），这个顺序本轮**一字未动**。所以本轮的门禁分两层：

| 层 | 判据 | 结果 |
|---|---|---|
| 端到端 | 346 条语料的 `SupportPlan.intent` 逐条不变（含 `UNKNOWN` 的位置） | **漂移 0 条** |
| 过程层 | `classify()` 的写意图分支 vs 目录 `write_path: true` 行 | **差异 0 条** |

只卡过程层会漏掉合成顺序：一句话同时命中写行 cue 与 collaboration cue 时，过程层给
`TICKET_CREATE`、端到端给 `HUMAN_HANDOFF`，只有端到端那层能看出「转人工先于写路径」这条
规则（ADR-011）有没有被写坏。

反过来，目录里那些**软字段**（影子比对时记录的 `catalog_write` / `catalog_match`）本轮
确实变了 14 条——那是施工面的证据，不是失败：软字段记录的是「目录现在能不能读出这一行」，
它变而端到端不变，正是等价重构应有的形状。这 14 条逐条登记在
`openspec/changes/add-intent-routing-data-driven-2026-10/diff-list.md`。

### 4. 循环导入用函数内延迟导入解开，不反转依赖方向

`app/agent/intent_catalog.py` 在**模块级**从 `routing` 导入 `blocks_write_action`、
`is_policy_question` 等谓词（目录的匹配器需要它们）。如果 `routing.py` 反过来在模块级
导入 catalog，就是环。本轮的处理是让唯一那条查询边**延迟到函数内**：
`_match_write_intent()` 的第一行 `from app.agent.intent_catalog import get_catalog`，
类型注解走 `if TYPE_CHECKING`。

这不是随手绕过去的技巧，两个理由：

1. **依赖方向不变**：`docs/architecture-guard.yaml` 的清单一字未动，
   `tests/test_architecture_guard.py` 的 `module_edges` 只从**顶层 import** 构图，
   函数内的导入因此不引入新的模块级边——守卫 24 条全绿就是这条的证据。
2. **可测性**：函数内的 `from X import Y` 每次调用重新读模块属性，所以测试可以用
   `monkeypatch.setattr("app.agent.intent_catalog.get_catalog", ...)` 换掉判定源。
   若改成模块级 `from ... import get_catalog`，那个名字就被绑死了，第 6 节那条
   「加一行即生效」的用例证不出来。

被否决的替代是「把写意图查询下沉到 `support_agent`，再把结果作为参数传进 `classify()`」：
`classify()` 有四个生产调用点（`app/agent/pydantic_agent.py`、`app/agent/support_agent.py` 两处、
`app/services/runtime.py`），加参数等于把判定接口面扩到本轮范围之外，且 `classify()` 单独
被调用时（例如 SQL/运行时路径）会失去写意图判定。

### 5. 写行必须登记：白名单 + 显式豁免，静默跳过用测试拦住

`write_path: true` 的目录行有**三**个，而 `Intent` 枚举只有六个成员。
`DELIVERY_ISSUE` 是 `write_path: true` 却没有对应枚举成员——它是「客户说没收到货」这类
句子，端到端由 `classify_support()` 第 ③ 步取目录行给出，`classify()` 从来判不出它。
于是 `_match_write_intent()` 的循环必须跳过它，而**跳过**正是最危险的形状：
如果跳过是裸 `continue`，那么「加一行写意图就生效」这句话第二次失效，而且失效时没有任何动静。

本轮把它定成一个可判定的机制：

- `routing._WRITE_INTENT_IDS`：`classify()` **可以**认领的写行白名单（`REFUND_REQUEST`、`TICKET_CREATE`）。
- `routing._WRITE_INTENT_EXEMPT`：显式点名豁免、并写明理由的集合（`DELIVERY_ISSUE`）。
- `tests/test_intent_catalog.py::test_every_enum_label_has_a_catalog_row` 内加一条子集断言：
  `write_path: true` 的行集合 ⊆ 白名单 ∪ 豁免集，失败消息直接把「该扩哪儿」写出来。

这条断言的**失败可见性不是声称的，是实测的**：本轮临时往 `intents.yaml` 追加一行
`write_path: true` 且两个集合都不在的假写行，用例立刻 `1 failed`，
消息为 `未登记的写路径行 ['NEW_WRITE_ROW']`；随后恢复 YAML（`diff -q` 为空）。
读数在 `tasks.md` 的 4.8。

### 6. 「加一行即生效」现在是被测试证明的承诺，而不是注释里的一句话

`tests/test_intent_catalog.py::test_the_catalog_row_replaces_the_agent_branch` 里追加了两段
（都**并写在既有用例体内**，不改收集数）：

1. 用 `intent_catalog._load(tmp_path / "intents.yaml")` 造一份含假写行的目录，
   断言 `patched.match(...)` 返回那个假意图，而生产目录对同一句话返回 `None`——
   证明目录是唯一判定源。这里必须走 `_load`：`get_catalog()` 带 `lru_cache(maxsize=1)`，
   改不动也清不干净。
2. 把 `REFUND_REQUEST` 的 cue 在临时 YAML 里多写一条词，`monkeypatch` 换掉
   `intent_catalog.get_catalog` 后 `classify()` 立刻把那句话判成 `REFUND_REQUEST`；
   `monkeypatch.undo()` 后回到 `UNKNOWN`——证明**改 YAML 数据即改判定**，不改一行判定代码。

### 7. `intents.yaml` 的注释：承诺收窄到读行，写行的规则放文末脚注

头部那句「加一行即可，不改路由代码」原本对写行不成立。本轮把它改成**只对读能力成立**
（「加一个读能力 = 加一行 + 一个 action 实现」），写行的唯一被校验的规则挪到**文件末尾脚注**。

放脚注不是排版偏好，是被引用面逼的：`intents.yaml` 的行号被多处文档**逐字引用**
（`docs/spec/项目规格.md` 引 `:51` / `:96`，`.qoder/rules/refund-reason-taxonomy.md` 引
`:31` / `:49-55` / `:80` / `:84-87` / `:93-96`，后一份本轮**不可写**）。把整段说明写在头部
会把 `version` 从 `:31` 推走，连带打漂一批别人的引用。所以这次编辑是**净零行**的：
头部原地替换两行，说明追加在最后一行之后。

### 8. 本轮明确不做（登记，不是遗漏）

1. **不给 cues 加词**。「那笔钱给我退回来」这类说法本轮之后**仍然读不出**，这是有意的：
   加词会让判定结果变化，等价性基线就没了参照物。加词属下一轮（F-1 展开时一起做更划算）。
2. **不迁读路径的词表**。`_REFUND_ELIGIBILITY` / `_LOGISTICS` / `_POLICY` / `_ORDER` 四张
   读路径词表仍在 `routing.py`，与目录 cues 各写一份——所以 D2 是**部分收口**。
   迁它们要同时处理 T2（`POLICY_QA` 与 `LOGISTICS_QUERY` 的优先级倒置）与 T3
   （`REFUND_ELIGIBILITY` 被降级为 `POLICY_QA`），那是判定行为，不是判定源。
3. **不把合成优先级写成契约文件**。`classify_support()` 的三步顺序目前仍然只存在于代码里。
4. **不扩采纳面、不动 `model_gate()` 的 `question` 出口**（ADR-020 / ADR-024；属阶段 A / F-1）。
5. **不新增意图行**，**不新增评测语料**，**不改 `evals/intent_metrics.py` 的指标口径**
   ——本轮用它做 A1 等价性回归，评测扩量是另一件事。
6. **不为了门禁绿改三份守卫清单**（`docs/fact-baseline.yaml` / `code-anchors.yaml` /
   `architecture-guard.yaml`）。

### 9. 两处必须让后来者看见的副作用

**其一：`RULESET_FINGERPRINT` 的覆盖面因此变窄了一格。**
`app/agent/routing.py::ruleset_fingerprint` 按源码字节做摘要，摘要集合是
`routing.py` + `app/sql/planner.py` + `app/core/money.py`——**不含 `intents.yaml`**。
本轮之前写意图词表在 `routing.py` 里（在摘要内）；本轮之后它搬进了 YAML（在摘要外）。
于是「改目录 cues」不会作废存量模型决策缓存，而「改词表」过去会。本轮没有把这个键
加进摘要：加进去是缓存失效语义的变更，不在等价重构范围，且需要单独的用例证明。
**登记为缺口，交给后续轮次裁定。**（本轮自身的 `routing.py` 改动确实轮转了一次指纹，
使缓存按既有设计作废一次；没有任何用例硬编码指纹值，`tests/test_decision_reuse.py`
是导入常量做比对，因此不受影响。）

**其二：候选集的证据面多了一类，但本语料实测无变化。**
`app/agent/candidates.py::_evidence` 给每个候选行找证据时，把目录 cue 命中记成 `cue:<词>`，
它**不读** `match_request_only`。本轮给两行写意图加上 cues，理论上会让「cue 命中写行、
但被问句门槛挡住、却仍进了 `consult`」的句子多出一条 `cue:` 证据。
在同一份 346 条语料上实测（离线纯函数，不调模型）：走到 `consult` 的有 **99 条**，
其中改造前后**候选集逐字相同的是 99 条，变化 0 条**。
原因是结构性的：cues 与旧词表逐字一致，而 `classify()` 的写读数正来自这批 cue，
所以「cue 命中」与「`rule:` 命中」在写行上同构。**这个同构是本轮条件的产物，不是永久保证**——
一旦下一轮给 cues 加词，或给 `_evidence` 读 `match_request_only`，它就未必成立。登记在案。

### 10. 规则 2 的「同层耦合」按「同 tier 跨层」读（本轮**不改**那个测试文件）

`tests/test_architecture_guard.py::test_dependencies_only_point_strictly_down` 的**用例级**
docstring 写「反向与同层耦合必须登记在 `exceptions`」（`tests/test_architecture_guard.py:239`），
而同一用例体的循环里 `if source == target: continue`
（`tests/test_architecture_guard.py:245-246`）把**同名层**的边整段跳过，`kind` 也只在
**tier 相同、层不同**时才取「同层跨层耦合」（`tests/test_architecture_guard.py:255`）。
也就是说，被规则 2 要求登记的只有**同 tier 的跨层耦合**；同名层内的边既不参与判定，
也不必进 `exceptions`。模块级 docstring（`tests/test_architecture_guard.py:11-12`）写的
正是「同层跨层耦合」，与循环体一致——偏差只在那一句用例 docstring 的措辞。

**决定**：本轮**不改** `tests/test_architecture_guard.py`。改那一句措辞会动一个与本变更无关的
守卫文件，且不改任何判定；读那个用例时一律按模块级 docstring 与循环体的「同 tier 跨层耦合」
理解。用例 docstring 的措辞订正留给架构守卫自身的轮次（归属 ADR-025），届时与守卫的三条判定
一起改，不在这里顺手改。

## 后果

正面：

1. 写意图的判定源进了数据层，「改 YAML 即改判定」从注释变成被用例证明的承诺（第 6 节）。
2. D1 收口，D2 部分收口；`routing.py` 少了两张词表，`classify()` 的写分支变成一行查询。
3. 风险最高的一条路径从此可以随数据调整，而调整的可观测性由子集断言兜住——
   新增写行不登记就红，不会静默。
4. 等价性有可复算的证据链：改造前后各存一份端到端基线（346 条 `SupportPlan.intent`）
   与一份 `intent_metrics` 输出，逐条比对，不靠「大概一样」。

代价与风险（逐条登记）：

1. `classify()` 与 `catalog.match()` 现在**共享**一份 cue 数据，一处写坏两处同时失真；
   换来的是不会再出现「两套词表各改一半」这种更难查的形态。
2. 写行判定从此受 `IntentCatalog` 的加载器约束（`_reject_unknown`、priority 顺序），
   YAML 里的一个手误 priority 会影响写路径——本轮之前不会。
3. 第 8 节那六条「不做」里，第 1 条（不加词）意味着本轮**没有**改善任何一句话的读数；
   这是等价重构的定义，不是缺陷。
4. 诊断量 `cue_overlap.with_gold_cue` 从 61 变到 74（`evals/intent_metrics.py::_cue_overlap`
   的定义是「语料里有多少句天然含有其 gold 意图的 cue」，模块文档写明它是 visibility number，
   不是分数）。目录里多了 11 条 cue 字符串，被数到的句子自然变多。它不进任何门禁判定，
   `--enforce` 只查 `exact_cue_texts` 与「overlap ≤ 语料条数」，两项都仍然成立。

## 被否决的方案

1. **`classify()` 全面委托 `catalog.match()`**（plan 里最省事的读法）——否决：
   `Intent` 只有 6 个成员，目录有 12 行；`Intent(spec.intent_id)` 对
   `REFUND_STATUS` / `LOGISTICS_QUERY` 等行直接 `ValueError`。真要全面委托，就得把
   读意图也塞进枚举，或把 `RoutePlan.intent` 换成字符串——两者都不是「判定源迁移」，
   而是判定契约改写。本轮只迁写意图，正是要把改动面限制在能被等价性回归钉住的那一块。
   另外读路径的两处既有分歧（T2 优先级倒置、T3 的 `REFUND_ELIGIBILITY` 降级）一旦委托
   就会变成**行为变化**，而它们端到端本来惰性——见 `known-divergences.md`。
2. **把写查询下沉到 `support_agent`，作为参数传进 `classify()`**——否决：理由见第 4 节。
3. **再开一张关键词→意图的 YAML（第四张表）**——否决：项目已有「数据在 YAML、代码只读」
   的形状（`intents.yaml`、`escalation.yaml`、`refund_reason_rules.yaml`），但写意图的
   数据本来就该长在**意图行**上；另开一张表等于制造第三个判定源。
4. **裸 `continue` 跳过 `Intent` 里没有的写行**——否决：这是「静默跳过」，让本轮想修的
   那句承诺第二次失效且不留痕迹。改用白名单 + 显式豁免 + 子集断言（第 5 节）。
5. **迁移顺手把明显缺的说法补进 cues**——否决：等价性就没有基线了（第 8 节第 1 条）。
6. **为了让候选集「更准」把 `match_request_only` 读进 `_evidence()`**——否决：本轮无实证
   收益（第 9 节实测 0 条变化），且它在改的是模型能看到什么，属阶段 A 的范围。
