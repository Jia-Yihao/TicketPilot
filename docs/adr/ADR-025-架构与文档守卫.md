# ADR-025：架构依赖守卫与文档一致性守卫——让「诚实标注」被测试验证

- 状态：Accepted
- 日期：2026-10-25
- 关联：[ADR-002](ADR-002-有界智能体.md)（受限抽取与分层）、[ADR-006](ADR-006-目标库与开发库.md)、[ADR-021](ADR-021-稠密通道闸门.md)、[ADR-024](ADR-024-三级模型闸门.md)（三级模型门控）

> **当前分布形态**：这份 ADR 记录的是决策本身。本文提到的「事实基线」与「代码锚点」两份清单
> 随内部规划文档一起不在当前分发版内，因此对应守卫也不在库里；现存的是架构依赖守卫
> （`docs/architecture-guard.yaml` + `tests/test_architecture_guard.py`）与文档守卫里
> 「端点落点 / 配置项映射」两类判据（`tests/test_docs_consistency.py`）。决策理由不变，
> 清单的落地形态以仓库现状为准。

## 背景

这个项目的叙事是「诚实标注」：每个对外数字都要能跑出来，每个边界都要写出来而不是藏起来。

但截至本次，这个诚实只存在于**散文**里：

- `docs/spec/项目规格.md` §19.2 有一张漂移表，手工把「原措辞」和「复核后」并排放着；
- README 当时写着「45 个操作 / 42 条路径」「13 条迁移」「24 张表」，测试文件数与用例数还停在「43 个测试文件、收集 502 条」。

这些数字**没有一个人替它看着**。加一个接口、迁移一次、加一张表、改一个测试文件之后，文档里的数字不会自己变——它会安静地变成错的，而项目里没有任何东西会报警。§19.2 的漂移表恰恰记录了这件事已经发生过：路径数写着 41、实际 42；mypy 文件数写着 134、实际 137。

更糟的是，**漂移的方向总是对自己有利**：代码长到 45 个操作时，文档还写着 45，但下一个接口来的时候没人会记得改。同理，架构分层写在 `docs/guide/架构说明.md` 里，`app/agent/` 引用 `app/services/` 这种反向依赖是**已知的**（ADR-002 那轮为了拿到业务状态做的取舍），但它只存在于人脑里，下一个人加一行 import 就把它固化了。

所以本次要的不是「再写一份规范」，而是**把规范变成会失败的测试**。

## 决策

加两个守卫，都是测试，都以「策略即数据」的方式落盘：

| 守卫 | 策略文件 | 测试 | 回答的问题 |
|---|---|---|---|
| 架构依赖守卫 | `docs/architecture-guard.yaml` | `tests/test_architecture_guard.py` | 这个包还认不认自己写在文档里的分层？ |
| 文档一致性守卫 | 事实索引清单（已撤下） | `tests/test_docs_consistency.py` | 文档里写的数字，还等于代码现算出来的数字吗？ |

### 1. 策略即数据，规则写在文档里，不写在测试代码里

两个守卫都**不把规则硬编码在测试里**：

- 架构约束（层、例外、禁止边）写在 `docs/architecture-guard.yaml`；
- 事实索引（哪个文件的哪一行有个数字、用哪个正则抠出来）写在独立的 YAML 清单里。

理由：规则写在测试代码里，规则就成了实现细节，读代码的人才知道它存在；写在 YAML 里，它就是**可评审的文档**，改它等于改架构，必须走 ADR（这也是 YAML 文件头部写明的要求）。

### 2. 架构守卫：六条规则

层次自下而上分六档（`core`/`observability`/`db` = 0 → `models`/`schemas` = 1 → `repositories`/`retrieval`/`sql` = 2 → `tools`/`agent`/`channels` = 3 → `services` = 4 → `api` = 5；层号越大越靠上），`main`/`seed`/`asgi` 是组合根，豁免方向规则。

1. **层必须声明**：`app/` 下每个含 `.py` 的目录都要出现在 `tiers` 里。加层是做决定，不是顺手的事。
2. **依赖只能严格向下**：跨层依赖必须 `tier(源) > tier(目标)`。反向依赖（低层依赖高层）与同层跨层耦合一律违规，必须登记进 `exceptions` 并写清 why。
3. **`forbidden` 的边一律不许出现**，哪怕方向是向下的。
4. **层图里不许有未登记的互环**：两层互相依赖时，至少有一个方向必须登记。
5. **不许有模块级 import 环**（Tarjan 强连通分量）。这一条只算模块顶层求值的 import：函数体里的 import 是运行时依赖，导入时不会炸。
6. **登记不许腐化**：`exceptions` 与 `known_deviations` 里的每条边必须真的还在用。修好了就要删登记，别留着当借口。

第 6 条是这套守卫和「贴张架构图」的根本区别：登记本身也会过期，所以登记也要被守着。

守卫**故意不修**当前已知的偏离。它只如实记录：

- `agent -> services`、`tools -> services`（反向依赖，正解是抽 ports，本次未做）；
- `channels -> agent`、`core -> observability`（同层 / 基础件之间的横切耦合）；
- `api -> sql`（HTTP 层绕过 services 直接用受控 SQL 服务，改走服务层需要先把 SQL 查询下沉一层）。

这些登记都带 why，守卫在它们失效时报错，让人把它删掉。

### 3. 文档守卫：数字只写一次

那份清单里**没有数字**。它只写「哪个文件的哪一行有个数字」和「用哪个正则把它抠出来」，数字的唯一定义在代码里，由守卫现算：

```text
代码现算的值  ==  文档里写的值   →  通过
代码现算的值  !=  文档里写的值   →  失败，并指出是哪个文件的哪一行
```

现算的事实有 14 项：OpenAPI 路径数与操作数（`create_app().openapi()`）、迁移条数与 head 修订号（解析 `alembic/versions/*.py`）、SQLAlchemy 表数、`app/` 与 `tests/` 的文件数、mypy 实际检查的文件数、`pytest --collect-only` 收集到的用例数、ADR 篇数、Golden Set 与只读评测集的用例数、离线用例总数、控制台页面数。

三条约束让清单不至于自己变成第二份事实源：

- **锚点必须唯一且不含数字**。锚点是定位用的，一行里只能命中一次；带数字的锚点等于把事实值复制一份，改数字就会改锚点，守卫会以「锚点失效」而不是「数字对不上」的方式报错。
- **正则里不许有字面数字**（`\d` 与字符类除外）。
- **每个事实至少要在两处文档里被写出来**。只写一处的地方最容易忘更新；两处以上漏了一处，守卫会指出来。

另外守两件和数字相关的事：

- **（已停用）说明书必须与规格同步**：曾把 `docs/spec/项目规格.md` 渲染成 Word 说明书，
  由 `scripts/build_manual.py` 写一份构建记录（源文件 sha256 + pandoc 版本 + 体积/段落/表格数）。
  守卫先比 sha256（不依赖 pandoc，规格改了没重生成就红），再在 pandoc 版本一致时逐段比
  重新渲染的结果——把「说明书过期」与「换了 pandoc 版本导致渲染细节不同」这两种看起来
  一样的情况分开。说明书随文档面收敛撤下后，这条判据不再执行；脚本只保留渲染与自检。
- **（已停用）说明书本身要干净**：所有 XML part 的 U+FFFD 计数为 0、没有私有区字符、
  没有退化成 `<w:sym>` 的符号。这部分校验现在由 `scripts/build_manual.py` 自己执行。

### 4. 失败信息必须能直接用

两个守卫的失败信息一律带 `文件:行号`，架构守卫还带上层名与 tier。理由和 §19.2 漂移表一样：一条「断言失败」没有位置信息，就等于没有反馈。

## 后果

- **两个守卫都做过反向验证，而且反例是仓库里的脚本**：`scripts/guard_negative_check.py` 把要用的子树复制到临时目录，在副本上造六处破坏——未声明的新层目录、低层反向依赖高层（core -> services）、`forbidden` 边（api -> tools）、模块级 import 环、登记腐化（代码里那条边没了，登记还在）、文档数字漂移（把 README 的路径数改错）——每一处都断言对应的守卫用例**红**，还原后断言**绿**；它不碰仓库里的任何文件。守卫不是「看起来能跑」，是**确实会拦**，而且这个「会拦」是可复现的：`make guard-negative`。
- **加这个守卫立刻改掉了四处漂移**：新增两个测试文件之后，`tests/` 的文件数从 43 变 45、收集到的用例数从 502 变 519、ADR 篇数从 23 变 24，守卫当场把四处文档指了出来（`docs/spec/项目规格.md` 的 §19.2 漂移表、`CONTRIBUTING.md` 的编号规则等）。**这正是这个守卫存在的意义**：漂移在提交前就被抓住，而不是留给下一个读文档的人。
- **守卫本身也是要被守的**：清单里登记了却没实现的现算函数、实现了却没人核对的事实、只在文档里出现一次的事实、指向不存在文件的锚点，都会失败。
- **`docs/architecture-guard.yaml` 的例外清单会被人盯着**。想加一层反向依赖，得先在 YAML 里写清 why；这让「顺手加一行 import」变成一件要先说服自己的事。
- **成本**：两个守卫合计 17 条用例，收集耗时约 4 秒（其中大部分是 `pytest --collect-only` 子进程与 pandoc 重渲染）。CI 的 `python -m pytest` 会自动跑到它们。
- **已知边界**：架构守卫只看 `app/` 内部的 import，不看 `scripts/` 与 `evals/`；跨进程、跨服务、运行时反射出来的依赖它管不了。文档守卫只守**列进清单的那些事实**——它不是「所有数字」的全集，清单之外的数字（比如耗时的秒数、token 数）仍然靠带日期的复跑记录，不是靠这个守卫。说明书逐段比对要求本机 pandoc 版本与构建记录一致，不一致时该条跳过、改由 sha256 检查兜底。
- **`tests/` 的文件数与用例数现在由守卫盯着**，所以每加一个测试文件就要同步三处文档。这是这个守卫的代价，也是它的意义：数字不再靠记。

## 备选方案

- **只在 `docs/spec/项目规格.md` 里写一份「当前口径」并靠人维护**：本次之前就是这个做法，漂移表证明它漂了。
- **用 `import-linter` / `pytest-split` 之类的现成工具**：`import-linter` 的契约写在 Python 里，等于把规则藏回代码；而且它不做「登记不许腐化」这件事——本项目需要的是**例外必须被承认、用完必须被删**。本项目的分层还需要「同层跨层耦合」和「层间互环」两条自有规则，现成工具都不覆盖。
- **用 `pytest --doctest-glob` 或 markdown 里的可执行代码块来跑数字**：markdown 里的代码块要么变成第二份计算实现（和「数字只写一次」冲突），要么依赖执行顺序和全局状态；本项目要的是**纯读取 + 比对**。
- **把守则做成 `pre-commit` 钩子而不是测试**：钩子不跑在 CI 上，别人 clone 下来第一次提交就绕过去了；做成测试，至少 CI 和 `pytest` 会跑。
- **把数字直接写进 YAML 清单里**：那正是这个项目一直在被咬的地方——第二份事实源必然漂。清单里只放位置与正则。
- **把架构守卫做成运行时断言**：分层是结构问题，不是运行时问题；运行时断言只能在某条路径恰好被走到时才生效，覆盖不到冷门路径。
