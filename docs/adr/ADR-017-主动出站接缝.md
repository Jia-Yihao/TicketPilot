# ADR-017：主动通知的出站接缝——去向由服务端拼，`SENT` 只到通道边界

- 状态：Accepted
- 日期：2026-10-24
- 关联：[ADR-013](ADR-013-事务性发件箱.md)（事务性 Outbox）、[ADR-014](ADR-014-客户记忆与主动授权.md)（客户记忆与主动确认）、[ADR-016](ADR-016-渠道抽象.md)（渠道抽象）

## 背景

T5 把「规则 → 七道抑制闸 → 客户确认 → 与业务事实同事务写 Outbox」做完之后，队列里的
`proactive.confirmed` **没有任何消费者**。当时的实测是 `POST /api/v1/outbox/deliver` 返回
`{claimed: 1, sent: 0, failed: 1}`，`last_error` 是
`MessageNotDelivered: No handler for proactive.confirmed.`——客户在界面上点了「同意」，
通知永远停在 `CONFIRMED`，重试五次后进死信。文档当时只能写「`SENT` 对主动消息不可达」。

补这个出口有三种做法，其中两种是陷阱：

1. **把发送逻辑写进 `ProactiveService` 或 `TaskRuntime`。** 出站就得知道邮件要有主题、
   IM 只能 200 字，渠道知识第二次长进认知层，直接违反 ADR-016 的「协议差异停在边缘」。
2. **把收件人写进消息 payload。** 出站查询就变成「按 body 里给的地址发」，等于把
   「谁能收到什么」交给写消息的一方；跨用户投递是这个系统里最不能犯的一类错。
3. **为了演示直接连一个真实服务商。** 本仓库没有凭据、也没有送达回执接口，
   接上之后 `SENT` 会被所有人（包括写文档的人）读成「客户已收到」。

## 决策

### 1. 出站放在渠道层，与入站共用同一张能力表

新增 `app/channels/outbound.py`，渲染复用 `app/channels/render.py::render_notice`——
入站按 `ChannelCapabilities` 裁正文，出站按同一张表生成形状（邮件带主题与署名、
微信/企业微信裁到 200 字、短信保留退订行、语音追加转人工话术）。
`app/services/runtime.py` 的 `_outbox_sink()` 只多一个 `event_type` 分支：

```python
def sink(row: OutboxMessage) -> None:
    if row.event_type == PROACTIVE_EVENT_TYPE:
        ProactiveSender(session, self.settings).deliver(row)
        return
    if row.event_type != REFUND_PENDING_CONFIRMATION:
        raise MessageNotDelivered(f"No handler for {row.event_type}.")
    ...  # 退款：认领后对账，仍未确认则 MessageNotDelivered
```

队列与 Outbox 服务本身不认识渠道，也不认识通知表。

### 2. 去向由三段服务端事实拼出来，payload 只有 ID

```
队列行的 (tenant_id, user_id)
  → 该客户档案里的 preferences["contact_channel"]
  → 把入站身份映射表反查（_ADDRESS_MAPS：EMAIL → channel_email_identity_map，
     WECHAT / WECOM → channel_im_identity_map）得到地址
```

`row.payload` 里只有 `notification_id`，而通知与档案的两次查询**都带上队列行的
`tenant_id` + `user_id` 过滤**，所以伪造一个别人的 `notification_id` 得到的是
`[NOT_FOUND]` 而不是别人的通知。地址来源是配置：ADR-016 已经规定「身份不从 body 来」，
出站是同一条约束的反面——**去向也不从 body 来**。

档案里没有渠道 → `[NO_CHANNEL]`，**不回落到默认渠道**；渠道没有地址来源（`SMS` / `VOICE` /
`WEB` 等）→ `[NO_ADDRESS_SOURCE]`；有来源但映射表里查不到这个客户 → `[NO_ADDRESS]`。

### 3. 传输是一个协议，默认实现只会拒绝

```python
class OutboundTransport(Protocol):
    name: str
    def send(self, notice: OutboundNotice) -> None: ...
```

三个实现，`build_transport()` 按 `channel_outbound_transport` 选择：

| 实现 | `name` | 行为 |
|---|---|---|
| `RefusingTransport` | `none`（默认） | 抛 `[NO_TRANSPORT]`。没有任何东西被接上，所以不允许任何一行自称已送达 |
| `MisconfiguredTransport` | `local_file` | 开了传输却没配落盘路径，每条消息抛 `[DROP_FILE_MISSING]` |
| `LocalFileTransport` | `local_file` | 把渲染结果作为一行 JSON 追加到落盘文件并 `fsync`；写失败抛 `[DROP_FILE_FAILED]` |

`validate_production_safety` 在 `environment=prod` 时拒绝任何非 `none` 的取值。
真实服务商（SMTP / 微信 / 企业微信）是**第四个实现**：不改队列、不改通知表、不改 API。

### 4. 拒绝要留痕，但不算送达

所有拒绝走同一个异常 `OutboundDeliveryError(reason, message)`，消息一律以
`[REASON]` 开头——它是坐席在 `GET /api/v1/outbox` 的 `last_error` 里唯一能读到的东西，
没有原因码的拒绝无法诊断。抛出后行退回 `PENDING` 按指数退避，通知停在 `CONFIRMED`。

发送前重读一遍同意状态（`[NO_CONSENT]` / `[UNSUBSCRIBED]` / `[NOT_CONFIRMED]`），
所以「确认之后又关掉推送」不会变成一次成功的投递。冷却与当日额度**不在出站重跑**：
出站重试的是同一条已经确认过的消息，再跑一遍抑制闸只会把它按频控挡死。

### 5. `SENT` 的定义写死为「交给配置的传输并写成功」

不新增 `DELIVERED` / `BOUNCED` 状态，也不复用 `SENT` 表示服务商回执——送达回执是
另一个事实，需要服务商提供查询接口才存在。审计事件 `proactive.delivered` 只记
渠道、事件类型、传输名、字符数、`truncated` 与 `address_digest`
（地址的 SHA-256 前 12 位），**不记明文地址**；正文在渲染前过一次 `redact()`。

## 后果

- 演示里「点了同意」能真的产出一条可读的消息（打开落盘文件即可核对），
  同时默认配置仍然什么都不发——**发不出去是配置事实，不再是缺 handler 的 bug**。
- 控制台「已推送」徽标旁边挂了脚注，讲的就是这条 `SENT` 口径。
- 多出一个 PII 面：`OutboundNotice.record()` 为了可核对，落盘文件里**含明文地址与正文**。
  因此 `local_file` 只允许非 prod、路径必须显式配置（默认注释掉），演示一律写在 `.tmp/`
  下（已在 `.gitignore` 里）。
- 队列侧行为有个反直觉的点：一次投递失败之后**立刻**再点「投递」会得到
  `{"claimed": 0, ...}`，因为退避窗口还没过；这不是幂等坏掉，是 `available_at` 还没到。
- 出站不进 `evals/` 的 101 条评测集（那里测认知路径的终态与轨迹），由
  `tests/test_outbound.py` 的 17 条用例 + 一次真实 HTTP 与浏览器走查守住。

## 备选方案

- **地址从 payload 读**：省一次映射反查，代价是「把消息发给谁」变成调用方可控。否决。
- **不用 Outbox，`confirm` 时同步发一次**：路径最短，但会破坏 ADR-013 的不变量
  （出站事实必须与业务事实同事务落地、失败可重试），也会让客户确认请求等一次网络 I/O。
- **直接接 SMTP 或企业微信 API**：没有凭据、没有回执，等于在文档里承诺一个查不到的事实。
  改成 `OutboundTransport` 的第四个实现是本决策留下的口子。
- **用 Celery / 外部 broker 代替 Outbox worker**：演示环境（单机 SQLite + 无 Redis）跑不动，
  而且会把「与业务事实同事务」换成「跨系统最终一致」，属于另一期工程。
