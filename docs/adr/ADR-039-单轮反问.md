# ADR-039：单轮反问——模型读出的那一行不改路由，只换一次确认

- 状态：已接受（随 F-1 实现落盘；本 ADR 由交付轮 T7 补写；2026-10-29 经独立 reviewer 复审，结论**通过（附一般项）**，一般项（内部数字 / 引用漂移）已由后续返工轮处理；复审未运行任何测试 / 构建 / lint，结论以只读检索与逐行阅读为据）
- 日期：2026-10-29
- 关联：ADR-020（对话入口的模型缺口——本 ADR 修订它留下的「问句不问模型」形状）、ADR-024（三级模型闸门——`question` 档的语义在此被改写）、ADR-030（决策复用——复用轮为何天然换不出反问）、ADR-033（澄清候选降级）、ADR-034（意图候选收窄——反问选项就是那批候选）、ADR-037（写意图判定迁到意图目录）、`app/agent/counter_question.yaml`（唯一判定口径，第 7 轮独立复查通过）、`docs/下一步规划.md` §15.5.2 / §15.7

## 背景

三级闸门把「规则读不懂」分成两档，两档各丢一类信息，而且**丢得悄无声息**。

**问句档一次都不问。** `model_gate()` 判成 `question` 的回合（规则读不出 + 这句是问句）
今天不碰模型：返回的是一个**固定字典** `_QUESTION_GAP`（`app/agent/support_agent.py:176-185`，
`source: rules` / `intent: UNKNOWN` / `adopted: False` / `gate: question`）。
理由写在函数自己的 docstring 里（`app/agent/support_agent.py:123-125`）：
「No model reading could be adopted for a read question, so the call would buy nothing.」
前半句对——采纳面只有 `REFUND_REQUEST`（`app/agent/pydantic_agent.py:39`）；
后半句错——「不能采纳」推不出「问了没价值」，因为读出来的那一行还可以**拿去问客户**。
于是客户问「运费谁出？」（探针 `scripts/llm_gap_probe.py:103`）得到通用菜单；
探针里三句转人工话术（:100-102）也在菜单里打转。

**咨询档问到了，然后丢掉。** 非采纳的合法读数在 `_consult_model` 的「不采纳 → 原样返回规则读数」
return 点（`app/agent/support_agent.py:1787`）被无声丢弃：我们手里有一个「服务端有证据、
模型认为规则读错了」的行名，客户收到的却仍是兜底答案，两边都不知道对方看到了什么。

**但反问不能改变路由，这是硬约束。** 意图采纳的口径（`app/agent/support_agent.py`、
ADR-024 决策）定死了非退款读数不改路由、模型读数不执行写动作。而 `IntentBrain.plan()`
的两条模型分支**必然**执行 `decide_adoption()` 并把判定计数写进 trace——盘上不存在
「只问模型、不做采纳判定」的现成入口。所以「问一次但不采纳」不是一句口号，
它要求**新开一条通路**，或者要求**一个新的数据携带方式**。这是本 ADR 的全部内容。

## 决策

### 1. 反问是「一次确认」，不是「第二次路由」

四条前置同时成立才反问（口径 §3.1）：`AGENT_MODE=pydantic_ai`、`counter_question_enabled`
为真、本会话上限位未置位、模型给出**合法候选读数**（在当轮候选集内、非 `UNKNOWN`、非 `NONE`）。
展示面再加一条（口径 §3.3）：**只有当轮规则读数是 `UNKNOWN` 才展示**——反问替代的只有
`UNKNOWN` 兜底菜单那一段（`support_agent.py:564`），其他落点保持各自的答案。
草稿的 `intent` **永远是规则读数**，不是模型读数（`_counter_question_draft` :224-240），
`resolved=False`，`Draft.action` 为空。

### 2. 问句档新开一条只读问询通路

`IntentBrain.probe_question()`（`app/agent/pydantic_agent.py:686-770`）复用与 `plan()`
同一个候选内核和同一个 `IntentAgent.parse`，然后**停住**：不调 `decide_adoption`、
不产 `ModelDecision`、不 `replace` 四计数键。这三件事由行号就能自证：全文件
`decide_adoption` 只出现在 :580 与 :637（都在 `plan` 内），唯一的 `replace(` 在 :661
（也在 `plan` 新路径内），而 `probe_question` 是 :686 之后的另一条路径。
返回的 `QuestionProbe`（:458-481）里，调用方只需要问一个事实——`asks`（:479-481）；
「为什么不问」落在封闭词表 `QUESTION_PROBE_REASONS`（:447-455）的七个码上，
**不是新 trace 键、也不是客户可见文本**。

读数本身是**裸目录行 id**，不做 `Intent` 枚举转换（:746-756 的注释写明这是 T4 消费端的决定）：
`REFUND_STATUS` 这类「在目录里但不是 `Intent` 成员」的行是合法读数，
而反问要的只是它的中文显示名。

### 3. 咨询档借用采纳面已经算好的那一个布尔

`decide_adoption` 的公式（`app/agent/pydantic_agent.py:90` 起）已经排除了「无改道」「NONE」
「越界」三类读数，所以 consult 出口的反问触发判据就是照抄它的输出：
`model_trace.redirect_rejected is True`（`support_agent.py:1768-1775`）。
对话层**不重写等价逻辑**——「再拼一遍 `adopted` / `redirect_kind` 组合」会造成两处判据各说各话。
采纳 return 点（:1788-1798）不反问，因为「被采纳」与「被拒的改道」这两个四键组合互斥，
无需另设条件。

### 4. 数据经两个「带内、永不序列化」的字段同轮携带（路线 γ）

反问要成句需要「读数 + 候选 id 序」跨过 `plan()` 的返回值边界，而拓宽返回元组会波及
口径 §14.2 登记的约 30 处解包点（含 `app/services/runtime.py:410`），二次调用模型违反单本账。落法是
`ModelTrace` 新增两个默认 `None` 的字段：`answer`（:203）与 `candidate_ids`（:204），
**只有** `plan` 新路径那一次 `replace`（:661-682，`candidate_ids` 写入在 :675）赋值；
`as_dict()`（:237-261）不写它们、`from_dict()`（:211-235）不读它们，因此它们进不了
`model_gap`、进不了 `ModelDecision.trace`、进不了数据库、span、审计 detail 与客户文本。
判据是逐字相等：反问轮 `ModelTrace.as_dict()` 的键集与落地前相同，
`ModelTrace.from_dict({})` 两字段为 `None`（口径 §8.3、§12.13）。

**由此得到一条免费的正确性**：`plan` 的台账复用分支返回的 trace（:600
`ModelTrace.from_dict(decision.trace, reused=True)`）两字段必为 `None`，
所以「从台账复用的读数」天然换不出第二次反问——不是一句纪律，是一个 `is not None` 判据。

### 5. 上限是状态位，随回合末那一次槽位写回落库

`ConversationSlots.counter_question_asked: bool`（`app/services/conversations.py:42`，
随 `to_dict` :59 / `from_dict` :85 全量往返；`from_dict` 缺键取 `False`，因此**零迁移**）。
置位表达式 `carried.counter_question_asked or counter_asked`（`support_agent.py:721-723`）
经**既有的那一次** `conversations.save_slots(...)`（:731）落库
（口径 §5.1 裁定 (b)；(a)「独立的条件 UPDATE」被否决，见下）。
置位时机是「反问文本真的成为本回合的回复」，与审计行同一个位置——
所以不存在「置了位但没问出口」或反过来的中间态，被拦的轮次也**不清** carried 的已置位。

### 6. 文案是数据，且缺一个名字就整句不问

`app/agent/counter_question.yaml` + 独立 loader `app/agent/counter_question.py`：
顶层键封闭集合 `version` / `prompt_template` / `labels` / `max_options`，
`_TOP_FIELDS`（:38）+ `_reject_unknown`（:51）在加载期拒绝未知键。
`intents.yaml` 一行不加、`_INTENT_FIELDS` 一族不放宽（放宽会把「拼写键静默改变判定」
的守卫拆掉一个角）。渲染器 `_counter_question_draft`（:188-240）：`UNKNOWN` 不进选项
（它的客户语言是兜底句那句「转人工」）、`max_options` 截断、**读数或任一待呈现选项缺显示名
就整句不问**（半截反问比不反问更误导）。呈现序 = 携带序 = 模型实际收到的候选序，不重排。
模型输出文本 0 参与任何面向客户的字符串。

### 7. 留痕：一个新枚举值 + 一个审计动作，零新键

`clarification.reason = "COUNTER_QUESTION_INTENT_AMBIGUOUS"`
（`support_agent.py:166`）落在**既有** trace 键 `clarify_reason` 的取值域（:750），
`expected_slot` / `resumable_intent` 定死 `None`——公开契约因此从「两键必填字符串」
放宽为可空（`app/schemas/support.py:57-58`），这是**对外响应形状的一处真实变化**。
审计 `counter_question.asked` 写在**消费点**（:571-583），`detail` 恰三键
`{gate, reading_intent, option_count}`：不写客户原话、订单号、候选证据与模型原文
（与「只记候选数量、不记订单号」同一条边界）。形成但被拦的轮次**一行都不写**。

### 8. 开关只闸反问，不闸模型调用

`counter_question_enabled: bool = True`（`app/core/config.py:122`，`.env.example:203-209`）。
问句档关闭时**连探针的钱都不付**（:1663-1666，返回值与「上限已用」分支逐字相同）；
咨询档关闭时 `plan()` 调用本身不受影响（:1769）——回退的是反问，不是整个 consult 门。
回退等价范围定死在口径 §10.2。

### 9. rules 模式靠两道既有闸门保持逐字不变

所有反问代码挂在 `support_agent.py:1647-1648`（`agent_mode != "pydantic_ai"` 即早退）与
`pydantic_agent.py:603-604`（`plan` 的 rules 早退）之后，探针侧同一位置（:713-714）。
因此「状态位读、YAML 标签读、审计写」在 rules 模式全部不可达，三不变
（零模型调用 / 零反问审计行 / span 键集与取值逐字一致）不是新增守卫，是这两道闸的位置。

## 后果

**正面。**
转人工说法与「运费谁出」这类问句第一次有了「一次确认」的出口；被拒的合法改道读数第一次
不再无声丢弃；`clarify_reason=COUNTER_QUESTION_INTENT_AMBIGUOUS` 为 R10 的
「问句 / 陈述分列」预埋了单列口径（`docs/下一步规划.md:73`）；rules 模式与评测装配
（`evals/support_run.py`、`evals/replay.py` 都用默认 `agent_mode="rules"`）逐字不受影响。

**代价（三条如实登记，不得软化）。**

1. **并发情形不承诺上界，也不承诺收敛时点。** 上限的判定域是**顺序回合**：置位是回合末
   那**一次**槽位保存的一部分，而 `save_slots` 是整列覆盖写（`app/services/conversations.py:147-152`：
   `conversation.slots = slots.to_dict()`），**无版本列、无锁**，`resolve` 在回合开始裸读槽位 JSON
   （:111-121），且 `support_agent.py:524-527` 的注释明确禁止跨模型调用持写锁。机制后果：
   反问回合 T1 读到 `False`、回合末写回 `True`；与它并发、自身不触发反问的回合 T2 也读到 `False`，
   它回合末的整列覆盖会把已置位的 `True` **抹回 `False`**；于是并发都结束之后的 T3 仍读到 `False`，
   **可以再反问**。因此本文**不写**任何「最坏 N 次」或「次数 ≤ 并发回合数、随首个写回收敛」的
   结论——口径在第 7 轮复查时已把这两版量化措辞**全部撤回**（§5.1、§14.2），理由正是整列覆盖
   能把置位抹回，连「≤ 并发回合数」这块天花板都不成立。
   这条代价**不触及写路径判据**（§7 的行数增量差 0 与采纳面无关）、**不放宽顺序回合上限**、
   **不引入新机制**（无锁、无版本列、无条件更新、无新增配置项）。若后续判定该代价不可接受，
   须回报 organizer 补裁定，不得自行加锁扩面。
2. **`append` 型升级叠加下，客户看到的是「反问 + 追加句」，不是静默。** 审计行（:571-583）
   与置位（:723）都发生在**阶段七**（:601 起）之前：回合后再判一次升级（:609-617）、
   `_shape`（:620-621 → :1370-1377）随后按信号的 `reply_mode` 决定替换还是追加。
   追加型信号——`idle_timeout`（`app/agent/escalation.yaml:192-201`，`takeover: false`）、
   `risk`（:151-161，`takeover: false`）、以及 **`complaint`（:77-81，`takeover: true` +
   `continue_task: true`，接管但不丢当前任务）**——命中反问轮时，反问文本与追加句**都在**，
   这是**预期行为**。所以本文与 `specs/counter-question/spec.md` 一律**不写**
   「反问后客户看不到反问 / 反问轮必静默」这种与实物相反的措辞。
   替换型（`repeated_clarification` :187 `reply_mode: replace` 等）与「接管且非续跑」
   （`support_agent.py:533-550`）在消费点**之前**就已分流，走不到反问那段，
   因此那一类轮次**根本不产生** `counter_question.asked` 行。
3. **§12.8 的三分支是分层钉住的，不是三条端到端。** 生产消费侧只有**一道闸**：
   `_consult_model` 问句支的 `if not probe.asks or probe.trace is None`（:1677），
   只读一个事实；`probe.reason` 在整个 `app/` 内**没有任何读取点**（交付轮实测：
   `pydantic_agent.py` 定义 :445/:468/:477 与 `support_agent.py:1677` 的 `probe.asks`
   之外零命中）。所以 T6 钉住的是「**这道闸不按拒绝原因分叉**」，
   而 `NONE` / 越界 / 模型失败三分支各自的「不产生反问」由
   `tests/test_question_probe.py` 用真实 `IntentBrain` 钉在生产者侧（:183/:193/:285 与 :299）。
   端到端逐分支（`TestModel intent="NONE"` / 越界读法 / `FailingAgent` 三种回合并列断言）
   **尚未存在**，登记在下面的「已知缺口」，本轮不开测试轮。

**其他可观察后果。**
每次反问 `clarification_count` +1（`app/services/escalation.py:109`），离
`clarification_rounds`（默认 3，`app/core/config.py:57`）更近，`repeated_clarification`
命中数、转人工率、平均每会话轮数会浮动（口径 §13.1）；问句档每个满足触发的轮次多一次模型调用，
`llm_usage` 行数与 token 成本上升（口径 §13.3，`tests/test_llm_gap.py` 与
`tests/test_security_model_cross.py` 的成本断言按此改判，判据形状不动）；
单轮上限放弃了「客户补充细节后第二次反问」的机会（口径 §13.4）。

## 被否决的方案

1. **复用 `plan()` 后在反问侧丢弃读数**：`plan` 新路径必然执行 `decide_adoption`
   并把非 `None` 的判定计数写进 trace，直接违反「四键保持未判定」；产出的 `ModelDecision`
   还会被台账复用分支回放，等于**变相放开问句采纳**。「丢弃读数」丢不掉「已经判过」这个事实。
2. **对话侧绕过 `IntentBrain` 另建第二套模型调用**：产生第二套模型路径、第二本用量账与
   另一种 trace 形状，违反 `llm_usage` 单本账与单通路纪律。
3. **给状态位做原子的「检查—置位」（独立条件 UPDATE）**：需要行锁或版本列，属新机制，
   且会让置位与本轮可见回复出现不一致窗口，破坏回退等价范围的可判定性。
   残余竞态窗口如实登记为代价（见「后果」第 1 条），**不用新机制去掩盖它**。
4. **拓宽 `plan()` 的返回元组**：口径 §14.2 登记的约 30 处解包点（含
   `app/services/runtime.py:410`），
   改动面远超本任务边界。
5. **把 `CandidateSet` 对象塞进 `ModelTrace`**：trace 会被 `as_dict()` 搬运落盘，
   候选行是客户自己的单，越界。
6. **复用 `ModelDecision.reason` / `ModelTrace.candidates`**：前者是问句侧的拒绝原因词表，
   后者是**计数不是行**（`app/agent/pydantic_agent.py:177-180` 注释原文
   「A count, never the rows or their evidence」），装不下 id 序。
7. **给反问单独加计数器、历史栈或专用升级信号**：上限是 1，bool 足够；历史栈与专用信号
   都会新设一套真相（口径 §11.5、§5.2）。
8. **默认关闭、留给评测轮再开**：与口径 §10.1 已定死的默认值冲突，且实现轮无法验收
   §12.1 / §12.3 的正用例（会被闸死）。
9. **给反问扩意图目录或加 `Draft.cards` 新 kind**：扩大留痕面与呈现面（口径 §4.5、§11.6）。

## 已知缺口

1. **`counter_question_asked` 没有「写回后立刻读」的语义**：同一回合内的判定用的是回合开始时
   的 `carried`，因此**同回合**不可能自我修正——这是设计，但意味着任何「同回合内多处判上限」的
   未来改动都会踩空。并发不设上界的完整机制只在口径 §5.1 与本 ADR「后果」第 1 条两处登记。
2. **`probe.reason` 今天在生产侧无人读取**。后果是：问句档的拒绝原因只存在于探针返回值与
   `tests/test_question_probe.py` 的断言里，**运维侧读不到「今天有多少问句轮被 `NONE` 挡掉」**
   ——口径 §3.2 明文禁止为此新增 trace 键（覆盖读数留给 R10），所以这不是遗漏，是排期。
   配套的端到端分层断言见「后果」第 3 条。
3. **「复用轮不产生反问」目前是由类型保证的，没有端到端用例。** 保证它的是 :1772 的
   `model_trace.answer is not None` 与台账复用 trace 的两字段 `None`。
   现盘证据只有单元级断言（`tests/test_consult_counter_question.py` 与
   `tests/test_question_probe.py` 的相应用例），没有一条「同一请求两次、第二次走台账复用」的
   端到端反问轮用例。登记为待增强项，**不得写成已覆盖**。
4. **`max_options=3` 与「候选集上限 6」的关系没进守卫**：两个数是两份数据里的两个约定
   （口径 §4.3、§14.3），没有断言钉住「呈现上限 ≤ 答案上限」，改一边不会报错。
5. **`labels` 与 `intents.yaml` 的行集没有交叉校验**：loader 只校验顶层键封闭与类型；
   目录新增一行而 `labels` 忘了补，后果是**含该行的那次反问整句不问**（由 :218-220 保证
   不发半截问句），不是崩溃，也不是日志可见的告警。
6. **`model_gate` 的 docstring 已经过期**：`app/agent/support_agent.py:123-125` 仍写
   「No model reading could be adopted for a read question, so the call would buy nothing」，
