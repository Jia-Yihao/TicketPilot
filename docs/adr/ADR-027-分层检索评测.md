# ADR-027：分层检索评测集——金标给质量，银标只给覆盖

- 状态：Accepted
- 日期：2026-10-25
- 关联：[ADR-026](ADR-026-查询改写.md)（查询改写）、[ADR-021](ADR-021-稠密通道闸门.md)（稠密门控）

## 背景

旧检索评测只有 `evals/support_set.json` 里 **17 条带 `policy_id` 的标注**。它能卡住回归，但有两个
问题：

1. **量太小**：17 条里一条用例就能改变 `recall@1` 约 0.06，改写前后、通道之间的差异很容易
   被单条样本的偶然性淹没；
2. **没有分层**：质量结论和覆盖结论混在同一个数字里，无法回答「是主路径变好了，还是只是
   多覆盖了几种问法」。

需求方要求把评测集扩到 1k 量级，并且明确：**外部数据只能借措辞，不能借标签**。因此不能把公开
客服语料的问答对直接当金标，也不能让模型生成的标签冒充人工标注。

## 决策

建立 **1,000 条分层检索评测集** `evals/retrieval_set.json`，由
`scripts/build_retrieval_set.py` 从两个进仓库的源文件生成：

| 层 | 规模 | 来源 | 用途 | 是否有门槛 |
|---|---|---|---|---|
| `legacy_gold` | 17 | `evals/support_set.json`（原样保留） | 跨版本可比的历史回归 | 是 |
| `gold_dev` | 100 | 手写金标 | 调参 / 诊断，不作为发布结论 | 否 |
| `gold_test` | 100 | 手写金标 | 主质量结论 | 是 |
| `silver_dev` | 400 | 模板生成 | 覆盖与压力 | 否 |
| `silver_test` | 400 | 模板生成 | 覆盖与压力 | 否 |

质量指标（`recall@1/3/5`、`mrr`、`nDCG@5`）与覆盖指标**分开报告**；银标数字只能叫「覆盖指标」，
不能和金银标合并成一个总数。`stale_hits` 与 `cross_tenant_hits` 在每一层都必须为 0。

### 1. 金标：逐条对照政策写定

`evals/retrieval/gold_cases.json` 按「政策 → 章节」分组，每章 8～16 条，共 200 条：

| 政策 | 条数 | 章节 |
|---|---|---|
| `POLICY-REFUND` | 80 | 适用范围、退款条件、退款金额、审批要求、结果确认 |
| `POLICY-DELAY` | 48 | 延迟判定、处理方式、证据要求 |
| `POLICY-RETURN` | 48 | 七天无理由退货、退货与退款的区别、不予退货的情形、操作要求 |
| `POLICY-TICKET` | 24 | 优先级定义、创建规则、转人工 |

每条用例带 `query` / `policy_id` / `sections` / `facets`（5W1H 子集）。生成器在构建时校验：

- 章节必须属于该政策的 ACTIVE 章节表；
- 金标问法**不得逐字出现在政策正文里**（防止把原文复制成问句）；
- 六个 5W1H 面向都必须有人覆盖，不允许全堆在 `WHAT`；
- 全局 id 与 query 都不能重复。

`split` 由生成器按每章前一半 `dev`、后一半 `test` 固定分配，不随机，因此同一份源文件永远
生成同一个 100/100 拆分。

### 2. 银标：标签由构造决定

`evals/retrieval/silver_templates.json` 定义 **20 个模板 × 8 个问法 × 5 个槽位 = 800 条**。
每个模板声明 `policy_id` / `section` / `facet` / `slots`，槽位值只替换问法中的占位符，
期望章节由模板本身决定——**不是模型判断、也不是人工逐条标注**，所以叫银标。

银标用来回答「改写会不会把某类问法整体带偏」「某章节是不是长期没有召回」，不用于证明
检索质量。它的分母大，单条波动小，适合当压力与覆盖信号。

### 3. 外部数据只借措辞

公开数据选用 ModelScope 的 `E_commerce_Customer_Service`（Apache-2.0）。
`scripts/sample_external_phrasings.py` 按固定规则抽 200 条**用户原话**，只保留
`query` 与文件行号：

```json
{"provenance": {"dataset": "...", "file": "dev_clean_v2.jsonl", "line": 6},
 "query": "什么时候发货啊"}
```

- **不导入**外部数据自带的意图、答案或相关性标签；
- 采样文件与 `manifest.json` 进仓库，记录来源 URL、许可证、源文件 SHA256、采样 SHA256；
- 采样脚本需要原始数据集，**不是 CI 依赖**；CI 只校验已入库采样文件的哈希与字段；
- 200 条外部问法**不进任何指标分母**，它只证明措辞来源可追溯。

### 4. 门槛只套金标

`evals/retrieval/thresholds.json` 只写两层：

```json
{
  "gold_test": {"recall@1": 0.75, "recall@3": 0.9, "recall@5": 0.9,
                "mrr": 0.85, "ndcg@5": 0.85},
  "stale_hits": 0, "cross_tenant_hits": 0
}
```

`legacy_gold` 继续沿用 `support_set.json` 里原有的五项门槛；`gold_dev` 是调参集，不设门槛；
银标两层**没有通过/失败这一说**。阈值取当前实测值向下留出余量，不按单条用例回调。

### 5. 生成器是唯一入口

```bash
python scripts/build_retrieval_set.py          # 写出 retrieval_set.json
python scripts/build_retrieval_set.py --check  # 重算并与入库文件逐字比较
```

`--check` 在 `tests/test_retrieval_set.py` 与 CI 里都会跑。数据集形状、分层拆分、模板网格、
金标不抄原文、章节不漂移、外部问法哈希与「只借措辞」边界都由测试钉住。

## 证据

同一语料、同一 `today`、同一 BM25 通道，只切换 `--rewrite`（2026-10-25 实测）：

| 层 | recall@1 关 → 开 | recall@3 关 → 开 | recall@5 关 → 开 | MRR 关 → 开 | nDCG@5 关 → 开 |
|---|---|---|---|---|---|
| `legacy_gold`（17） | 0.7941 → **0.9706** | 0.9118 → **0.9706** | 0.9706 → 0.9706 | 0.8745 → **1.0000** | 0.8824 → **0.9772** |
| `gold_dev`（100） | 0.8700 → **0.9050** | 0.9600 → 0.9500 | 0.9600 → 0.9600 | 0.9433 → **0.9658** | 0.9303 → **0.9450** |
| `gold_test`（100） | 0.7550 → **0.8100** | 0.9400 → 0.9400 | 0.9400 → 0.9400 | 0.8733 → **0.9067** | 0.8743 → **0.8976** |
| `silver_dev`（400） | 0.7438 → 0.7612 | 0.9150 → 0.9200 | 0.9200 → 0.9325 | 0.8700 → 0.8792 | 0.8590 → 0.8711 |
| `silver_test`（400） | 0.7312 → 0.7300 | 0.9012 → 0.9163 | 0.9350 → 0.9350 | 0.8587 → 0.8610 | 0.8568 → 0.8595 |

所有层的 `stale_hits = 0`、`cross_tenant_hits = 0`。`gold_test` 的五项门槛全部通过。
两处回落都记在这里，而不是抹平：`gold_dev` 的 `recall@3` 从 0.960 降到 0.950（100 条分母上
正好少 1 条命中）；`silver_test` 的 `recall@1` 从 0.7312 降到 0.7300（400 条分母上净少
0.5 条命中，46 条用例有升有降后相抵）。其余指标在两个金标层与两个银标层上均不降。

门槛文件写的是 `gold_test` 当前值的下方余量：`recall@1 ≥ 0.75`（实测 0.81）、
`recall@3 ≥ 0.90`（0.94）、`recall@5 ≥ 0.90`（0.94）、`mrr ≥ 0.85`（0.91）、
`nDCG@5 ≥ 0.85`（0.90）。这不是目标值，是回归护栏；检索器变强后应同步抬高。

## 后果

- `docs/guide/评测说明.md`、`docs/spec/项目规格.md` §14.2.1 与 `README.md` 的检索基线必须按层报告，
  不能再只写一个 17 条的总分。
- 新增 `tests/test_retrieval_set.py`：生成器可复现、1,000 条形状、200/800 与 100/100/400/400
  拆分、15 个章节与 6 个面向全覆盖、20 个模板各 40 条、门槛只出现在 `gold_test`、金标不抄原文、
  章节表与种子库 ACTIVE 政策不漂移、外部采样 200 条且哈希/许可证/字段符合 manifest。
- 银标由模板生成，**问法多样性受 20 个模板限制**；它涨了不等于真实流量上也会涨。
- 金标由项目单人写定，**没有第二标注者与一致性系数**；章节标签唯一、对照政策原文，
  但「同一句话是否只能对应这一章」仍可能有边界争议。
- 200 条金标只覆盖随包的 4 份政策、15 个章节；换语料必须重写金标，不能只扩模板。
- 外部采样只借措辞，不构成对公开数据集质量的背书；采样文件的许可证与来源随 manifest 一起保留。

## 备选方案

- **把公开客服语料直接当金标**：外部数据自带问答对，但标签体系与本项目章节不对应，
  且无法核对政策原文；照搬会把别人的标注错误变成我们的质量结论。
- **用模型生成 1,000 条金标**：成本低，但模型标签无法审计，且会把模型偏见写进门槛。
  本轮只允许模板生成**银标**，金标必须人工逐条对照政策。
- **只扩旧金标到 1,000 条**：人工成本高，且 17 条之外的问法分布没有真实流量依据；
  分层后把「主质量结论」控制在 200 条，既够稳定又能逐条复核。
- **金银合并报一个总数**：银标占 80%，会把金标的问题稀释掉；分层报告才能看出差异。
- **给银标也设门槛**：模板问法可预测，门槛很容易被拟合，且不能代表真实问法，因此不设。
