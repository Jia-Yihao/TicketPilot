# ADR-011：转人工是一等公民，Agent 接管后必须静默

- 状态：Accepted
- 日期：2026-10-24

## 背景

「转人工」在之前的实现里只是一个意图：命中后创建一张工单，客户拿到一个工单号。

这不符合客服系统的真实形态：

1. **客户要的是人，不是工单。** 工单是后台产物；「我要人工」是要现在有个人接上。
2. **接管之后 Agent 还在说话。** 如果人工已经在回答，Agent 继续插话（「还需要我帮您查一下吗」），是明显的体验事故。
3. **移交内容会丢。** 坐席接手时看到的是「客户要退款」，而不是「客户已经提供了订单号 ORD-DEMO-1001、退款金额 129 元、上一轮检索到的政策版本是 refund-v3」。客户被迫再说一遍。
4. **没人知道 Agent 什么时候该停。** 「客户问了三次都没解决」「客户说了一句『你们这什么破服务』」——这些都需要一个可判定的触发条件，而不是靠感觉。

## 决策

### 1. 转人工是状态，不是工单

会话有一个接管状态机，Agent 在其中扮演一个角色：

```text
AGENT_ACTIVE --escalate--> HANDOFF_PENDING --claim--> HUMAN_ACTIVE
     ^                            |                      |
     |                            +--timeout--> QUEUED    |
     +---------release------------+----------------------+
HUMAN_ACTIVE --close--> CLOSED
```

- `HANDOFF_PENDING`：已升级，等待坐席接单；
- `QUEUED`：等待超时（`handoff_claim_timeout_seconds`，默认 120 秒），仍在队列里等；
- `HUMAN_ACTIVE`：坐席已接管；
- `RELEASED`：坐席把会话交还给 Agent；
- `NOTED`：坐席记录了但不接管（也要在队列里被看到）；
- `CLOSED`：会话了结。

`HUMAN_ACTIVE` 与 `RELEASED` 之间是**接管静默**：`HUMAN_ACTIVE` 期间 Agent 不再产出客服回复，只处理仍然在跑的任务。

### 2. 触发条件是数据，不是代码

`app/agent/escalation.yaml` 声明 8 个信号，代码不重复这些值：

| signal_id | 优先级 | 触发方式 |
|---|---|---|
| `user_request` | P0 | 客户明确要人工 |
| `complaint` | P0 | 消息含投诉线索 |
| `risk` | P0 | 意图风险等级达到 R3 |
| `frustration` | P1 | 连续负面轮次达到阈值 |
| `repeat_failure` | P1 | 连续未解决的意图轮次达到阈值 |
| `no_evidence` | P1 | 检索没有可用依据 |
| `repeated_clarification` | P2 | 连续追问槽位次数超阈值 |
| `idle_timeout` | P2 | 空闲分钟数超阈值 |

信号按声明顺序判定，同优先级下先列出的胜出，所以「投诉」即使同时命中「不满」，也仍然进投诉队列。

信号只描述**触发什么**；**比多少**放在策略引擎（`app/core/policy.py`）里，可以独立调整：

```text
escalation_frustration_rounds / handoff_after_failed_attempts /
escalation_no_evidence_score / session_idle_minutes /
handoff_claim_timeout_seconds / handoff_repeat_window_hours /
abandon_idle_minutes / handoff_digest_max_chars
```

每个信号还声明 `reply_mode`（替换回答还是追加）、`soothe`（客户在生气时先安抚）、`continue_task`（接管期间写操作是否继续跑）。

### 3. 移交包随事件一起存

`HandoffBundle` 在升级时构造并**存进事件里**：意图记录、槽位、动作记录、引用、情绪快照、摘要。

这样坐席的首屏与审计留痕不可能对不上「当时移交了什么」——它们读的是同一份数据，而不是各自重建。

### 4. 坐席侧是独立入口

7 个坐席接口（队列、详情、接单、释放、关闭、指标、放弃），与客户接口分开：

- 坐席接口要求 `support` 角色，缺角色返回 403；
- 队列按租户隔离，跨租户表现为 404；
- 接单别人已接的会话返回 409；
- 释放会把会话交还给 Agent（`RELEASED`），而不是关掉它。

指标接口按租户统计，给出：会话数、升级过的会话数与升级率、Agent 自助解决率、未结案例数，以及按队列 / 原因 / 信号 / 小时四个维度的分布；另有放弃事件数、放弃率与按渠道 / 意图 / 小时的分布。放弃（`abandon_events`）单独记录，因为「客户放弃等待」是这类系统最重要的失败信号。

## 后果

- 「我要人工」不再产生一张没人看的工单，而是进入一个有人接的队列。
- 客户不必重复自己说过的话：移交包里已有订单号、金额、已查到的政策。
- 接管期间 Agent 沉默，不会和人工抢话。
- 触发阈值与回复话术在 YAML 里，可以灰度调整而不发版。
- 代价是多了一套状态机、一张事件表和一组坐席接口；复杂度是可接受的，因为它替代了「转人工=建工单」这条本来就不对的路。

## 备选方案

- **继续用「转人工=建工单」**：客户拿到的只是工单号，体验与「排队等一个人」差得很远。
- **把升级逻辑写进代码**：阈值与话术会散落在服务层，调整阈值要改代码并重新发版。
- **接管期间 Agent 仍然回复**：省掉静默逻辑，但人工与 Agent 同时说话是最明显的体验事故。
- **移交内容实时重建**：坐席首屏与审计可能不一致；存快照更简单也更可靠。
