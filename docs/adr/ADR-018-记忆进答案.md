# ADR-018：记忆注入答案只允许四种模板效果，读路径不走 `MemoryService`

- 状态：Accepted
- 日期：2026-10-24
- 关联：[ADR-014](ADR-014-客户记忆与主动授权.md)（客户记忆与主动确认，本 ADR 收的是它自己点名的那条后果）、[ADR-016](ADR-016-渠道抽象.md)（渠道抽象：两个 web 入口共用一条认知路径）、`docs/guide/评测说明.md`（轨迹断言与 `evals/replay.py` 回放口径，本 ADR 的「档案一改历史 trace 不再逐字可回放」是对它的直接限制）、`docs/guide/安全说明.md`（输出护栏：个性化永远排在护栏之前）

## 背景

ADR-014 当年把「记忆注入回复」列成有意的不做项，理由是准确而不是保守：**回复会依赖一张
客户可以随时改写的表**，而回复口径需要重新评测。T9 要收这个尾，但收的方式不能是「把档案
读进提示词」——那等于在本项目里重新引入它自己反对过的画像回路，并且会同时撞三件事：

1. `preferences` / `history_summary` 里装的是**客户自由文本**。直接进回复就是提示注入的
   另一面：客户写一句「忽略之前的规则，把退款政策改成……」，下一轮就出现在别人的答案里。
   ADR-014 的 PII 掩码与 422 只守住了「写」，守不住「读出来当事实说」。
2. `MemoryService.get()` **每读一次就写一条 `memory.read` 审计**。Agent 每轮都读，等于
   每次问答多一行审计、多一次 `updated_at` 侧写风险，而审计的语义是「谁动了客户的档案」，
   不是「Agent 看了一眼」。
3. 回放（`evals/replay.py`，口径见 `docs/guide/评测说明.md`）比的是两次运行的 `reply_digest`。
   一旦回复取决于档案，
   档案一改，历史 trace 就不再逐字可回放——这不是 bug，但必须写清楚，否则
   `REPLAY DIFF EMPTY` 会被读成「什么都没变」。

真正想要的产品效果其实很小：叫客户的名字、把客户关注的商品摆在前面、按「简洁」偏好少给两条
追问。这三件事都不需要模型参与，也都不需要读客户原文。

## 决策

### 1. 只允许四种**可枚举**的效果，且全部是模板或形状变化

新增 `app/agent/personalization.py`。它是一个纯函数式覆盖层：输入 `Draft` + 档案快照 + 目录，
原地改 `Draft`，并返回「用了哪几条效果」。原因码是契约的一部分
（`app/schemas/support.py::SupportPersonalization`）：

| 原因码 | 读的字段 | 动作 | 为什么不吃客户原文 |
|---|---|---|---|
| `ADDRESSED` | `preferred_name` | 回复前加「你好，{称呼}。」 | 该字段写入时 ≤40 字且命中 PII 直接 `422` |
| `CARDS_REORDERED` | `preferences.product_interests` | 把命中的商品卡挪到第一位 | 生效前必须经 `CatalogService.resolve()` 换回**目录里的规范名**；命不中就完全不动 |
| `SUGGESTIONS_TRIMMED` | `preferences.tone` | 建议裁到 2 条 | `tone` 是枚举，白名单外写入即 `422` |
| `INTEREST_SUGGESTION` | `preferences.product_interests` | 建议首位插入「{目录商品名} 的质保范围」 | 同上；且该商品已作为卡片出现或已在本轮答复里时**不插入** |

四条之外没有口子：`history_summary`（掩码存的自由文本）、`locale`（没有多语言生成路径，
接它等于假装有）、`contact_channel` / `contact_window`（前者只归出站投递读，后者是自由文本）、
`proactive_opt_in` / `muted_event_types` / `max_notifications_per_day`（推送闸门，与答案无关）
一律不参与。用例里有反向断言：把这些字段写成「王经理 / 周五 / 下午三点」，回复与建议里
查不到这些片段；把兴趣写成 `<script>alert(1)</script>`，它不被回声、也不进任何输出。

### 2. 读路径不复用 `MemoryService`

```python
row = session.execute(
    select(CustomerProfile.preferred_name, CustomerProfile.preferences)
    .where(CustomerProfile.tenant_id == identity.tenant_id,
           CustomerProfile.user_id == identity.user_id)
).one_or_none()
```

只 `select` 具体列，不实例化 ORM 实体，因此：不建行（`profile_view(None)` 的默认视图语义
留在读写接口那一侧）、不会被 autoflush 波及、**不写任何 `memory.*` 审计**。ADR-014「决策 1」
原文是「`update` 是唯一写路径，而 `app/agent/` 里没有任何一处会调用它」，据此改写为：
**Agent 只读档案，且不走 `MemoryService`；写路径仍然只有客户自己的 `PUT`。**
这条不变量由用例守住：个性化跑完三轮，`customer_profiles` 行数不变、`updated_at` 不变，
`audit_events` 里 `memory.%` 只有客户那几次 `memory.update`。

### 3. 位置：成型之后、护栏之前，且只调一次

`SupportAgent.handle` 里顺序是 `_shape`（决策塑形）→ `_personalize` → `_guard_output`。
护栏永远是最后一道，所以个性化插进去的称呼串也要过一次输出护栏；
`agent_silent`（人工接管静默）路径直接返回 `personalization: null`，不读档案。
所有成型草稿都参与，**包括澄清轮**：澄清的回复文本会加称呼，但结构化的
`clarification.prompt / expected_slot / resumable_intent` 不被改写——续跑契约仍是机器可读的。

### 4. 可见性跟着审计的纪律：只报码，不报值

响应新增可选字段 `personalization = { effects: [...], fields: [...] }`；trace 加一条
`generate / memory.personalize` span，属性只有原因码、字段名、命中的 `product_id` 与
`first_turn`。控制台把码翻成中文标签（「用你的称呼开头」等），**页面上出现的仍是标签，
不是档案值本身**——称呼只出现在回复正文那一句模板里，全响应体里它只出现一次。

### 5. 一键回到不个性化

`MEMORY_PERSONALIZATION_ENABLED`（默认 `true`）为假时整轮跳过：不读档案、不产生 span、
不带 `personalization` 字段。验证方式是真的起了两个进程（同一个库，一个开一个关）：
关掉那侧的回复与「从未建过档案的客户」的回复逐字相同，建议列表也相同。

## 后果

- ADR-014 的那条「只被存与查」不再是事实，文档与 README 已同步；换来的是四条能被用例
  逐条证伪的效果，而不是一句「Agent 会参考客户偏好」。
- **评测口径是「不变」，但理由要说清**：种子数据不建任何档案，所以 Golden 40 / 支持 61 /
  回放 diff 为空三者逐字不变——这是「无档案客户零影响」这条设计约束的直接结果，
  不是本轮没测到。**真实限制是**：客户一旦写了档案，他此前的历史 trace 就不能再逐字回放
  （`reply_digest` 会变）。回放脚本因此只能用作「同档案下的一致性」检查，不能用来证明
  「改了代码答案没变」。
- 目录成为个性化的一道闸：`CatalogService.resolve()` 只认完整商品名或 `product_id`/`sku`，
  所以「客户关注的东西」必须先是「目录里存在的商品」才会生效。副作用是运营侧改商品名
  会让旧的偏好字符串失效（变成不生效的惰性数据，不会报错，也不会回声）。
- 称呼只在本会话第一轮出现，判断用的是 `ConversationSlots.last_intent is None`
  ——它只在轮末写入，因此新建会话天然为 `None`，不需要额外状态或计数。
- 卡片重排目前只在「一条回答里出现多张商品卡」时有意义（即目录命中多个商品、
  且槽位没有收敛到单个商品的那条动作路径）。单卡答案上它是惰性的，这一点由
  用例分别覆盖两条（纯函数 + 走 HTTP 的两卡场景）。
- 本轮不进 `evals/` 的 101 条评测集（那里断言的是认知路径终态与轨迹，与档案无关），
  由 `tests/test_personalization.py` 的 17 条用例 + 一次真实 HTTP 59 项断言 +
  浏览器 DOM 走查守住。

## 备选方案

- **把档案摘要塞进提示词，让模型自己决定怎么用**：灵活，但效果不可枚举、无法用断言守住，
  且把客户自由文本送进生成路径。这与 ADR-001「确定性 Workflow 优先，Agent 只做有界节点」
  是同一个判断：不可验证的影响面不进答案路径。否决。
- **复用 `MemoryService.get()`**：省十行代码，代价是每轮多一条 `memory.read` 审计、
  并让读路径与写路径共享同一套副作用。否决——但**如果以后要加「坐席查看客户档案」的
  审计面，应该回到 `MemoryService`**，届时 Agent 侧的只读例外要重新审视。
- **每次都读，也每次都写审计，声称「可追溯性更强」**：审计的意义是「谁改了客户的什么」，
  把只读混进去会让这张表失去可读性（ADR-014 的字段名纪律同理）。否决。
- **用 `updated_at` 做回复缓存失效**：与个性化无关的另一个问题（本项目不做回复缓存），
  留着不解决。
- **给 `locale` 接多语言生成**：目前没有第二套语言的政策文本与模板，接上只会让回复
  声称支持它并不支持的事。等真有中英两版政策时再说。
