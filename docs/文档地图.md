# 文档地图

这套文档分成四卷，每卷只回答一类问题。改代码之前先确认你要改的口径属于哪一卷——写错卷的地方，
下一个人就会在两处读到两个版本。

| 卷 | 目录 | 谁来读 | 只回答一个问题 | 不该出现在这里的内容 |
|---|---|---|---|---|
| 对外叙事 | 仓库根 `README.md` | 第一次打开这个仓库的人 | 它是什么、凭什么可信、哪里不行 | 逐轮读数、返工与审查记录 |
| 使用与实现 | `docs/guide/` | 要跑起来、要改代码的人 | 它怎么运作、接口长什么样、边界在哪 | 历史决策的来回过程 |
| 契约 | `docs/spec/` | 要改行为的人 | 系统**必须**表现出什么行为 | 实现步骤、操作日志 |
| 记录 | `docs/records/` | 要追溯「当初为什么」的人 | 那一轮发生了什么、当时读数几 | 当成现状的结论 |

## 唯一事实源

同一件事只允许有一个定义处，其余都是引用：

| 事实 | 唯一定义处 | 怎么被守住 |
|---|---|---|
| 业务行为与不变量 | `docs/spec/项目规格.md` | 说明书由它渲染，摘要不一致守卫就红 |
| 接口形状 | 代码里的 `app.openapi()` | `docs/guide/接口说明.md` 与它逐条对齐；路径与操作数由守卫现算比对 |
| 文档里的数字 | `docs/fact-baseline.yaml` | 守卫现算代码再比对，文档只写「哪一行有个数字」 |
| 文档点名的代码符号 | `docs/code-anchors.yaml` | 守卫用 AST 确认符号真的存在 |
| 分层依赖方向 | `docs/architecture-guard.yaml` | 守卫按这份清单检查 `app/` 的 import 图 |
| 还剩什么没做 | `docs/下一步规划.md` 的 §0.2 | 每项都能在代码里被核实，做完必须给读数 |
| 为什么这么排 | `docs/下一步规划.md` §15 | 判据可判定；条目落入 §0.2 后以清单状态为准 |

## 写文档的三条规矩

1. **数字不手抄**：要么交给守卫绑定，要么写成「时间点读数 + 生成命令 + 日期」，并且标明它已经不是现状。
2. **不写「本轮 / 上一轮」**：那是记录卷的语言。主文档只写现状与待办。
3. **改规格必须重生成说明书**：`python scripts/build_manual.py`（或 `make manual`），否则 `tests/test_docs_consistency.py` 会红。
